# Rust SPDM in the Kernel

> 说明：本文依据 LPC 2026 官方 22 页幻灯片、报告摘要和 v4 补丁封面信整理。页码指该 PDF 页码；补丁细节以封面信标明。开发状态为报告及 v4 的快照，不代表当前内核发行版状态；“后续发展启示”为分析，不代表会议共识或独立安全审计结论。

## 核心结论

报告介绍一套用 Rust 实现的最小 SPDM 请求方，代码位于 `lib/rspdm/`，包含 `state.rs` 与 `validator.rs` 等文件。它基于 Lukas Wunner 的 C 实现思路并经过重构；v4 封面信说明这是独立系列，而非依赖原 C SPDM 系列才能工作的实现。核心问题是安全地解析不可信设备响应，并把认证机制与用户态策略衔接起来。

v4 的目标很明确：先把"能跑通的最小实现"推进上游，为后续工作提供构建基础。当前实现只在与设备完成认证后向用户态返回"已认证"（authenticated）这一结果，并未把证据或证书链暴露给用户态，也不代表证书链已锚定到受认可 CA，或完整安全策略已被接受。换言之，"已认证"只表示在已实现的那部分检查下通过，距离完整的信任决策还有相当距离。v4 并非完整的 SPDM 功能集，度量端到端证据路径也尚未打通。报告把这一状态如实呈现为单步推进的起点，而非终点承诺。

## 问题背景

SPDM 由 DMTF 标准化，用于认证、证明与密钥交换，采用请求方（requester）与响应方（responder）模型；这里主机内核作为请求方，设备应答。`GET_CERTIFICATE` 用于取得证书链，`CHALLENGE` 则让响应方证明持有相应私钥，二者不能混为一个步骤。设备证明还使用固件、配置和状态等度量值，供验证者结合参考值与安全策略作判断（第 4 至 6 页）。协议体系也支持安全会话与受保护的消息，但 SPDM 会话不等同于 PCIe IDE 数据面加密，也不等同于 TDISP 的设备接口安全分配流程；本报告没有证明这些后续能力已由 v4 一并实现。

威胁模型把尚未验证的设备视为可能恶意，因此协议解析器本身就是攻击面。报告以 SPDM 1.2.1 近 200 页、1.3.0 近 250 页说明规范复杂性，并将 Rust 用于不可信数据解析作为主要动机（第 3 页）。Rust 的所有权和有界访问有助于减少内存安全风险，但不会自动证明状态机、密码学、资源限制和策略正确；安全 Rust 也仍需避免输入导致的 panic。v4 还与 C 密码学和 X.509 设施交互，不能称为完全没有 `unsafe` 或 C 代码的实现。

## 核心技术

实现使用不可信数据包装类型 `Untrusted` 与 `Validate` trait，并为校验函数提供 `context`，携带 `SpdmState` 等协议上下文。响应字节经显式校验转换为普通 Rust 结构，而非直接以 C 风格指针转换为 `repr(C, packed)` 结构。`.get()` 等可失败访问用于检查输入范围，构造结构时显式转换字节序，并将不满足要求的输入作为错误返回（第 9 至 11 页及 v4 封面信）。

v4 的关键取舍是将响应解析、拷贝为类型化 Rust 结构，而不是把报文直接映射成 packed 结构。作者认为常规协议报文较小、认证不在持续数据面热路径上，因此可接受额外拷贝，以换取更清晰的校验、字节序处理和结构访问。这是设计理由，不是已经量化的性能结论；材料没有提供拷贝开销或吞吐基准（v4 封面信）。

幻灯片第 9 页以 `GET_VERSION` 为例：先校验返回长度、再做截断、然后走 `Untrusted` 校验；第 10 页为 `GetVersionRsp` 的解析案例，第 11 页为 `NegotiateAlgsRsp` 的分支处理。这里必须区分三层含义：`validate()` 让内部类型"合法"，并不等于密码学上"证书可信"，也不等于策略上"被批准"。这三层是独立的判断，不能混为一谈。

集成路径上，PCI 侧通过 TSM 提供 C 语言的 PCI CMA 驱动（幻灯片第 12 页），它调用 Rust 请求方库并通过传输回调工作，PCIe DOE 作为示例传输。封面信给出的 QEMU NVMe over DOE 是测试示例，说明该路径可端到端跑通，但这并不表示所有原生 NVMe 命令传输都已就绪。SPDM 可承载于多种传输，涵盖 PCIe、MCTP/SMBus/I3C、TCP、SCSI/ATA、NVMe 等协议可能，但第 13 页与第 21 页所示其他驱动属于未来工作，并非全部已实现。术语上需要澄清：TSM 指 Trusted Security Module，负责 PCI 安全驱动协调，并非 TPM；CMA 指 Component Measurement and Authentication，并非 Contiguous Memory Allocator，二者在此语境下与内存分配无关。

## 用户态接口与未决问题

v4 为 00/22，于 9 月 28 日提交并征求评审（幻灯片第 14 页）。最小请求方支持 `GET_VERSION`、`GET_CAPABILITIES`、`NEGOTIATE_ALGORITHMS`、`GET_DIGESTS`、`GET_CERTIFICATE`、证书校验与 `CHALLENGE`（依据封面信补丁列表）。度量端到端证据路径尚未完成。封面信明确列出当前不支持的内容：不向用户态暴露证据或证书、不允许用户提供 nonce、不支持 PQC 或更高级特性，只在已实现检查下返回"已认证"。证书链并不对内核 keyring 校验，留待用户态策略在证据 API 可用后再做。

必须强调：返回"已认证"并不意味着证书链已锚定到受认可 CA，也不代表完整安全策略已被接受。这一点在阅读实现状态时尤为关键，不能把"协议握手通过"等同于"设备可信"。RFC v3 曾有 netlink 证据与自定义 nonce 的概念验证，最小化的 v4 将其移除，草稿并非已发布兼容契约，不应据此假设未来 ABI 形态。封面声称对 SPDM 1.4 提供"初始支持"，但第 21 页表明更多 1.4 特性属未来工作，不宜声称完整 1.4；PQC 同样属未来。

用户态接口的讨论集中在如何取得证据并执行策略（第 16 至 19 页）。官方摘要还提出让远程验证者在内核可能恶意时验证系统的需求，这是目标而非当前安全保证。单个 Netlink 属性的长度字段为 16 位，大小约受限于 64 KiB，而报告希望承载的证据 blob 可接近 16M；后者是目标证据规模，不代表每个 SPDM 报文或每份证据都如此大，也不是整个 Netlink 消息体系的总大小上限。第 16 页的 NACK 指此前“multi-message object receive”设计遭到评审反对，不是运行时接收方返回的协议错误，更不代表所有 Netlink 方案都被否决。

第 17 页的候选包括：去掉 `F_MULTI`，每条消息重复相关属性并增加 offset，使片段更独立；或保留 `F_MULTI`，将对象拆为多属性，并让 YNL 支持重组。第 18 页讨论 [`nla_put_blob()` 提案](https://github.com/l1k/linux/commit/6e73bb999128)，将 blob 后备页作为 skb fragments，目标是降低复制及 skb 大小限制，不能据此声称端到端路径已经零拷贝。第 19 页介绍 [CTLV 的 pre-RFC 草案](https://github.com/jpirko/linux_mlxsw/commits/wip_ctlv_pre_rfc_draft1/)：使用 provider 中立的 fd/ioctl 接口，将大证据写入引用缓冲区，并把用户态裁决绑定到准确的设备/证据代次（generation），同时表示度量日志、事件和安全状态转换。以上均是讨论方向，不是已定稿 ABI。

## 当前进展与路线图

第 14 页明确状态为 v4 已提交并请求评审；第 21 页列出零拷贝、更多 SPDM 1.4 特性、PQC 和其他传输作为后续问题。封面信给出 QEMU PCIe NVMe 设备经 DOE 通信的测试方式，但没有提供跨设备兼容性、生产部署或性能基准。当前目标是先提交最小请求方作为基础；更完整的证明证据接口、信任策略和扩展协议能力仍需后续工作。提出补丁、演示通信与完整可部署支持是三个不同阶段。

## 后续发展启示（分析）

其一，应把输入解析、协议不变量和 C FFI 安全边界分别评审。类型化校验降低风险，但不能代替长度算术、协议状态、错误恢复和资源上限验证；小型安全抽象和恶意输入测试有助于后续扩展。这是工程建议，不是本文独立发现的缺陷或安全证明。

其二，机制与根/策略需要分离。内核只提供认证机制，证书信任根与策略判断交由用户态决定，避免把策略硬编码进内核。这也是当前不校验 keyring、待证据 API 可用后再回到用户态的原因。

其三，大体量证据接口不仅要搬运字节，还要绑定设备身份、证据代次和裁决。设备复位、固件更新或重新采集之后，旧证据对应的批准不能被不加区分地套用到新状态。CTLV 的 generation 绑定方向说明，生命周期一致性与数据传输同样重要。

其四，多传输架构应保持可扩展，并对各传输的接入状态给出清晰标注。PCI 经 TSM 接入，其他传输因 TSM 不适用而需各自的 netlink 或 sysfs 包装，库本身能支撑，但状态需透明。

其五，SPDM 是安全 I/O 信任链的一环，不能替代 IOMMU DMA 隔离、IDE 数据面保护或设备分配策略。用户态完整信任决策尚未具备时，尤其应避免把 `authenticated` 当作放开设备权限的充分条件。
