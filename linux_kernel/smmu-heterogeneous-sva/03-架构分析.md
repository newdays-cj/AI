## 2. 必须分开的标识与对象

```text
原进程 mm（进程身份和退出事件）
  └─ 统一 PASID P
       ├─ CPU 共页表设备的绑定 → 原进程 CPU 页表
       └─ 异构设备的绑定      → 同一个设备地址空间
                                 ├─ 合法 VA 范围、权限、驱动内存对象
                                 ├─ 一份异构物理页表及其配置
                                 └─ 多个 SMMU 的硬件上下文及失效状态
```

1. PASID 是请求选择标识；不等于 CPU/SMMU TLB 的 ASID/VMID。
2. 同 PASID 可以在不同设备/group 上选择不同类型的翻译根；同一 group/PASID 只有一个 core attach handle，不能未经适配挂两个冲突 domain。
3. 异构侧的虚拟地址、映射权限和页表根统一，CPU 侧 VA 与之无关。
4. 共享页表内容，不代表共享 CMDQ、配置缓存或设备 ATC。每个实例仍有硬件绑定及完成状态。
5. 在同一硬件翻译缓存命名空间里，不能让两套可能冲突的翻译根随意共用同一缓存标签。CPU 视图与异构视图通常需区分其 ASID；即使 PASID 相同，也不应直接复制原进程 CPU ASID。具体按翻译制度/VMID/ASID组合判断。

| 普通 SVA unbind | `void iommu_sva_unbind_device(struct iommu_sva *)`；每次绑定引用对应一次解绑，调用前停止该 PASID 新请求并冲刷硬件请求 |

| map | `int iommu_map(domain, iova, paddr, size, prot, gfp)`；必须确认当前domain ops/页表格式支持；不得传入物理不连续范围当作连续映射 |
| unmap/sync | `size_t iommu_unmap(domain, iova, size)`、gather相关接口；检查实际撤销长度，确认必要失效完成后释放内存 |
| io-pgtable | `alloc_io_pgtable_ops(fmt, cfg, cookie)` / `free_io_pgtable_ops(ops)`；cfg被allocator调整，free前硬件不可再walk；flush callbacks可在原子上下文调用，不得睡眠 |

## 4. 动态行为与生命周期

### 4.1 当前绑定与释放

```text
SVA bind（iommu_sva_lock）
 → 校验/建立 owner_mm->iommu_mm，分配或复用PASID
 → 查找/分配 SVA domain，mmgrab(owner_mm)
 → attach（group mutex → 后端锁）
 → 安装 CD/STE、发布绑定引用

进程 mm_users 归零
 → __mmput → exit_mmap
 → mmu_notifier_release：先冻结次级访问
 → CPU unmap/free页表

最后 mm_count 归零
 → __mmdrop → mm_free_pgd/destroy_context
 → mm_pasid_drop：释放进程PASID
```

证据：`iommu-sva.c:72–159,303–330`；`fork.c:973–991,1459–1480`；`mmap.c:3433–3472`。

扩展时不应长期 `mmget(owner_mm)` 并等待进程退出通知，否则自己会阻止mm_users归零。建议按现有notifier/mm_count模式保持结构，短期操作再 `mmget_not_zero()`；原进程退出时关闭上下文，最后引用清理不依赖用户显式调用。

原进程 mm 是PASID身份基准，不因新增设备mm而改变。异构先绑定时需要从同一个分配入口取得/建立owner_mm的PASID状态；若后续设备的有效PASID范围（包括下界、上界及保留值）不容纳该值，应拒绝新增绑定，不能静默重编号已有活跃设备。当前core主要检查上限，不等于完成全部兼容性检查。第一次绑定也不知道未来所有设备范围，公共范围策略须在⑤明确。

### 4.2 推荐的不变量及状态转换（两种候选共用）

- 上下文：PREPARING → LIVE → CLOSING → DEAD；只有LIVE接受新绑定、登记、map及成功补页。
- 绑定：准备能力/资源 → 安装但不提交设备任务 → 纳入可维护的后端集合 → 允许访问；不能先启用设备再加入失效列表。
- 范围：合法但未驻留 / 已映射 / REVOKING。缺页不得只凭地址相等复用已撤销范围的旧内存对象。
- map成功后所有已启用异构设备能walk同一份有效映射；新增设备绑定同一根，不回放复制全部页表。
- 多设备绑定不要求一次API原子绑定所有设备；某一新设备失败只回滚其本次资源，不破坏已有设备。

主动映射与按需缺页共存：登记驱动对象和范围后，可以立即建立PTE，也可以留空由故障补齐。重复同页缺页只产生一份最终映射，同步已完成后才回复成功。

### 4.3 独立 VA 缺页

```text
事件中的设备/group + PASID
 → attach handle / per-instance domain
 → 共享设备地址空间
 → 校验LIVE、范围、权限及对象offset
 → 获取/按需分配驱动内存页（允许睡眠处执行）
 → 再次检查范围状态/代际
 → 一次修改共享异构页表，完成必要映射同步
 → 向原请求设备回复并释放IOPF group
```

不得 `handle_mm_fault(owner_mm, device_va)`。CPU可选映射同一内存对象但不参与独立VA权限判断。若设备内存不能按需分配或不支持struct page，内存对象的取页/取物理段契约必须据实际内存类型确定，不能泛化使用GUP。

查找与撤销需明确串行点：可用短期读锁+范围对象引用及代际，慢分配后重查；或先采用可睡眠范围锁覆盖补页提交。不要在自旋锁内分配内存/等待设备。

### 4.4 撤销、退出与错误路径

撤销先阻止范围内新补页，删除或标记PTE，执行硬件要求的BBM/同步，完成BTM或显式TLBI和必要ATC维护，确认不再有旧内存访问后解除对象引用。TLB失效完成不应未经硬件协议证明就等同所有设备在途DMA完成；必要时需要队列排空、fence或阻断访问。

退出/移除时：禁止新访问与新补页 → 硬件冻结/停止来源 → 排空或拒绝在途缺页、等待既有work → 撤销上下文与完成失效 → 释放绑定、共享表、内存对象及PASID引用。具体停机与同步可以分阶段，但`release`返回前必须保证进程CPU页被回收不会被旧设备访问；驱动自持内存可留到后续work释放，不能仅排队清理却放任硬件继续访问已失去所有权的对象。

主要失败规则：

| 失败点 | 必需结果 |
|---|---|
| PASID/ASID/页表分配失败 | 返回错误，成对撤销本次引用，已活跃绑定不受影响 |
| 新设备格式/粒度/属性/广播域不兼容 | 不能复制另一份表来伪装满足R5；BTM不兼容可显式失效，翻译本身不兼容则拒绝绑定 |
| 映射部分完成 | 撤销本次已建立部分并完成失效；不可将残留映射报告为全成功 |
| 合法范围补页失败 | 回复失败，不发布指向未初始化或已释放对象的PTE |
| 失效/停机超时 | 不报告安全撤销成功，不释放可能仍被访问的页及标识；阻断/恢复策略在⑤明确 |
| 退出与新绑定竞争 | 退出状态发布后禁止提交新绑定；初始化中的资源也必须回收 |

## 5. BTM 与 ASID 深入分析

### 5.1 已确认事实

标准驱动设置CR2.PTM，SVA的SMMU ASID来自独立xarray，当前不靠CPU广播自动维护。UMMU普通SVA则pin CPU ASID并按硬件BTM能力决定notifier；但其根仍是CPU pgd。

`arm64_mm_context_get()`（`arch/arm64/mm/context.c:279–323`）受CPU ASID锁、代际、pinned数量及KPTI规则约束。为独立设备视图保留一个架构分配的标签是一种可能的桥接，但需要与SMMU私有ASID分配器协调，不能只把get返回值覆盖到CD字段。

### 5.2 新发现：本地下游CPU flush作用域优化

`arch/arm64/include/asm/tlbflush.h:188–201` 的 `flush_tlb_begin()` 依据 `mm_cpumask()` 返回LOCAL/DOMAIN/BROADCAST；`:306–328`、`:611–661`据此选择本地TLBI或局部域TLBIP等。相关提交包括：

- `040bad800013`：无FEAT_TLBID时也启用local TLBI。
- `5468798756f2`、`e28c4375a213`、`a43893f89baa`：按TLBID优化整mm、范围和单页失效。

没有CPU运行记录的设备mm，直接调用普通flush很可能选择LOCAL，不能保证SMMU接收。即便使用原进程mm，CPU分布也不足以代表全部设备所在的广播拓扑。

因此：**设备失效必须有显式、已验证的作用域选择；不得靠伪造mm_cpumask来绕过优化。** 此处是新特性与既有优化的交互约束，不是在本任务内认定或修复整个系统其他驱动的问题。

### 5.3 两种候选共同的BTM契约

1. 区分设备VA视图与CPU视图的翻译标签，明确广播接收者、地址范围、翻译制度和安全状态。
2. 页表写入对所有walker可见；根据硬件需要执行cache clean和屏障。多个walker的DMA配置不同，不能只对一个iommu_dev做DMA同步就假定全部可见。
3. 兼容后端使用明确作用域的广播与完成保证，其他后端显式失效；统一API等待必要路径完成。
4. ATC与配置缓存按各自语义处理。支持非BTM翻译后端不代表可以忽略其缓存。
5. 广播标签释放前使所有相关硬件上下文失效并排空访问；CPU ASID pin仅是其中一个资源。

可研究的实现分支：A）架构提供设备专用ASID保留/广播接口；B）合法辅助mm仅作ASID token，保留CPU格式pgd且不承载设备PTE，再提供明确设备广播入口。token并非统一地址空间对象的必需替代，也不等于“新mm自然支持BTM”。选哪种需要硬件协议和⑤设计，不在本阶段伪造寄存器实现。

## 6. 新 mm 方案的可复用部分与边界

### 6.1 文件 mmap/fault 钩子不能替换整个页表格式

`__handle_mm_fault()` 在文件fault之前已执行 `pgd_offset/p4d_alloc/pud_alloc/pmd_alloc`（`memory.c:5884–5985`）。后续也可能安装CPU PTE。`exit_mmap()` 先unmap/free CPU页表，再close VMA（`mmap.c:3455–3483`）。故不能将异构根写进`mm->pgd`后只改file ops。

另外，文件mmap回调发生在VMA最终插入/发布前（`mmap.c:2935–2997`），回调中建立设备映射后仍可能发生回滚；它不是整个映射事务完成通知。VMA close也不能替代部分unmap/mprotect的同步撤销协议。

### 6.2 可行的“保留新mm”变体

新增一个正常CPU格式、从不承载异构PTE的mm，复用其VMA元数据和mmap_lock；异构物理页表另存共享对象。通过新设备缺页入口在CPU页表walk之前分流，并通过完整映射/撤销适配层维护设备表。

这可以保留“文件+地址区间”的编程风格，但需要：

- 明确地址选择、map/partial unmap、权限与VMA拆分/合并的支持集合；审计current依赖。
- 明确metadata mm的CPU PGD永远由CPU MM正确分配/释放，异构根另存；拒绝CPU fault/GUP等不受支持入口进入设备范围。
- 主进程与metadata mm分别管理生命周期，PASID仍来自原进程，而非调用两次普通SVA分别分配。
- 设备fault采用专用契约，不能随意直接调用普通vm_ops->fault并继承CPU的`vm_fault`返回值/锁约定。
- metadata mm若用于ASID token也必须显式pin和广播，不能复用普通flush作用域。

这是原始提议的受控变体，架构上可实现，仍有更多MM适配成本。把异构格式贯穿通用MM所有walk/teardown的完整可插拔mm改造则属于更广泛第三方向，目前缺少必要性，不作为最低成本方案。

## 7. 并发与锁约束

### 当前事实

- SVA全局mutex → core group mutex → SMMU ASID mutex；设备列表使用spin_lock_irqsave。后端回调不得反向调用取SVA全局锁的绑定函数。
- notifier注册需要mmap_lock及MM内部锁；notifier的arch secondary TLB回调可在PTL自旋锁下调用，不得睡眠。
- attach lookup只借用handle；IOPF异步任务和退出必须有独立生命周期保护。
- io-pgtable flush callbacks可以在原子上下文调用，不能直接在其中获取共享地址空间睡眠mutex或等待workqueue。
- `tlb_flush_all`、`tlb_flush_walk`有同步完成契约，不能仅排队到workqueue后返回。允许延迟的leaf失效须在gather/sync等明确完成点收敛，完成前不得回收相关内存及页表；若硬件无法满足此上下文约束，⑤需调整接入方式，而非省略同步。

### 候选公共策略（⑤需形成可验证锁序）

- 控制面可睡眠锁管理bind/map/unmap事务；后端快路径仅短期锁/原子操作，慢分配和设备排空不在自旋锁下。
- 共享页表对象引用独立于某个绑定；后端列表读侧若用RCU，只在RCU段中取得稳定引用，再退出读侧做可睡眠工作。RCU不替代硬件完成。
- 不在持有IOPF worker需要的范围锁时flush该worker；先标记CLOSING/REVOKING，解锁后排空，再完成回收。
- notifier注册放在可安全持mm_users的准备阶段，避免在持控制锁时进入可能回调同一对象的MM路径；发布LIVE前复核退出状态。
- map/unmap与设备加入用固定后端快照或串行事务，防止新设备错过失效；解绑先移出可访问状态，但引用保留至所有失效/worker完成。

## 8. 配置、接口与外部依赖

现有Kconfig及Makefile已在②核实：ARM_SMMU_V3_SVA依赖标准驱动并选择SVA/IOPF/MMU_NOTIFIER；UMMU是ARM64/ARCH_HISI/UB专用。新增框架不应无故依赖整个UMMU硬件栈。

外部consumer主要是调用SVA绑定的设备驱动、新的自研功能驱动、IOMMU后端、MM退出通知。当前还没有自研驱动，不能列出不存在的consumer调用链。映射/绑定是内核接口；是否新增ioctl由⑤界定。CPU侧可选设备文件mmap不代表异构地址空间需暴露为普通进程VMA。

不预设新增sysfs/procfs/debugfs作为功能接口；验证需要观测PASID、页表根及失效路径，可通过后续明确的测试后端/trace设计提供，不能把调试读取当作硬件正确性的唯一依据。

## 9. 缺口策略与影响评估

| 缺口 | 初步策略 | 影响范围 |
|---|---|---|
| 原进程统一PASID，异构先绑定 | 提取/扩展同一个mm级分配和引用契约 | iommu-sva.c、iommu头文件；保持旧接口行为 |
| 一份异构表跨实例 | 页表存储/ops与per-instance domain分离，共享所有权 | 自研IOMMU后端、io-pgtable格式；必要的core接口 |
| 独立VA登记和补页 | 独立范围对象或metadata mm变体 | 新管理层、IOPF handler、驱动内存接口 |
| BTM优先与回退 | 设备失效后端及显式广播作用域、ASID协调 | ARM64 context/TLBI边界、自研硬件配置 |
| 进程退出及热移除 | owner-mm notifier + 状态机 + 排空/失效完成 | 管理层、设备驱动、IOPF队列 |
| 硬件缺失下验证 | 可执行mock验证软件资源/并发，真实或模型验证BTM/翻译 | 阶段⑥测试设计；不降低R1–R10 |

潜在冲突包括本树ARM64 local/TLBID优化、io-pgtable CONT/dirty tracking扩展、UMMU logic/config共享更新、SVA ABI/KABI及厂商扩展。不能据现有未跟踪文件推断具体并行任务，实施前需重新检查Git状态与相关历史。逻辑依赖顺序应为共享所有权/PASID基础 → 页表及绑定后端 → 内存与缺页 → 失效策略及生命周期联动，再做组合验证；实际commit拆分在⑤决定。

本分析没有发现已确认目标之间必然矛盾；未知硬件参数是设计输入缺口，不申请需求回退。交由④比较两种可实现的组织方式。
