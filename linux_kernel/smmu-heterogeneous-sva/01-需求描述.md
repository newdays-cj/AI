# 异构 SMMU 页表与统一 PASID 支持

## 1. 状态与背景

- 项目：smmu-heterogeneous-sva。
- 基线仓库：`/home/chenjun/Git/OLK-6.6-2`，OLK-6.6 下游内核。
- 当前阶段：① 已经 Momus 条件通过并按意见修订，用户已确认；进入②调研。
- 用户确认原文：“按建议确认，增加BTM优先”。确认范围见第7节。
- 当前没有对应的自研设备/SMMU 驱动可供分析。

同一进程需要绑定多个 SMMU 的后端设备。其中一部分 SMMU 可以使用 CPU 页表，另一部分不能使用 CPU 页表，但后者的页表格式相同，硬件允许指向同一份物理页表。用户希望保留 SVA 的相关能力，同时由驱动管理独立设备地址空间及内存映射，并避免调用者逐个 SMMU 重复建立映射。

## 2. 已确认的原始诉求与约束

| 编号 | 需求 |
|---|---|
| R1 | 同一进程可绑定多个 SMMU 的后端设备。 |
| R2 | 同时考虑可与 CPU 共页表的设备和使用异构页表的设备。 |
| R3 | 所有使用异构页表的设备共享设备虚拟地址空间，对同一内存使用相同设备虚拟地址。 |
| R4 | 异构设备虚拟地址与 CPU 侧无关，不要求相同；不要求自动镜像 CPU 地址空间。 |
| R5 | 异构 SMMU 的页表格式相同，必须共享一份物理页表。 |
| R6 | 映射对象仅考虑驱动内存；由驱动主动建立映射。 |
| R7 | 异构侧提供统一映射入口，调用者无需按每个 SMMU 重复执行映射操作。 |
| R8 | 同一进程的 CPU 共页表设备和异构设备全部使用相同 PASID；不同进程仍须隔离。 |
| R9 | 保持第3节列出的 SVA 能力，包括异构侧可恢复缺页；保持现有 SVA 调用者行为，允许新增异构侧接口。 |
| R10 | 缓存失效流程尽量利用 SMMU 的 BTM（Broadcast TLB Maintenance）能力，减少逐 SMMU 软件失效；这是优先优化目标，不豁免必要的同步及回退。 |

“驱动内存”的具体分配来源、CPU 映射属性、缓存一致性模型，尚待硬件与驱动接口信息明确；本阶段不假定它一定是普通可缓存系统 RAM。

## 3. SVA 能力边界（已确认）

| 能力 | 确认边界 |
|---|---|
| 绑定与解绑 | 支持进程关联、多个设备绑定、重复绑定引用管理和设备移除；CPU 共页表侧保留现有 SVA 行为。 |
| PASID | 同一进程统一管理 PASID，并协调现有 SVA 分配机制；覆盖任一类设备先绑定以及最后解绑的顺序。 |
| 主动映射 | 驱动对异构地址空间执行一次 map/unmap，维护一份共享异构页表；逐 SMMU 的硬件同步由底层完成。 |
| 可恢复缺页 | 必须支持。允许驱动先登记合法内存范围，缺页时根据设备地址定位驱动内存对象、建立页表项并恢复访问。不能直接使用该地址触发原进程 CPU 缺页；目标硬件须具备相应请求与重试能力。 |
| 无效访问 | 越界、无映射或无权限访问不能建立授权外映射，不能返回虚假恢复成功。 |
| 生命周期 | 进程退出、设备移除、解除绑定和撤销映射时，明确停止访问、排空缺页/在途请求、缓存失效和内存释放的顺序。 |
| CPU 侧兼容 | 不改变现有 CPU 共页表设备的地址语义；异构映射不自动在原进程 mm 中建立映射。 |

保持现有 SVA 调用者行为，允许新增异构侧接口。默认 `handle_mm_fault()` 路径依赖 CPU 页表格式，异构侧不能未经适配直接使用。硬件尚未提供，不能承诺现有 SVA 的所有硬件相关行为均可验证。

## 4. 功能目标

1. 支持按进程统一管理设备绑定与异构映射，区分 CPU 共页表地址空间和独立异构地址空间；具体对象结构留待方案选择。
2. 异构侧统一管理虚拟地址、权限、内存对象及共享页表，支持设备先绑定后映射、先映射后增加设备。
3. 同一进程两类设备使用同一 PASID，分别指向各自翻译上下文；异构设备共享独立设备地址空间和物理页表。
4. 页表修改与每个 SMMU 的失效操作分离；映射撤销完成后，不允许旧映射继续被使用。
5. 对绑定、映射和资源分配失败定义可观测结果及回滚规则，不发布不完整的可用映射，不泄漏资源。
6. 优先采用 BTM 失效路径。仅在广播维护的标识、翻译制度、作用域和完成语义均适配共享异构地址空间时使用；不满足条件的后端采用显式失效。PASID 相同不代表广播使用的 ASID/VMID 等标识相同。独立设备地址空间不自动受原进程 CPU TLBI 正确覆盖。页表格式不同本身也不直接证明 BTM 可用或不可用。

## 5. 初步候选方向（不是已确认设计）

优先候选为“每进程统一管理上下文 + 原进程 mm 的 SVA 后端 + 独立共享异构页表后端”。异构页表不直接放入 `mm->pgd`；共享页表对象与各 SMMU 的硬件绑定、失效状态分离。

用户最初提出“每进程创建新 mm_struct，通过 __do_mmap_mm 和设备文件 mmap/fault 管理异构页表”。该方向保留为方案对比候选，尚未确认或排除。正式方案选择在调研与架构分析之后进行。

### 已核对的本地线索

- `mm/mmap.c`：有 `__do_mmap_mm()`，但仍有当前任务上下文依赖，需要审计，不能等同于通用异构页表支持。
- `mm/memory.c`：普通缺页路径按 CPU 页表格式遍历、分配页表，不能仅靠文件 fault 回调替换整个格式。
- `drivers/iommu/iommu-sva.c`：现有 PASID 与 `mm->iommu_mm` 关联；`mm_pasid_drop()` 负责释放。新后端必须协调所有权，不能独立重复分配或提前释放。
- `drivers/iommu/iommu.c`：有 `iommu_attach_device_pasid()`；绑定按 IOMMU group/PASID 管理，需评估设备分组对不同后端并存的限制。
- `drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c`：普通 S1 domain 有 PASID 绑定实现，但当前不允许该 domain 跨不同 SMMU 实例使用。共享硬件页表不等于现有 domain 可直接跨实例复用。

上述只是需求可行性线索，不是阶段②的上游调研结论，也不证明自研硬件已获支持。

## 6. 验收标准（阶段①确认基线）

| 编号 | 对应需求 | 验证及通过判据 |
|---|---|---|
| AC1 | R1/R2/R8 | 同一进程绑定至少一个 CPU 共页表设备和两个异构 SMMU 后端设备；检查全部设备 PASID 相同，翻译根符合所属类型。分别验证两类设备先绑定的顺序。 |
| AC2 | R3/R5/R7 | 调用一次异构映射接口；两设备使用同一设备地址访问同一物理内存，读写结果正确。两个异构 SMMU 页表根指向同一份物理页表，增加设备不复制已有页表。 |
| AC3 | R4 | 使用与 CPU 映射地址不同的设备地址，或在 CPU 侧未映射该对象时执行异构访问；访问正确，CPU 地址空间未被隐式增加对应映射。 |
| AC4 | R6/R7 | 对已绑定设备执行映射、解除映射，以及先映射后增加设备；返回成功后所有已启用设备看到约定映射。撤销完成后通过翻译检查和设备访问验证旧映射不再可用。 |
| AC5 | R9 | 对有效但尚未建立页表项的驱动内存范围触发可恢复缺页，映射到正确内存并成功重试；无效地址和越权请求被拒绝。目标硬件或模型须支持该请求与重试路径。 |
| AC6 | R8/R9 | 不同进程的绑定不能越权访问彼此对象；解绑一个设备不影响其余设备；覆盖进程退出、设备移除和在途缺页并发，检查无资源泄漏、悬空访问或 PASID 过早复用。 |
| AC7 | R7/R9 | 注入内存分配、绑定和映射失败；接口返回明确错误，已做的本次变更被回滚或保持明确的未启用状态，可重试且不影响既有映射。 |
| AC8 | R2/R9 | CPU 共页表路径回归测试通过；异构页表操作不改变该路径的映射语义。新增配置关闭时不影响既有行为。 |
| AC9 | R10 | 在支持且配置兼容的 BTM 后端上，记录广播触发、覆盖范围及完成路径；通过映射替换、权限收紧和解除映射后的设备访问验证旧翻译不可用。对不支持、受勘误限制或配置不兼容的后端验证显式失效回退，含可用与不可用后端混合绑定。ATS/ATC 等缓存是否受广播覆盖须单独证明，不能默认省略其维护。无真实 BTM 后端时仅可验证软件决策，不能宣称广播端到端通过。 |

编译基线采用 `~/tools/qemu_arm64_defconfig`，后续按流程完成 ARM64 编译与 QEMU 测试。硬件驱动尚不存在，真实异构格式翻译、多 SMMU 共享与设备重试需要相应硬件或可执行模拟后端；QEMU 标准 SMMU 不能单独证明这些能力。需在测试设计阶段明确模拟、真实硬件及不可验证项，不能把纯软件检查记为硬件端到端通过。

## 7. 待确认与待调研事项

### 阶段①用户确认记录

用户回复“按建议确认，增加BTM优先”，确认：

1. 同一 PASID 覆盖同一进程的 CPU 共页表与异构两类设备。
2. 异构侧必须支持可恢复缺页，允许先登记合法内存范围再按需建立页表项。
3. 保持现有 SVA 调用者行为，允许新增异构侧接口。
4. 共享同一份物理异构页表为硬性要求。
5. 兼容时优先使用 BTM，不适用时保留必要的显式失效与同步。

驱动内存的来源与属性尚无规格，保留为后续设计输入，不能预先承诺支持所有内存类型。

### 后续调研输入

- 目标架构、PASID/SSID 位宽、页表层级/粒度/属性、失效与完成语义、缺页及重试协议、跨 SMMU 页表访问一致性。
- IOMMU group 布局；每个硬件可见的设备/PASID 组合必须能唯一确定一个翻译上下文。不能仅凭 PASID 相同就推断支持任意分组并存。
- 与现有 SVA 的 PASID 生命周期整合、设备加入能力校验及不兼容后端的失败规则。
- 同一进程含多个线程、fork/exec、文件描述符继承/传递及管理上下文归属的语义。
- 编程接口及其同步/异步完成约定，进程退出与显式解绑职责。
- BTM 广播接收能力及平台拓扑、ASID/VMID 标识的分配和跨 SMMU 协调、翻译制度/安全状态/共享域匹配、独立设备 VA 广播维护的触发方法与完成保证、硬件勘误及 ATS/ATC 的覆盖边界。不能仅因支持 BTM 就省略所有逐设备缓存维护。
