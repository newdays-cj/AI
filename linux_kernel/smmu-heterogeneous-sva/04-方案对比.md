# 异构页表与统一 PASID：方案对比

## 1. 决策范围

输入为已确认的R1–R10及 `03-架构分析.md`。本阶段选择地址空间组织方式，不选择未知的硬件寄存器编码，不改变统一PASID、独立设备VA、共享一份异构物理页表、恢复缺页和BTM优先要求。

两个候选均保留CPU共页表设备现有SVA接口行为，并允许为异构设备新增接口。都需要自研硬件页表后端；“可行”表示有明确的软件实现路径，不表示未知硬件已经通过BTM/翻译验证。

## 2. 公共部分：无论选哪种都需要

1. **PASID身份属于原进程mm。** 两类设备均取同一值，兼容任一类先绑定。新增绑定校验后端有效范围（下界、上界及保留值），不能只检查位宽；当前core主要检查上限，不表示全部兼容性已验证。新设备不容纳既有PASID则失败，不能默默换号。
2. **一份异构物理页表。** 多个per-SMMU绑定引用共享对象，各自保存上下文配置、能力、队列及失效状态。不能每个domain各建一份页表。
3. **独立缺页。** 设备VA查询合法范围及驱动对象，在专用入口补异构PTE并回复；不拿设备VA进入原进程CPU缺页。
4. **BTM优先，显式失效兜底。** 显式保证广播标签、作用域和完成；处理不支持BTM的实例及ATC。普通CPU flush可能LOCAL或TLBID收窄，不能直接照搬。
5. **生命周期和同步。** 进程退出、设备移除、补页与撤销有统一状态机；释放物理页、表和标识前阻止旧访问并排空相关请求。
6. **硬件兼容性检查。** 共享格式还要兼容IAS/OAS、粒度、属性、walk可见性及根地址可达性；翻译不兼容拒绝绑定，不通过复制表规避要求。
7. **失效回调契约。** io-pgtable的同步flush-all/walk回调可能在原子上下文执行，必须同步完成，不能只排队worker后返回；leaf批处理在gather/sync完成点收敛。不能以不睡眠为由破坏回收前的完成保证。

## 3. 方案A：独立设备地址空间对象（推荐）

### 3.1 实现思路

```text
owner_mm → 进程设备上下文 / PASID P
             ├─ CPU SVA绑定 → owner_mm->pgd
             └─ device_as
                  ├─ 范围索引：dev_va、长度、权限、内存对象、状态
                  ├─ shared_pt：异构root、格式ops、配置、引用
                  └─ 各SMMU绑定与失效后端
```

采用内核现有范围索引/地址分配基础设施构建设备专用元数据，不要求用VMA表达。驱动登记内存对象，调用一次map/unmap；按需补页与主动映射使用同一个内存对象和共享页表。

PASID分配扩展现有SVA的mm级契约，绑定层复用core PASID attach及IOPF。per-instance domain不拥有共享表的最终free权限，只持引用；共享表的flush cookie指向生命周期稳定的共享后端对象。

### 3.2 BTM实现方向

采用独立的设备失效接口，输入设备视图的广播标签与设备VA；后端保证明确广播作用域及完成。标签可通过架构保留接口管理，或评估正常辅助mm仅作为ASID token的桥接方式。后者不改变A的地址范围模型，也不把设备根放进mm->pgd。需要协调SMMU私有ASID命名空间和CPU allocator，不能只调用pin接口便认为完成。

硬件BTM不兼容时对相关实例显式维护；BTM可用性不阻塞软件框架的设计，但硬件完成语义必须在⑤/⑥前落实。

### 3.3 驱动使用方式（语义示意，非现有API）

```text
取得本进程上下文 → 绑定设备 → 取得统一PASID
登记驱动内存范围(dev_va, object, offset, len, permissions)
  ├─ 主动建立映射
  └─ 或允许合法范围内的设备缺页补映射
撤销范围 → 等待访问/失效完成 → 释放对象
```

地址由驱动指定或统一分配器选择；所有异构设备使用同一dev_va，与CPU地址无关。

### 3.4 优缺点与可验证性

- 优点：异构翻译与CPU MM解耦；页表一次更新；可表达不适合CPU VMA范围的设备地址；范围管理不依赖额外mm/VMA。若采用辅助mm作ASID token，仍需管理其CPU PGD、引用及ASID pin生命周期，但不承担B的设备VMA映射适配成本。
- 代价：需定义范围/对象接口、状态和并发契约，不能直接把已有普通设备文件fault当作完整设备缺页机制。
- 验证：mock可记录多个后端看到相同root、相同PASID和不同CPU/设备地址，验证单次更新、并发补页与回滚；BTM接收及实际翻译仍需要硬件或相应模型。

## 4. 方案B：设备专用 metadata mm + 独立异构页表

这是用户最初“额外mm + 文件mmap/fault”思路的受控变体，保留VMA元数据管理，避免通用MM误解异构页表。

### 4.1 实现思路

```text
owner_mm → 进程设备上下文 / PASID P
             ├─ CPU SVA绑定 → owner_mm->pgd
             └─ device_mm（正常CPU格式、设备元数据用途）
                  ├─ VMA → 驱动文件/内存对象
                  ├─ CPU PGD保持合法，不存异构PTE
                  └─ 另存shared_pt → 多SMMU引用同一异构root
```

扩展受控的非current-mm映射入口，用device_mm的VMA记录设备地址、权限与对象；异构表独立保存。文件mmap可以设置范围关联，但设备可用状态必须在整个映射事务成功后发布。

新增设备缺页分发入口，在任何CPU页表walk之前查询device_mm VMA并调用专用设备补页操作。普通vm_ops->fault的返回值、锁和PTE契约不能直接照搬；可由驱动提取共享的内存对象取页逻辑，再分别包装CPU和设备回调。

所有设备地址范围修改都经过适配层，处理完整/部分unmap、权限变化、VMA拆分/合并及失败回滚；不能仅靠vm_ops->close。device_mm不对用户公开可随意操作的普通CPU地址空间，禁止不受支持的GUP/CPU fault等入口。实现需选择明确的VMA操作子集及标记/断言，不暗示获得全部通用MM功能。

### 4.2 PASID、BTM与生命周期

- PASID始终从owner_mm取得，不对device_mm再调用普通SVA分配另一个PASID。
- 如以device_mm承载ASID token，必须pin与CPU allocator协调，再协调SMMU标签分配；页表根与ASID来源是分离的。
- 禁止直接靠 `flush_tlb_mm(device_mm)` 完成BTM，因为空mm_cpumask会触发LOCAL等优化；仍需公共设备失效入口。
- device_mm由上下文显式销毁，owner_mm退出先冻结设备，排空后解除VMA/异构表。它不会自动跟随原进程退出。

### 4.3 可行性条件、代价与验证

- 正常device_mm的PGD永远是CPU格式，通用teardown不接触异构表；异构表由独立对象唯一释放。这消除了原始“异构根直接放mm->pgd”的主要障碍。
- `__do_mmap_mm()` 已存在，为复用VMA提供入口，但需审计和改造current依赖、锁与记账。地址必须落在适配后的VMA支持范围；若硬件要求超出该范围，应显式扩展地址校验，不能截断。
- 相比A多一套mm生命周期与MM交互；权限修改/部分撤销不能漏掉设备同步。
- 验证除公共AC外，需覆盖CPU PGD未被异构操作污染、不会走CPU fault、VMA拆分合并/撤销一致性、owner退出与device_mm释放顺序，以及非current调用。

### 4.4 不采用的简化假设

本方案不是“只增加mm_alloc并写几个mmap/fault回调”：必须增加上述映射和缺页适配。若坚持将异构根本身存入mm->pgd并沿用整个普通fault/unmap/free路径，则需进一步做通用MM页表格式可插拔改造，范围远超本候选。

## 5. 对比

| 维度 | A：独立device_as | B：metadata mm |
|---|---|---|
| R1–R10目标 | 均可按公共契约实现 | 均可按公共契约实现，额外MM适配 |
| 多异构SMMU一次映射 | 更新共享表一次 | 更新共享表一次 |
| 与CPU地址无关 | 独立地址校验/分配 | 设备VMA地址，需校正CPU MM范围假设 |
| 相同PASID | 接入owner_mm分配与引用 | 同左，device_mm不另分PASID |
| 异构页表根 | 独立共享对象 | 独立共享对象，不能放CPU PGD |
| 缺页 | 专用范围查找和设备handler | 专用VMA查找和设备handler |
| VMA/文件模型复用 | 不依赖VMA，可引用内存对象/文件 | 较多复用，但须定义设备专用契约 |
| BTM | 显式标签及广播入口 | 同样需要，不因新mm自动获得 |
| CPU MM变更 | 较少，集中于必要的PASID/架构标签边界 | 较多，涉及非current映射和VMA操作路径 |
| 生命周期与锁 | 自有范围/绑定模型，较直接 | 原mm + device_mm + 共享表，交互较多 |
| 初始开发成本 | 新增设备地址范围/对象管理 | 减少部分范围管理，但增加MM适配 |
| 长期演进 | 适合设备专用地址/内存语义 | 适合确需VMA/file语义的设备编程模型 |
| 测试重点 | 范围并发、共享根、绑定/退出、IOPF与BTM | 公共项加VMA拆分、非current-mm和CPU路径隔离 |

没有硬件规格和实际实现前，不提供代码行数、性能收益或工期的虚假量化。页表写入次数相同，A的主要优势是职责边界和MM改动范围，不是已实测更快。

## 6. 推荐与选择依据

**推荐A。** 当前需求是驱动内存、独立设备VA、共享异构表，并未要求匿名内存/COW/CPU页表回收等通用MM语义。A可直接表达这些对象；B引入的MM生命周期、CPU格式PGD及VMA操作适配，并不会消除PASID/BTM/共享根的公共工作。

如果“必须通过设备专用mm和文件映射管理范围”是业务接口要求，B也有可实施路径，代价是明确接受专用缺页入口和完整映射适配，不将其视为零改动复用。

无论选A/B，若最终ASID管理使用一个合法辅助mm作token，可以作为⑤局部实现决策，不因此把A改成B。是否需要token取决于硬件BTM及架构分配边界，不应为了拿ASID而让全部地址映射依赖VMA。

## 7. 后续设计输入与阶段中止点

选择A/B后进入⑤，需补齐以下输入才能最终确定硬件后端：

- 异构页表格式和walk配置、硬件能访问的物理地址、缓存一致性与映射内存属性。
- PASID/SSID有效范围及保留值、group拓扑；CPU与异构视图不能在无法区分的同一group/PASID槽位内冲突。
- BTM匹配标签/作用域、触发及完成协议、ATS/ATC关系；独立设备VA使用广播的硬件保证。
- 可恢复缺页请求/重试、阻断和排空机制；没有现成驱动时如何建立可执行模型。
- 驱动内存对象来源与生命周期、并发和内存记账，以及fork/exec/文件句柄传递的边界。

这些不是要求用户现在提供完整驱动；可先选软件组织方案，再逐项形成硬件接口契约。但不能在未解决输入前宣称详细设计已能指导真实硬件编程。

**需用户选择：A（推荐），或B。选择本身不授权代码实施；⑤详细设计仍需另行审核确认。**
