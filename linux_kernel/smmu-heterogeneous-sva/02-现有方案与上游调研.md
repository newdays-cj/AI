# 现有方案与上游调研

## 1. 范围与证据基线

- 输入：阶段①已确认的 `01-需求描述.md`，包括统一 PASID、独立异构 VA、强制共享异构物理页表、可恢复缺页和 BTM 优先。
- 本地代码基线：`de4fb9a1670f22cb3f164ae4016380447d6074ac`。
- 上游访问时 HEAD：`c44104f3642da720164042623e4832836aefdd8e`，其 Makefile 为 **7.4.0-rc3**。本报告仅描述此已读取快照，不预设版本。
- 本地为包含大量 backport 与 UMMU 扩展的下游，不能按原生 6.6 的能力判断。
- 代码证据直接读取本地文件；上游通过 GitHub Contents/Commits/Search API 读取源码、提交消息与相关 diff。GitHub raw 返回429，kernel.org/lore 部分页面返回反爬挑战；未取得的邮件正文不作已读证据。
- 流程指定的 explore/librarian 均尝试启动，但模型 `openai/gpt-6.1` 不存在导致失败；改由主代理直接调研。

## 2. 结论摘要

1. 已核实的机制中，**未发现无需修改代码即可完整满足所有已确认需求的方案**。这不是断言所有社区代码都不存在，而是本报告证据范围内的结论。
2. 现有 SVA 已能让同一 mm 的多个设备使用同一 PASID，但其默认缺页处理与 ARM SMMUv3 翻译根都依赖 CPU 页表。
3. 普通 S1 domain + PASID 可承载独立页表，但当前 ARM SMMUv3 domain 绑定单个 SMMU 实例，不能直接跨实例共享该 domain；统一 map API 不等于共享物理页表。
4. 下游 **UMMU logic 层、SVA separated 模式**是重要参考，比单纯新增 mm 更贴近多实例统一编程需求。separated 引入背景是无 IOPF 场景，但当前能力检测与模式选择有条件分支，不能据此宣称该开关下绝对不支持 IOPF。现有页表后端仍为 ARM LPAE；已读证据尚未证明其独立设备 VA、统一进程 PASID和恢复缺页形成满足本需求的完整路径。
5. **当前标准 ARM SMMUv3 路径没有启用 BTM**。它设置 `CR2.PTM`，SVA 通过 notifier 发 CMDQ TLBI 并单独维护 ATC。上游已读取 HEAD 也是如此；不能把 BTM feature 宏和注释当作可用实现。
6. BTM 不要求 CPU 真正使用异构设备页表才能在概念上讨论广播，但需要一个正确、无冲突的广播标识及可用触发/完成机制。相同 PASID、共享物理根均不足以证明这一点；自研硬件条件仍待补齐。

结论：继续 **Feature** 路径；不满足早期终止条件，也没有足够证据把整个需求改为一个现成 patch series 的 Backport。

|---|---|---|---|
| 普通 SVA | `drivers/iommu/iommu-sva.c:18–53,72–159,201–209` | PASID 存于 `mm->iommu_mm`，后续绑定复用并检查设备位宽；domain 列表与绑定引用 | 私有分配函数、SVA 锁和 mm 释放路径共同管理 PASID；异构先绑定时需要接入同一所有权，不能另外分配一个“恰好相同”的数值 |
| CPU 页表翻译根 | `arm-smmu-v3-sva.c:55–119` | 生成每设备的 PASID 上下文 | `virt_to_phys(mm->pgd)`、CPU MAIR 和翻译参数，不是可插拔异构页表容器 |
| 普通 S1 PASID | `arm-smmu-v3.c:3216–3243`；`iommu.c:3652–3693` | 通过明确 PASID 安装独立 domain | `smmu_domain->smmu != smmu` 时拒绝；不提供跨 SMMU 共享页表生命周期 |
| IOPF 分发 | `io-pgfault.c:124–162,220–269` | 按 group/PASID 找 attach handle，调用 `domain->iopf_handler`；已有分组、响应与释放规则 | 需自定义异构 handler 和合法范围/内存对象查找；硬件注册、排空和解绑同步不可遗漏 |

| KSVA/isolated bind | `iommu-sva.c:334–482,535–539` | 私有数据和独立绑定、内核地址空间权限管理 | isolated 接口每绑定分配独立 PASID；KSVA 使用 `init_mm` 且无默认 IOPF handler，与本需求不同 |

### 3.1 关键调用链及限制

普通 SVA：

```text
iommu_sva_bind_device(dev, process_mm)
  → iommu_alloc_mm_data()：取得/分配该 mm 的 PASID
  → 查找可用 SVA domain，或 domain_alloc_sva()
  → iommu_attach_device_pasid(domain, dev, PASID, handle)
  → 后端安装页表根及硬件翻译标识
```

异构侧可以考虑复用显式 PASID attach 和 IOPF 基础设施，但分配/释放接口的职责需扩展，避免最后解绑、mm 销毁与异构引用交错导致提前复用。

IOPF：

```text
硬件事件 → iommu_report_device_fault()
  → group + PASID → attach_handle → domain->iopf_handler
  → 默认 SVA：原进程 VMA + handle_mm_fault()
  → 可扩展异构路径：设备合法范围 + 驱动内存对象 + 自研页表
```

`io-pgfault.c:210–216` 明确要求 domain 释放前停止缺页来源并排空在途事件。这不是仅靠引用计数就能代替的硬件顺序。

同一 IOMMU group 的同一 PASID 在当前框架里只有一个绑定入口。如果两类设备落在同一 group，却要求相同 PASID 分别选不同翻译根，不能直接用现有 group/PASID 模型表达；必须核实实际拓扑与隔离能力。不同 group 的同号 PASID 本身不要求同一个 domain。

### 3.2 配置

- `CONFIG_ARM_SMMU_V3`：ARM64，选择 IOMMU_API、LPAE io-pgtable。
- `CONFIG_ARM_SMMU_V3_SVA`：选择 IOMMU_SVA、IOMMU_IOPF、MMU_NOTIFIER。
- `CONFIG_UB_UMMU` / `CONFIG_UB_UMMU_SVA`：依赖 ARM64/ARCH_HISI 及 UB 基础设施，后者选择 IOMMU_KSVA 等。
- `CONFIG_UB_UMMU_SVA_SEPARATED_PAGES`：UMMU core 内的独立表模式，不是“启用后任意 SMMU 可用”的通用选项。
- 自研格式与驱动未提供，不能现在确定最终 Kconfig 依赖；后续新增特性需独立配置控制。

separated 相关特别说明：`hisilicon/iommu.c:817–819` 依据 separated 设置、iopf_enabled 及 STALLS 等条件报告 HW_CAP_IOPF；`ummu-core/core_ioctl.c:640–649` 又根据能力选择 SHARE/SEPARATE。必须区分配置开关、硬件能力与实际模式。阶段③需追踪“独立设备 VA → 驱动内存对象 → 共享独立页表补页 → 设备恢复”整条链，而非单凭 Kconfig 帮助文本判定支持或不支持。

## 4. BTM 专项

### 4.1 当前标准 SMMUv3：有历史设计，未启用

- `arm-smmu-v3.c:4916`：初始化 `reg = CR2_PTM | CR2_RECINVSID`。
- 当前代码没有探测并置位 `ARM_SMMU_FEAT_BTM` 的普通启用路径；MMU-700 勘误处反而清除它。
- `arm-smmu-v3-sva.c:132–162`：notifier 发 ASID/范围 TLBI，并调用 `arm_smmu_atc_inv_domain()`。
- SVA ASID 由 `arm_smmu_asid_xa` 分配（`:413–418`），不是直接 pin 原进程 CPU ASID。新增设备 mm 不会自动修复广播标识与启用状态。
- 上游 HEAD `c44104f...` 的 `arm-smmu-v3.c:5128` 仍设置 CR2.PTM，普通 PASID domain 仍限制同一 SMMU。

### 4.2 下游 UMMU：已有实际 BTM 分流，但语义不是本需求的完整答案

- `hisilicon/ummu_main.c:353–356`：根据 CAP2_BTLBI 探测并置位 UMMU_FEAT_BTM。
- `hisilicon/sva.c:347–364`：普通 SVA 调用 `arm64_mm_context_get/put()`，固定 CPU ASID；`:270` 使用 CPU pgd。
- `hisilicon/iommu.c:828–833`：有 BTM 时不要求 notifier 失效路径。
- 这证明本地下游有“标识固定 + 广播优先”的参考实现，但不能把它直接用于不同 VA/不同页表格式。独立设备地址空间必须重新定义广播的标识、触发和完成。

### 4.3 后续必须回答的问题

1. 异构页表视图使用何种 ASID/VMID/翻译制度，与 CPU/SMMU 现有分配器如何避免冲突及复用竞态？统一 PASID 不替代这一步。
2. 发出何种广播、在哪个执行上下文发出、用哪个设备 VA，才能覆盖全部相关 SMMU？CPU 不访问这些地址不代表不能讨论维护，但须有明确架构/硬件依据。
3. 页表写入可见性、失效完成与物理页回收如何排序？混合不支持 BTM 的实例如何合并完成？
4. ATS/ATC、上下文配置缓存等哪些仍需显式维护？不能把 TLBI、CFGI、ATC_INV 视作同一种广播。
5. UMMU 的软件遍历并向多实例发送命令，即使被代码或提交称为“broadcast”，也不能直接等同 DVM/BTM 硬件广播。

本节没有认定需求不可实现，不触发③→①回退；BTM 已确认是兼容时优先、否则回退的目标。

### 5.2 上游最新快照与替代机制

**A. SVA + 非 SVA PASID domain** [U1][U2]

最新 SVA core 仍按 mm 管理 PASID，默认 fault 仍调用 `handle_mm_fault()`。标准 ARM SMMUv3 仍把普通 domain 绑定单个实例。可复用设备绑定框架，不能直接承载此次独立共享异构表与 BTM。

**B. IOMMUFD IOAS/HWPT/FAULT** [U4][U5]

IOAS 提供统一 IOVA map/unmap，内部对多个 HWPT 同步映射；兼容时可复用一个 HWPT。FAULT 对象提供缺页队列与响应。这是统一管理地址范围和多个翻译后端的成熟参考。

但是“同 IOAS”不保证“同一份物理页表”，跨实例限制仍由驱动决定；驱动内存的直接接入、与原进程 SVA 共享 PASID、BTM 都不是自动获得的。上游 UAPI 已有 `IOMMU_HWPT_ALLOC_PASID`，不能把概览文档中旧的“no support of PASID yet”句子当作现行能力结论，应以固定版本 UAPI/实现为准。是否采用 iommufd 取决于未来用户态控制边界，不宜为内核驱动内存需求直接引入整套用户态模型。

**C. generic_pt/iommupt** [U6][U7]

上游已引入泛化页表实现，包含 Intel/AMD 等格式与 KUnit，能作为异构格式实现、并发和测试的参考。该框架共享的是通用实现能力，不能仅从“generic/shared”推导同一物理根跨 SMMU 可用。上游 ARM SMMUv3 的 7.4 合并说明仍称失效重构在为未来 iommu-pt 接入准备 [U7]。

因此不建议在硬件格式尚未知时先决定大规模 backport generic_pt；优先比较本地 io-pgtable、共享页表对象与最新框架的必要性。

## 8. 后续建议与阶段中止点

阶段③建议分别分析四个边界：

1. 进程 PASID 与退出生命周期：与原 SVA 共用的所有权及异构先绑定支持。
2. 共享页表对象：一份格式实现/根与多个 SMMU 上下文的引用、配置及锁。
3. 驱动内存/设备 VA：合法范围登记、主动映射、并发缺页、撤销与错误回滚。
4. BTM：共享翻译标识、触发与完成、显式失效回退、ATS/ATC 分流。

继续保留新 mm 候选，正式方案对比前不固化推荐实现。自研驱动、硬件页表格式及 BTM 协议缺失不会阻止抽象层分析，但会限制最终寄存器实现和硬件验证承诺。

**待用户确认：是否接受上述调研结论，继续 Feature 的阶段③架构分析。** 本阶段不申请早期终止，不把任何局部参考认定为完整现成方案。
