## 2. 范围与结论

根据使用场景，本次评估排除内存热下线、物理热移除以及 `page_owner_sort` 用户态工具问题。保留内核 page_owner 的分配、释放、迁移、拆分、初始化、栈存储、debugfs 读取与资源开销分析。

当前最确定的缺陷是：

1. 高阶页迁移后再拆分，尾页可能错误归因到迁移目标的分配路径。
2. 迁移后的释放时间赋值错误，且释放历史字段来源不一致。

其次需要考虑并发读取的非快照语义、固定内存开销、分配路径性能变化以及栈保存失败导致的归因退化。在本次限定场景、当前配置和已检查的常规调用路径中，尚未确认 page_owner 会导致越界写、UAF 或死锁；这不等于证明所有潜在故障不存在。

本文使用以下证据等级：

- **源码确认**：赋值、状态转换或调用路径能够直接支持结论，未必做过运行复现。
- **设计限制/成本**：功能本身的语义或明确资源成本，不等同于代码缺陷。
- **条件风险**：不安全条件可以说明，但当前配置或实际调用的触发性尚未证明。
- **已撤回**：此前判断经完整调用链核对后不成立，不纳入缺陷清单。

本文不复用同目录中基于 Linux 7.3-rc7 的分析结论。当前基线没有该新版本的 page_owner 栈汇总及计数接口，不能把对应实现的问题直接套用到这里。

## 3. 功能结构与数据语义

| 路径 | 主要位置 | 行为 |
| --- | --- | --- |
| 启动与初始化 | `mm/page_owner.c:48-105` | 处理启动参数、注册特殊栈、启用静态分支并补记早期分配 |
| 分配 | `mm/page_alloc.c:1569`、`mm/page_owner.c:164-203` | 记录 order、GFP、分配栈、PID/TGID、comm、时间 |
| 释放 | `mm/page_alloc.c:1156`、`mm/page_owner.c:139-162` | 清除 allocated 标记，保留分配历史并记录最近释放信息 |
| 迁移 | `mm/migrate.c:722`、`mm/page_owner.c:235-279` | 将源页 owner 转移到迁移目标 |
| 迁移原因 | `mm/migrate.c:1380`、`mm/page_owner.c:205-216` | 更新目标头页的迁移原因 |
| 拆分 | `mm/huge_memory.c:3522`、`mm/page_owner.c:218-233` | 更新各基础页 owner 中的 order |
| 扩展存储 | `mm/page_ext.c`、`include/linux/page_ext.h` | 管理每页扩展信息及访问生命周期 |
| 栈去重 | `lib/stackdepot.c` | 保存、查找共享调用栈 |
| 当前分配导出 | `mm/page_owner.c:516-611` | 按 PFN 扫描并输出仍标记为已分配的记录 |
| 错误诊断 | `mm/page_owner.c:461-513` | 输出最近分配及释放信息 |

`PAGE_EXT_OWNER` 表示曾经建立过 owner 信息；`PAGE_EXT_OWNER_ALLOCATED` 表示当前被追踪为已分配。释放不会删除该 PFN 的全部历史信息。

page_owner 记录页面的分配来源，不记录该页后续所有使用者，也不是完整的分配、释放事件日志。debugfs 导出主动排除已释放页面；最近一次释放信息主要服务于内核 dump。

## 4. 确定缺陷

### PO-01：高阶页迁移后拆分，尾页归因错误

- 优先级：高，针对诊断正确性。
- 证据等级：源码确认，未运行复现。
- 位置：`mm/page_owner.c:164-188`、`:218-233`、`:235-279`。
- 触发条件：高阶 folio 迁移成功，随后发生拆分；直接对尾页进行诊断时也可能看到不一致。

分配高阶页时，`__set_page_owner_handle()` 更新范围内每个基础页的元数据。迁移时，`__folio_copy_owner()` 只复制头页。拆分时，`__split_page_owner()` 只修改 order，没有让尾页继承头页的原始 owner。

以 4 KiB 基础页、2 MiB THP 为例：

```text
原始 THP：512 个基础页记录原分配栈 A
迁移目标：512 个基础页最初记录迁移分配栈 B

迁移复制后：
    头页记录 A
    511 个尾页仍记录 B

拆分为 order-0 后：
    第一个基础页显示 A
    其他基础页可能显示 B
```

拆分前，读取接口通常跳过尾页；拆分后，原尾页开始作为独立记录输出，错误归因暴露出来。原始分配者的占用可能被低估，迁移分配路径的占用被高估，进而误导泄漏来源定位。

`__set_page_owner_migrate_reason()` 也只更新头页，拆分后尾页可能缺失对应迁移原因。

这不依赖内存热下线。内存规整、NUMA 页迁移等普通运行场景同样涉及迁移。它属于元数据正确性缺陷，不代表实际页面内容被破坏，也不代表发生内存泄漏。

建议修复方向：统一迁移时整个 folio 的 owner 更新，或让拆分过程可靠继承头页信息，同时处理迁移原因。需要明确拆分后保留哪些分配及释放历史，避免只修复栈而遗漏其他字段。

### PO-02：迁移后的释放时间与释放历史字段不一致

- 优先级：中。
- 证据等级：源码确认，未运行复现。
- 位置：`mm/page_owner.c:260-264`；输出位置 `mm/page_owner.c:489-506`。
- 触发条件：迁移复制 owner；随后检查释放历史字段。

当前代码：

```c
new_page_owner->free_pid = old_page_owner->free_pid;
new_page_owner->free_tgid = old_page_owner->free_tgid;
new_page_owner->ts_nsec = old_page_owner->ts_nsec;
new_page_owner->free_ts_nsec = old_page_owner->ts_nsec;
```

`free_ts_nsec` 被赋为源页的分配时间，属于明确的字段赋值错误。此外，迁移复制没有同步复制对应的 `free_handle`，使目标记录可能混合以下来源：

| 字段 | 来源 |
| --- | --- |
| `free_pid/free_tgid` | 源页历史释放身份 |
| `free_ts_nsec` | 源页分配时间 |
| `free_handle` | 目标 PFN 原有释放栈 |

该组合无法一致描述一次历史释放，可能误导坏页、重复释放或释放后访问的诊断。普通 debugfs 导出不打印这些 free 字段，因此它通常不直接影响当前已分配页数量统计。

建议修复方向：先明确迁移后的释放历史究竟属于逻辑页面还是物理 PFN，再使时间、身份和栈遵循一致语义。不能只替换错误时间字段，便认为所有释放信息已恢复一致。

## 5. 并发读取的一致性边界

- 分类：设计限制及并发元数据准确性风险。
- 位置：`mm/page_owner.c:568-605`、`:367-400`、`:423-444`。

读取过程允许与分配、释放、迁移和页面复用并发。page_ext 的 RCU 保护不是 owner 字段锁，也不能固定页面当前的分配身份。

### 5.1 单条记录不一定是原子快照

读取顺序包含 allocated 标记检查、handle 读取和整个 owner 结构复制。`page_owner_tmp = *page_owner` 不保证所有字段来自同一次更新；`READ_ONCE(handle)` 也只约束 handle 这一个字段的读取。

### 5.2 owner 与页面状态可能来自不同分配

owner 复制之后，代码分配输出缓冲区，再读取当前 page flags、pageblock 和 memcg。如果页面在间隔中被释放、重新分配，可能输出“旧 owner + 新页面状态”。

普通页面复用不会释放 `struct page` 描述符本身。在排除物理热移除的范围内，这首先是诊断数据不一致，不能据此认定为 UAF。

memcg 查询也没有把绑定固定为 owner 采样时的状态。`include/linux/memcontrol.h:599-619` 列出了非 kmem folio 绑定稳定性所需的页锁、隔离、独占引用等条件，当前输出路径没有持有这些条件。

### 5.3 全量导出不对应某一个时刻

扫描过程中页面可能变化，造成遗漏，或在迁移过渡阶段同时看到源页和目标页。结果适合发现长期占用的主要来源，不适合直接作为进程或 memcg 瞬时内存的精确账本。

如果需要增强一致性，应区分“单条记录的一致采样”和“全系统快照”两个目标；实现前者不自动实现后者。是否增加同步及其开销，需要另行设计和验证。

## 6. 内存、性能与栈保存成本

### 6.1 固定元数据开销

按当前结构定义及常见 ARM64 64 位布局估算，`struct page_owner` 为 64 字节，共享 page_ext flags 为 8 字节，合计约 72 字节/基础页。该估算来自结构布局，未通过目标构建产物的 pahole 验证。

4 KiB 基础页时约占被覆盖内存的 1.76%：

| 被覆盖内存 | owner 与共享 flags 的基础开销 |
| --- | --- |
| 64 GiB | 约 1.125 GiB |
| 256 GiB | 约 4.5 GiB |
| 1 TiB | 约 18 GiB |

以上不包含 stack depot、分配取整以及其他 page_ext 使用者。实际开销取决于 section 覆盖等布局，不能只按业务已分配页数量计算。使用 THP 不会将该开销变为每个 THP 仅一份。

开销会改变内存回收、规整和分配失败条件。page_ext 初始化分配失败还有直接 panic 路径，见 `mm/page_ext.c:483-484`。这是容量与可用性成本，不应称为 page_owner 自身泄漏。

### 6.2 分配和释放热路径成本

位置：`mm/page_owner.c:112-202`、`mm/page_alloc.c:4774-4783`。

启用后，分配和释放都需要栈回溯、stack depot 查找及元数据更新。新栈插入涉及共享锁，新栈池可能需要额外分配；高阶分配还要更新范围内每个基础页。

批量页分配路径在 page_owner 启用时主动退回逐页分配，这是明确的行为变化。高频 order-0 分配、网络页面分配以及分配延迟敏感业务应重点验证，不能仅用一次栈回溯估算总成本。

导出操作也有 PFN 扫描、缓冲区分配和符号格式化成本。本次未做性能测试，不提供未经测量的吞吐下降或延迟百分比。

### 6.3 stack depot 容量与归因退化

位置：`lib/stackdepot.c:258-317`、`mm/page_owner.c:126-135`。

当前 stack depot 不随页面释放删除历史栈。历史不同栈会占用存储，达到容量上限或内存分配失败时，新的调用栈无法保存。4 KiB 页配置下，当前代码的栈池容量上限约为 128 MiB，另有哈希表等开销。

保存失败使用 `failure_handle`，递归进入使用 `dummy_handle`。因此页面可能仍被记录，但真实来源丢失，多个来源混入同一个特殊栈。普通系统的栈集合可能趋于稳定，不能断言容量必然耗尽。

该实现没有要求 page_owner 对每个 handle 配对执行引用释放；未发现缺少 put 导致引用泄漏的证据。`current->in_page_owner` 的嵌套进入会直接返回 dummy handle，不会执行外层的清零路径，不能仅因它不是计数器便判定防递归失效。

应避免同时指定 `page_owner=on` 和 `stack_depot_disable=1`：后者使栈保存返回零，特殊栈也可能为零。owner 存储已经分配，读取路径却跳过 handle 为零的记录，导致开销与实际可观测性不匹配。

## 7. 读取接口限制及已撤回判断

### 7.1 完整记录读取限制

位置：`mm/page_owner.c:403-459`。

每次读取需要容纳一条完整记录，没有记录内部的分段读取状态。小缓冲区可能返回 `-ENOMEM`，而原因只是空间放不下记录。输出缓冲区最多为 `PAGE_SIZE`，超过限制的记录也无法正常导出。

按 PFN 定位到高阶分配的中间位置时，读取会跳过未对齐尾页；该接口不能直接实现“查询包含任意 PFN 的完整分配”。

这些是接口能力和错误表达问题，优先级低于迁移元数据缺陷。

### 7.2 撤回“普通 read 失败重试会跳过记录”

`mm/page_owner.c:600` 确实在格式化前修改 `*ppos`，但普通 `read()` 系统调用使用局部位置副本：

```c
/* fs/read_write.c:615-617 */
ret = vfs_read(f.file, buf, count, ppos);
if (ret >= 0 && ppos)
    f.file->f_pos = pos;
```

返回 `-ENOMEM` 或 `-EFAULT` 时，修改后的位置不会提交到文件的 `f_pos`。因此，不能将回调内部提前更新 `*ppos` 直接认定为普通用户态 read 失败后必然丢记录。

此前只检查读取回调，没有追完 VFS 的判断不成立。该项已撤回，不作为本文的缺陷或修复依据；这里的结论限定于已核对的普通 read 系统调用路径。

## 8. 条件风险：跨 section 的线性 page_ext 遍历

- 证据等级：跨 section 时算法不安全可由存储布局确认；当前配置可触发的实际调用尚未证明。
- 位置：`mm/page_owner.c:152-186`、`:227-230`、`include/linux/page_ext.h:90-95`、`mm/page_ext.c:268-300`。

SPARSEMEM 按 section 单独分配 page_ext 数组，而 `page_ext_next()` 只递增指针。set、reset、split 如果一次处理跨 section 的范围，就不会自动切换至下一 section 的实际数组，存在越界访问风险。

不能由此推导出“分配 1 GiB 大页必然越界”。实际调用约束为：

1. 当前 ARM64 4 KiB 配置的 section 为 128 MiB，普通 THP 不跨 section。
2. 普通 buddy 分配范围受到 section 大小相关约束。
3. `alloc_contig_range()` 只有 `__GFP_COMP` 分支才以整个范围的 order 调用 `prep_new_page()`，见 `mm/page_alloc.c:7035-7057`；非 compound 路径会分段处理。
4. `cma_alloc_compound()` 明确传入 `__GFP_COMP`，但当前配置未启用已经观察到的调用方 `CONFIG_CMA_FOLIO`；普通调用的实际 order 也需要核实。

本文不将该项列为当前环境中已确认可触发的内存破坏。后续若开放超大 compound CMA/自定义 folio，应按真实 order 和 section 边界专项检查。修复方向是按 PFN 或 section 边界取得正确的 page_ext，而非假定相邻 section 的扩展数组连续。

## 9. 使用语义与修复优先级

page_owner 记录分配者，不是唯一使用者。中断上下文可能记录被中断任务；异步分配可能显示工作线程；共享 page cache 和 slab 页不能直接归给唯一用户进程或具体对象。

调用栈深度为 16 层，早期分配补记不能恢复真实原始调用者。长时间存活的页面也可能属于合法缓存、内存池或长期对象，不能仅凭 owner 记录证明泄漏。

建议优先级：

| 顺序 | 项目 | 验收目标 |
| --- | --- | --- |
| 1 | PO-01：迁移与拆分后的 owner 一致性 | 迁移后、拆分后，各基础页仍正确指向原始分配来源，迁移原因语义一致 |
| 2 | PO-02：迁移释放历史一致性 | free 时间、身份和调用栈遵循明确且一致的保留语义 |
| 3 | 量化启用成本 | 比较可用内存、页面分配吞吐、分配延迟与业务尾延迟 |
| 4 | 明确并发读取及接口语义 | 区分单条记录一致性、全局快照需求与完整记录读取限制 |
| 条件项 | 跨 section compound 分配 | 有相关配置或调用时，验证真实范围与 page_ext 边界处理 |
