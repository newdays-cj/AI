## 1. 先建立正确直觉

### 1.1 一句话理解 HBM

**HBM 是通过多层 DRAM 堆叠、超宽数据接口和近距离先进封装，向处理器提供高吞吐、较低传输能耗的易失性内存。**

可以把计算芯片看作工厂，把内存看作仓库：

- **容量**：仓库能放多少货。
- **带宽**：每秒能运送多少货。
- **延迟**：发出一笔订单后，多久收到货。
- **访问并行度**：同时可以有多少订单在路上。

HBM 的主要优势是“并行运货的道路很多且很短”，并不意味着每一笔订单都瞬间到达。

### 1.2 HBM 主要解决什么问题？

现代 GPU/AI 加速器的算力增长很快。如果计算单元持续等待数据，再高的峰值 FLOPS 也难以兑现，这就是常说的 **Memory Wall，内存墙**。

以教学假设为例：

- 处理器可提供 `1000 TFLOP/s`。
- 内存可提供 `4 TB/s`。
- 某算子每传输 `1 Byte`，只能完成 `10 FLOP`。

那么仅从内存供给看，该算子最多达到：

```text
4 × 10^12 Byte/s × 10 FLOP/Byte = 40 TFLOP/s
```

它只能利用很小一部分峰值算力。解决方向有两个：**提高可用内存带宽，或减少同样计算所需的内存流量**。

### 1.3 必须先纠正的误区

| 常见说法 | 正确认识 |
|---|---|
| HBM 就是更快的缓存 | HBM 通常是 DRAM 主存/显存；GPU L1、L2、共享内存通常采用 SRAM |
| HBM 带宽高，所以随机单次访问一定很快 | 带宽与延迟是不同指标；随机依赖访问可能受延迟限制 |
| 堆叠层数翻倍，带宽就翻倍 | 层数主要影响容量；带宽取决于接口宽度、引脚速率和组织方式 |
| GPU 标称带宽就是程序有效带宽 | 实测还受访问模式、缓存、并行度、调度、温度和频率影响 |
| 统一内存等于 CPU/GPU 共享同一块物理 HBM | 统一地址/编程模型与物理放置、缓存一致性是不同问题 |
| 多卡总容量相加，程序就能当单卡使用 | 通常需要显式分片或运行时支持，远端访问还受互联限制 |
| HBM 能让所有 AI 工作负载等比例加速 | 只有相应访存环节受限时才有明显收益；算力、通信、调度仍可能是瓶颈 |

## 2. 放进整个存储体系看 HBM

### 2.1 典型 GPU 数据路径

```text
GPU 执行单元
    │
寄存器 / 共享内存 / L1（具体访问路径依架构和指令而异）
    │
    L2
    │
片上互联 + 内存控制器 + PHY
    │
封装内互联 / 中介层
    │
   HBM

CPU DDR ── PCIe 或一致性互联 ── GPU
其他 GPU ── GPU 互联 / PCIe ── 本地 GPU
```

要注意：GPU 的 **global memory 是编程地址空间概念**。在采用 HBM 的 GPU 上，它通常由 HBM 承载；其他 GPU 可能使用 GDDR，部分访问还可能指向系统或远端内存。

CUDA 的 **local memory 也不是“低延迟片上内存”**：它是线程私有的地址空间，寄存器溢出等数据通常经缓存访问设备内存。[R4]

### 2.2 HBM、DDR、GDDR、SRAM 的区别

| 类型 | 主要设计目标 | 典型连接方式 | 优势 | 主要约束 |
|---|---|---|---|---|
| DDR | 大容量、通用系统内存、可扩展性 | CPU 控制器经主板连接 DIMM | 容量扩展方便，生态成熟 | 插槽、通道数、走线与功耗限制带宽 |
| GDDR | 高吞吐图形/计算显存 | GPU 经 PCB 连接多颗显存 | 高单引脚速率，封装方案相对灵活 | 高速信号、板级布线和 I/O 功耗压力 |
| HBM | 高带宽密度、较低传输能耗 | 堆叠 DRAM 通过先进封装邻接计算芯片 | 超宽接口、短互联、节省板级面积 | 成本、封装、容量扩展和散热复杂 |
| SRAM | 低延迟、高片上吞吐 | 通常集成在计算芯片内 | 延迟低，不需要 DRAM 式刷新 | 面积成本高，难提供同等级容量 |

HBM 不限定只能用于 GPU，也可用于 CPU、FPGA、专用 AI 加速器和 HPC 处理器。

**比较时必须固定范围**：单颗 DDR 芯片、单条 DIMM、CPU 全部内存通道、单个 HBM 堆栈和整颗 GPU 的数字不能直接混用。

## 3. 四个指标与三条基本公式

### 3.1 容量：到底能装下什么？

粗略估算：

```text
单堆栈容量 = 每层 DRAM 的数据容量 × DRAM 层数
设备总容量 ≈ 已启用堆栈容量之和
应用可用容量 < 设备标称容量
```

差额可能来自固件/驱动预留、运行时上下文、其他进程以及具体可靠性配置。

`8H / 12H` 通常指堆叠的 DRAM die 数量，不应把基底 die 直接计入这组 DRAM 容量计算。

教学示例：每层为 `24 Gb`，8 层原始数据容量为：

```text
24 Gb × 8 ÷ 8 = 24 GB
```

该式采用芯片容量的常见标称写法。工程容量核算应换算成明确字节数，避免混用 GB 与 GiB。

### 3.2 带宽：单位时间能搬多少数据？

```text
理论带宽 Byte/s = 数据接口宽度 bit × 每引脚有效数据速率 bit/s ÷ 8
```

如果速率已经写作 `Gb/s/pin`，它已经是数据速率，**不要再因为 DDR 传输乘一次 2**。

示例：1024-bit 接口、每引脚 `6.4 Gb/s`：

```text
1024 × 6.4 × 10^9 ÷ 8
= 819.2 × 10^9 Byte/s
= 819.2 GB/s
```

若有 6 个同规格、同速率、全部启用且可并行工作的堆栈，接口理论总带宽是 `4.9152 TB/s`。这不是对某款 GPU 的实测承诺。

数据线通常在读写之间共享使用，不能把同一组引脚的完整读峰值和写峰值再相加，宣称为独立全双工带宽。

### 3.3 延迟：一次访问等多久？

端到端访问延迟由多部分组成：

```text
指令/地址处理 + 缓存与地址翻译 + 片上互联 + 排队
+ DRAM 命令等待与阵列访问 + 数据返回
```

不要把某个 DRAM 时序参数直接当作 GPU load 的完整延迟，也不要假设存在适用于所有 HBM 设备的固定纳秒值。

### 3.4 并行度：为什么要有很多未完成请求？

使用 Little's Law 的直觉估算：

```text
在途数据量 ≈ 带宽 × 平均访问延迟
```

假设需要维持 `3 TB/s`，平均端到端延迟为 `300 ns`：

```text
在途数据量 ≈ 3 × 10^12 × 300 × 10^-9 = 900,000 Byte
```

若把每个在途请求简化成 `128 Byte`，约需 7031 个请求；考虑整数覆盖约为 7032 个。这只是系统级量级估算，真实事务粒度、合并、缓存和队列分布依架构而异。

这解释了：**只有一个串行指针链，即便底层是 HBM，也很难用满总带宽。**

### 3.5 单位约定

- `b` 是 bit，`B` 是 Byte，`8 bit = 1 Byte`。
- `GB/s = 10^9 Byte/s`，`TB/s = 10^12 Byte/s`。
- `GiB = 2^30 Byte`，`TiB = 2^40 Byte`。
- `FLOP` 是运算次数，`FLOP/s` 是运算速率；一次 FMA 常按 2 FLOP 计算。

## 4. 物理结构：从 DRAM 到 2.5D 封装

### 4.1 结构示意

```text
                         单个 HBM 堆栈
                         ┌──────────┐
                         │ DRAM die │
                         ├──────────┤
                         │ DRAM die │  ← TSV 贯穿硅片形成垂直通路
                         ├──────────┤
                         │   ...    │  ← die 间通过细间距互联连接
┌──────────────────┐     ├──────────┤
│ GPU / AI 计算芯片 │     │ 基底 die │  ← 具体功能取决于代际与实现
└──────────────────┘     └──────────┘
══════════ 中介层 / 高密度封装内互联 ══════════
────────────────── 封装基板 ──────────────────
                         │
                        PCB
```

这是典型结构示意，不表示所有 HBM 产品都使用完全相同的基底和中介层方案。

### 4.2 四个关键词

**TSV（Through-Silicon Via，硅通孔）**：在硅片中建立垂直导电通路，用于层间信号或供电连接。它缩短了跨层连接距离，但也带来工艺、面积、应力和测试问题。

**Microbump（微凸点）**：相邻 die/互联结构之间的细间距连接方式。微凸点与 TSV 是不同结构，不能混为同一件事。更先进的键合方式是需要持续关注的技术方向，不能推定所有在售 HBM 都已采用。

**Interposer（中介层）**：提供高密度横向布线，把计算芯片与 HBM 连接起来。先进封装还可采用局部硅桥、不同材料的中介层等实现，需逐产品确认。

**Base die（基底芯片）**：可承载接口、测试、控制相关功能；新一代产品还可能强化逻辑功能。它不等于 GPU 内存控制器，也不意味着默认集成完整 AI 计算单元。

### 4.3 为什么同时听到“3D”和“2.5D”？

- HBM 内部多层 DRAM 垂直堆叠，属于 3D 集成。
- GPU 与多个 HBM 堆栈常并排放在中介层上，系统级通常称为 2.5D 封装。

因此“HBM 是 3D 堆叠”与“GPU 使用 2.5D 封装”并不矛盾。

### 4.4 为什么短互联有利于能效？

互联动态功耗可用下面的近似关系理解：

```text
P_dynamic ∝ α × C × V² × f
```

短互联有助于降低负载电容，宽接口允许通过大量并行线传输数据，而不完全依赖极高的单线速率。但这只是趋势解释：真实能耗还包括 DRAM 阵列、刷新、PHY、控制器和静态功耗。

**每 bit 能耗较低，不等于整套 HBM 的总功耗一定较低。** 总吞吐、容量、温度和运行状态都影响结果。

## 5. 逻辑结构：从 Channel 到 Bank

### 5.1 基本层次

```text
HBM stack
  └─ Channel
      └─ Pseudo-channel（支持该组织方式的代际）
          └─ Bank / Bank group（具体层次依规格）
              └─ Row
                  └─ Column
```

这是一张理解并行性的逻辑图，不意味着每一代都有相同数量的层级，也不代表 channel 与某一 DRAM die 固定一一对应。

| 名称 | 作用 | 对性能的影响 |
|---|---|---|
| Channel | 一组内存接口与命令/数据组织单元 | 提供较粗粒度并行性 |
| Pseudo-channel | 在规定共享关系下细分通道 | 提高调度粒度和独立访问机会 |
| Bank | 相对独立的存储阵列资源 | 不同 bank 可重叠部分操作 |
| Row buffer | 感应放大器中保持的已打开行 | 行命中能减少部分命令与等待 |
| Memory controller | 请求映射、排队、命令调度与刷新管理等 | 决定请求能否有效利用内部并行性 |
| PHY | 物理信号收发与时序相关逻辑 | 影响可实现速率、信号完整性和功耗 |

### 5.2 通道与伪通道：正确理解数字

用于建立概念的常见组织如下：

| 代际 | 单堆栈数据位宽 | 通道组织的典型描述 |
|---|---:|---|
| HBM / HBM2 系列 | 1024 bit | 8 个 128-bit channel；HBM2 的伪通道模式可细分为 16 个 64-bit pseudo-channel |
| HBM3 / HBM3E | 1024 bit | 16 个 64-bit channel，可细分为 32 个 32-bit pseudo-channel |
| HBM4 | 2048 bit | 通道数量与并行性继续扩展；精确命令共享关系以 JESD270 和产品资料为准 |

HBM3E 的 `16 channel / 32 pseudo-channel` 可由 Micron 产品资料核对。[R2] 不同材料可能把伪通道宽泛称作“独立通道”，读资料时要先核对其定义。

**伪通道不等于完全独立的物理 channel**：部分资源或命令路径存在共享，独立性边界应按对应规范判断。

### 5.3 DRAM 仍然需要开行、关行与刷新

简化的读路径：

1. 若目标 bank 没有打开目标行，需要安排行操作。
2. 若已打开另一行，可能先 PRECHARGE，再 ACTIVATE。
3. 满足相关时序后发出 READ。
4. 通过 burst 传输数据。
5. 控制器在多个请求、bank 和通道之间调度。

进阶需要认识这些参数：

- `tRCD`：从行激活到允许列访问的相关间隔。
- `tRP`：预充电相关间隔。
- `tRAS`：行保持激活的最小相关时间。
- `tRC`：同一 bank 行周期相关限制。
- `tRFC`：刷新操作相关的阻塞时间。
- `tRRD / tFAW`：限制一定范围内激活密度的时序约束。

这些是 DRAM 通用学习入口。具体定义、作用范围和取值需查对应 HBM 代际规范，不能照搬 DDR 数值。

### 5.4 为什么地址分布很重要？

地址会被控制器映射到 stack、channel、bank、row 等资源，可能使用交织和哈希。

- 分散到不同资源，可提高并行性。
- 集中到少数资源，可能形成热点，即使全局带宽仍有余量。
- 行命中与 bank 并行性之间可能存在权衡。
- 固定大步长访问有时会与地址映射产生不利关系。

GPU/驱动未必公开完整地址映射，普通 CUDA/PyTorch 分配也通常不能直接指定某个 HBM bank。FPGA/专用控制器环境可能暴露更多通道放置能力。

## 6. 代际演进：看变化，不只背型号

### 6.1 代表性带宽计算

下表用于学习接口计算。**它不是所有代际产品的最高速率表，也不是所有型号都能实现的性能表。**

| 代际/常见名称 | 单堆栈位宽 | 用于计算的每引脚数据速率 | 对应接口理论带宽 | 阅读重点 |
|---|---:|---:|---:|---|
| HBM | 1024 bit | 1.0 Gb/s | 128 GB/s | 超宽接口与堆叠路线的早期实现 |
| HBM2 | 1024 bit | 2.0 Gb/s | 256 GB/s | 更高密度、速率与伪通道组织 |
| HBM2E | 1024 bit | 3.2 Gb/s | 409.6 GB/s | HBM2 生态中的增强产品，型号速率存在差异 |
| HBM3 | 1024 bit | 6.4 Gb/s | 819.2 GB/s | 更多、更细的通道组织 |
| HBM3E | 1024 bit | 9.6 Gb/s（示例值） | 1.2288 TB/s | 更高引脚速率、容量和封装要求 |
| HBM4 | 2048 bit | 8.0 Gb/s（示例值） | 2.048 TB/s | 单堆栈位宽加倍 |
| HBM4 厂商产品示例 | 2048 bit | 大于 11.0 Gb/s | 大于 2.816 TB/s 的接口计算值 | Micron 页面标称单堆栈大于 2.8 TB/s [R3] |

HBM2E、HBM3E 中的 “E” 常用于描述增强产品或速率等级，不能仅凭名称推导出一套完全独立的协议。涉及标准兼容性时，核对实际 JEDEC 文档版本、器件手册和控制器支持矩阵。

### 6.2 产品参数如何正确引用？

已核对的例子：

- Micron HBM3E：24 GB 8H、36 GB 12H，页面标称单堆栈带宽超过 1.2 TB/s。[R2]
- Micron HBM4：页面列出 2048-bit 接口、超过 11 Gb/s 的引脚速率及超过 2.8 TB/s 的单堆栈带宽。[R3]
- NVIDIA H100 SXM：产品规格表列出 80 GB GPU 内存、3.35 TB/s GPU 内存带宽。[R5]

第一个和第二个是**单堆栈产品参数**，第三个是**整颗 GPU 参数**。不能把两种口径直接放在一起比较大小。

厂商页面可能同时保留较早的发布文字与更新规格。引用时优先标明具体型号、规格表和日期。JEDEC 标准规定能力边界，并不代表所有出货产品都采用同一速率、容量或配置。

### 6.3 为什么“堆更高”不等于“更快”？

带宽公式没有直接包含 die 层数。增加层数可以提高容量、改变内部并行性或负载，但并不会自动增加对外数据线数量。

更高层数还会增加薄片处理、对准、键合、热管理和测试难度。只有在系统确实需要更大工作集，并且控制器、封装和散热支持时，容量提升才会转化为实际价值。

## 7. 性能分析核心：Roofline 模型

### 7.1 两个上限决定可达到的性能

定义算术强度：

```text
I = FLOP 数 / 穿过所分析内存层级的字节数
```

对 HBM 层级，Roofline 的基本形式为：

```text
可达到性能 ≤ min(匹配精度和运算类型的峰值算力, HBM 带宽 × I)
```

分界点：

```text
I_ridge = 峰值算力 / HBM 带宽
```

教学假设：`1000 TFLOP/s ÷ 4 TB/s = 250 FLOP/Byte`。

- 远低于 `250 FLOP/Byte`：更可能受 HBM 带宽限制。
- 远高于它：更可能受计算限制。
- 低于两条理论上限很多：继续查并行度、指令、缓存、同步、访问效率等。

真实分析应优先使用**可持续带宽和对应精度的可实现算力**。不要把带结构化稀疏条件的 FP8 峰值用于预测稠密 FP32 算子。

### 7.2 示例一：向量加法

```text
C[i] = A[i] + B[i]，数据类型 FP32
```

每元素的理想逻辑流量：读取 A、B 各 4 Byte，写出 C 为 4 Byte，总共 `12 Byte`；完成 `1 FLOP`。

```text
I ≈ 1 / 12 FLOP/Byte
4 TB/s × 1/12 ≈ 333.3 GFLOP/s
```

这类算子通常应优先减少访存、提高连续访问效率，而不是追求更多浮点单元。

这里的 12 Byte 是有用数据流量；实际 HBM 流量还受缓存、事务粒度和实现影响，不应照搬 CPU 写分配模型。

### 7.3 示例二：矩阵乘法

对 `C = A × B`，维度分别为 `M×K`、`K×N`、`M×N`：

```text
计算量 ≈ 2MKN FLOP
理想数据流量 ≈ s × (MK + KN + MN) Byte
```

这里假设每个输入只从 HBM 读一次、输出只写一次，且元素大小统一为 `s`，不计额外读取旧 C。混合精度或 `βC` 情况要另算。

对于边长 `n` 的方阵：

```text
I_ideal ≈ 2n / (3s)
```

但“每个输入只从 HBM 读一次”是理想化流量下界，大矩阵通常无法全部留在片上。真正的 HBM 流量取决于分块、跨 block 复用、L2 和算法调度。

**Tiling 的意义**：把一块输入搬进寄存器/共享内存后，尽可能多次用于计算，提高每次 HBM 访问带来的工作量。

### 7.4 比单层 Roofline 再深入一步

一个算子可能同时面对：HBM、L2、L1/共享内存、寄存器和计算流水线的约束。

即便 HBM 流量已经很低，也可能受限于共享内存带宽、bank conflict、寄存器压力或指令发射。此时应构建分层 Roofline，而不是继续归咎于 HBM。

## 8. 为什么 HBM 用不满？

### 8.1 六类常见原因

| 原因 | 现象/证据 | 优先方向 |
|---|---|---|
| 工作量太小 | 执行时间接近启动开销 | 增大工作量、融合算子或减少启动次数 |
| 访问不合并 | 实际事务搬运很多无用字节 | 调整布局、线程与数据映射 |
| 并行请求不足 | 低带宽但存在长延迟等待 | 增加独立访问、合理增加并发 |
| 通道/bank 分布不均 | 某些模式性能异常，改变步长后变化明显 | 排查热点和映射，避免仅凭总体均值判断 |
| 资源/指令受限 | 计算、地址运算、同步或溢出占主导 | 简化索引、调分块、控制寄存器压力 |
| 系统状态限制 | 频率变化、功耗/温度限制、其他负载竞争 | 在一致状态下测量并记录条件 |

### 8.2 合并访问的本质

理想情况：同一 warp 的线程访问相邻地址，硬件用较少内存事务完成请求。

```text
较好：thread 0 → A[0]，thread 1 → A[1]，thread 2 → A[2]，...
较差：thread 0 → A[0]，thread 1 → A[大步长]，...
```

具体合并规则依架构、指令宽度和对齐方式而异，不能把“32 个线程永远只发一个事务”当作通用规则。[R4]

### 8.3 Occupancy 不是最终目标

更多驻留 warp 有时能隐藏延迟，但盲目追求最高 occupancy 可能减少每线程可用寄存器、破坏数据复用，甚至导致寄存器溢出。

优化目标是**更短的总执行时间**，不是某一个硬件指标最大化。

### 8.4 三种带宽一定要分清

1. **接口理论带宽**：由位宽和引脚速率计算。
2. **实际 DRAM/HBM 流量带宽**：由性能计数器统计穿过内存接口的字节数与时间得到，受计数口径影响。
3. **应用有效带宽**：按算法所需的有用读写字节数除以时间得到。

若缓存重用大量数据，应用有效带宽可以高于 HBM 接口带宽；这不代表 HBM 突破了物理极限。反之，不合并访问可能导致 HBM 搬运很多无用数据，实际流量高而应用有效带宽低。

## 9. HBM 与大模型：容量、权重、KV Cache

### 9.1 推理内存的组成

```text
设备内存需求 ≈ 权重 + KV Cache + 激活/临时工作区
             + 通信缓冲 + 运行时预留 + 分配器/碎片开销
```

仅估计权重：

```text
M_weights ≈ 参数量 P × 每参数存储字节数
```

以 70B 参数为例，采用十进制字节口径：

| 存储形式 | 权重主体估算 | 额外说明 |
|---|---:|---|
| FP32 | 280 GB | 不含任何 KV Cache 与临时空间 |
| FP16/BF16 | 140 GB | 常见基础估算 |
| INT8/FP8 | 70 GB | 需加 scale、元数据或非量化部分 |
| 4-bit 打包 | 35 GB | 需加分组参数、对齐与非量化部分 |

所以“70B 量化后约 35 GB”不等于“35 GB 显存就能运行所有 70B 推理配置”。

### 9.2 为什么 Decode 经常对带宽敏感？

小 batch 的自回归 decode，每一步只为每条序列生成少量新 token，但通常要使用大量模型权重。若权重不能驻留片上缓存，且复用不足，权重读取就可能主导时间。

对稠密模型、小 batch、每步近似完整读取一次权重的简化场景：

```text
t_step ≥ M_weights / BW_effective
```

教学示例：权重 `140 GB`，实际有效供给带宽 `2.5 TB/s`：

```text
t_step ≥ 140 / 2500 s = 0.056 s = 56 ms
batch = 1 时，权重供给对应的吞吐上界约为 17.9 token/s
```

这是**特定假设下的权重流量下界模型**，不包含 KV 读写、算力、启动、采样及通信开销。MoE 的激活参数、量化、缓存与分片会改变模型。

当 batch 为 `B` 且权重可以在该步充分复用时，单步产生约 `B` 个 token，总吞吐上界可粗略写成 `B/t_step`；但实际单步时间也随 batch 增长，不能据此无限线性外推。

### 9.3 Prefill 与 Decode 的瓶颈不同

| 阶段 | 工作特征 | 常见限制 |
|---|---|---|
| Prefill | 同时处理较多输入 token，矩阵运算复用更充分 | 计算、注意力 IO、长序列内存需求等 |
| Decode | 每步生成少量 token，反复使用权重并访问历史 KV | 小 batch 常对带宽敏感；长上下文的 KV 读取也重要 |

“Prefill 一定计算受限，Decode 一定带宽受限”只是过度简化。实际取决于 batch、上下文、精度、模型结构、内核实现和硬件。

### 9.4 KV Cache 容量公式

对各层配置相同、标准 K/V 缓存的 Transformer：

```text
M_KV = 2 × L × B × S × H_KV × D_head × bytes_per_element
```

- `2`：K 和 V 两份数据。
- `L`：层数。
- `B`：并发序列数。
- `S`：每条序列缓存的 token 数。
- `H_KV`：KV head 数，不一定等于 query head 数。
- `D_head`：每个 head 的维度。

教学示例：`L=80, B=1, S=8192, H_KV=8, D_head=128`，FP16：

```text
M_KV = 2 × 80 × 1 × 8192 × 8 × 128 × 2
     = 2,684,354,560 Byte
     = 2.5 GiB
```

若改成 `H_KV=64`，其余不变，则为 `20 GiB`。这体现了 GQA/MQA 减少 KV head 数的容量价值。

该公式不包括分页对齐、分配器元数据、预留空块和特殊架构额外状态。MLA、滑动窗口注意力、KV 量化等需要对应的新模型。

### 9.5 长上下文为什么会拖慢 Decode？

在标准稠密注意力中，新 query 需要与历史 key 交互，并读取 value。随着上下文增长，注意力相关的 KV 读取量通常增长。

应分别估计：

```text
每步流量 ≈ 权重实际读取量 + 历史 KV 实际读取量
         + 新 KV 写入量 + 激活/临时结果流量
```

缓存、跨 query head 复用、分页布局和内核分块决定“实际读取量”，不能简单把逻辑张量大小无条件当作 HBM 流量。

### 9.6 FlashAttention 为什么重要？

普通注意力若把完整 `S×S` 中间矩阵写回 HBM，会带来大量 IO 和容量开销。

FlashAttention 的核心是 **IO-aware tiling**：分块处理 Q/K/V，利用片上存储和在线 softmax，避免把完整注意力矩阵作为中间结果写入 HBM。[R6]

它主要减少数据移动，并没有把标准稠密注意力的计算量普遍从二次复杂度变成线性。所谓 exact attention 指算法保持标准注意力语义，不代表所有浮点结果逐 bit 一致。

### 9.7 训练需要额外考虑什么？

混合精度 Adam 的一种常见估算配置：

```text
BF16/FP16 权重：2 Byte/参数
BF16/FP16 梯度：2 Byte/参数
FP32 master weights：4 Byte/参数
FP32 一阶、二阶状态：8 Byte/参数
合计：16 Byte/参数
```

这不是所有框架的固定规则；有的使用 FP32 梯度，有的不保留独立 master copy，也有低精度优化器状态。

此外还需计算激活、临时工作区和通信缓冲。ZeRO/FSDP 通过分片减少各卡常驻状态，激活重计算通过增加计算减少保存内容；它们均有通信或计算代价。

## 10. 软件优化：围绕“少搬、搬好、搬得并行”

### 10.1 少搬：提高复用与减少中间结果

- **Tiling**：在片上重复使用输入块。
- **Kernel fusion**：将中间结果保留在寄存器/共享内存，减少写回再读出。
- **合适的低精度与量化**：减少权重、激活或 KV 字节数，同时验证精度与反量化代价。
- **避免重复布局转换**：转置、contiguous copy、数据类型转换也会消耗带宽。
- **选择合适算法**：例如 IO-aware attention，而非只优化同一算法的指令。

融合并非越多越好：它可能增加寄存器压力、共享内存占用和代码复杂度，导致并发下降甚至溢出。

### 10.2 搬好：让事务里的字节真正有用

- 尽可能连续、对齐访问。
- 按访问模式选择 AoS/SoA 等布局。
- 分析转置、gather/scatter 和稀疏访问的事务放大。
- 避免热点、过度原子竞争和不必要写回。

### 10.3 搬得并行：隐藏延迟并覆盖计算

- 提供足够多的独立工作和合理的驻留 warp。
- 利用适用架构的异步 global-to-shared copy 与流水化分块。
- 对数据集大于显存的情况，以分块和预取减少迁移停顿。
- 在硬件和依赖允许时重叠主机传输、计算与通信。

异步操作不会消除带宽消耗，也不能越过真实数据依赖。

## 11. 实验：从“知道规格”走向“能解释结果”

### 11.1 实验前记录环境

适用于 NVIDIA 环境的常用命令：

```bash
nvidia-smi
nvidia-smi -L
nvidia-smi topo -m
nvidia-smi -q -d MEMORY,CLOCK,POWER,TEMPERATURE,ECC
```

记录 GPU 型号、显存类型、驱动、CUDA/PyTorch 版本、MIG 状态、功耗/频率/温度和是否存在其他负载。不同型号与权限支持的查询项不同。

先确认设备实际使用 HBM。相同代码在 GDDR GPU 上也能运行，但结果应称作该设备的内存性能。

`nvidia-smi` 的 memory utilization 不是已用容量，也不能直接等同于 `实际 GB/s / 峰值 GB/s`。峰值比例应结合对应工具对指标的精确定义解释。

### 11.2 实验一：测设备内存顺序拷贝有效带宽

下面代码需要已配置好 CUDA 的 PyTorch 环境，保存为 `hbm_copy.py` 后运行：

```python
import statistics
import torch

if not torch.cuda.is_available():
    raise SystemExit("需要可用的 CUDA GPU 和对应 PyTorch 环境")

device = torch.device("cuda:0")
torch.cuda.set_device(device)
free_bytes, _ = torch.cuda.mem_get_info(device)

# 两个数组合计最多使用当前空闲内存约 1/4；单数组最大 1 GiB。
# 数组应显著大于设备 L2，才能主要研究外部设备内存。
array_bytes = min(1 << 30, free_bytes // 8)
n = array_bytes // 4
if n < 1:
    raise SystemExit("可用设备内存不足")

src = torch.ones(n, dtype=torch.float32, device=device)
dst = torch.empty_like(src)
array_bytes = src.numel() * src.element_size()
print("GPU:", torch.cuda.get_device_name(device))
print(f"单数组大小: {array_bytes / 2**20:.1f} MiB")

for _ in range(20):
    dst.copy_(src)
torch.cuda.synchronize(device)

repeats = 50
samples = []
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)

for _ in range(7):
    start.record()
    for _ in range(repeats):
        dst.copy_(src)
    end.record()
    end.synchronize()
    seconds = start.elapsed_time(end) / 1000.0
    # 源读一次、目标写一次；统计有用字节，不是硬件计数器字节。
    samples.append(2 * array_bytes * repeats / seconds / 1e9)

assert torch.equal(src, dst), "拷贝结果错误"
print("各轮有效带宽 GB/s:", [round(x, 1) for x in samples])
print(f"中位数有效带宽: {statistics.median(samples):.1f} GB/s")
```

理解实验边界：

1. GPU Event 测设备时间，分配与初始化位于测量区间之外。
2. 使用同设备、同类型连续张量，排除主机到设备传输。
3. PyTorch 的具体 copy 路径由版本和运行时实现决定，不预设一定由某类硬件引擎执行。
4. 重复访问有缓存效应；需要检查单数组大小是否显著大于 L2，必要时扫描更大工作集或轮换缓冲区。
5. 结果是应用有效带宽，不是 HBM 协议总线直接测量值。
6. 此处提供学习用实验代码；文中没有将其输出作为某型号 GPU 的实测数据。

### 11.3 实验二：改变访问模式

用自定义 CUDA/Triton kernel，或确认过实现路径的算子，比较：

| 变量 | 建议取值 | 要回答的问题 |
|---|---|---|
| 工作集 | 小于 L2、数倍 L2、数百 MiB 以上 | 测到的是缓存还是 HBM？ |
| 访问步长 | 1、2、4、8、32 个元素 | 有效带宽是否因事务浪费下降？ |
| 模式 | 连续、转置、随机 gather、依赖指针链 | 带宽限制与延迟限制有何不同？ |
| 并行规模 | 从少量 block 逐步增加 | 何时达到平台，何时并行度不足？ |
| 数据类型 | FP32、FP16、适用的低精度类型 | 字节数减少是否真正带来收益？ |

比较时固定有用元素数量或明确解释变化。随机索引本身也产生流量；不要把索引读取成本漏掉。步长实验还要控制实际地址跨度，避免工作集大小与步长一起变化后误判原因。

### 11.4 实验三：使用分析工具形成证据链

```bash
nsys profile -o hbm_timeline python hbm_copy.py
ncu --list-sections
ncu --section SpeedOfLight --section MemoryWorkloadAnalysis python hbm_copy.py
```

工具需单独安装并具备性能计数器访问权限；section 名称以本机 `--list-sections` 为准。对循环很多的程序，可按本机版本支持的过滤选项仅采集少数目标 kernel。

- **Nsight Systems**：先看时间线，区分 CPU 等待、kernel、数据迁移和多卡通信。
- **Nsight Compute**：再看目标 kernel 的 DRAM/L2 流量、事务效率、SM 吞吐、stall 和资源占用。
- 工具采集可能串行化执行、重放 kernel 或改变缓存状态；性能结论应与普通计时相互核对。

建议按如下顺序分析：

```text
端到端慢在哪里？
    ↓
主要时间在 GPU kernel、CPU、迁移还是通信？
    ↓
热点 kernel 的计算量与预期流量是多少？
    ↓
计数器中的实际 HBM 流量与预期一致吗？
    ↓
是带宽饱和、并行度不足、事务浪费，还是另一层资源受限？
    ↓
只改变一个关键因素，重测正确性与时间
```

### 11.5 实验四：LLM 场景扫描

固定模型、精度和软件版本，分别改变：

- batch/concurrency：观察权重复用与请求延迟的权衡。
- 输入上下文长度：观察 prefill 时间、KV 容量和 decode 时间。
- 权重量化：比较实际设备内存、吞吐、精度与反量化代价。
- KV Cache 精度或布局：比较长上下文性能与质量变化。

至少记录：TTFT（首 token 延迟）、TPOT（每输出 token 时间）、总 token/s、请求延迟分位数、峰值设备内存，以及 prefill/decode 各自的时间。

请求总延迟还包含排队和调度。不能把高并发总吞吐提升，直接解释成单请求 decode 延迟同比下降。

## 12. Linux、NUMA 与异构内存管理

### 12.1 Linux 是否把 HBM 当作普通内存？

答案取决于平台如何暴露它：

| 场景 | 软件视角 | 常用管理方式 |
|---|---|---|
| 独立 GPU 本地 HBM | GPU 设备内存 | CUDA/HIP 与设备驱动 |
| CPU 可寻址的 HBM | 可能是 NUMA 节点、特定内存层或缓存模式 | 固件配置、NUMA 策略、分配库等 |
| 支持一致性互联的 CPU/GPU | 可能提供更统一的访问语义 | 仍需分析物理位置和本地/远端代价 |

因此不能认为执行 `numactl --membind` 就能控制任意独立 GPU 的 HBM 分配。

### 12.2 CPU 可寻址 HBM 的观察入口

```bash
numactl --hardware
numastat
lsmem
```

结合固件模式、平台文档和节点属性确认哪些节点对应 HBM、DDR，以及实际容量。某些平台的缓存模式不会把 HBM 作为可显式分配的独立节点暴露。

NUMA distance 也不等于完整的带宽矩阵；需要分别测量各 CPU 节点访问各内存节点的延迟与带宽。

### 12.3 HMM 解决什么问题？

Linux HMM（Heterogeneous Memory Management）提供异构内存相关基础设施，包括地址空间映射协助、设备内存页表示与迁移辅助。[R7]

学习时关注三条线：

1. **地址空间协同**：设备如何跟踪 CPU 进程地址空间的变化。
2. **设备内存表示**：某些设备内存如何通过 `ZONE_DEVICE` 和相应页类型接入内核机制。
3. **页面迁移**：如何协助系统内存与设备内存之间的迁移。

HMM 本身不让 PCIe 拥有 HBM 的带宽，也不自动提供所有硬件都具备的一致性能力。具体驱动/运行时是否使用 HMM，以及使用哪些能力，需要按平台核对。

### 12.4 为什么 Unified Memory 可能出现性能断崖？

统一内存简化了编程，但物理数据可能仍需跨互联迁移。常见问题：

- 首次 GPU 访问触发缺页与迁移。
- CPU/GPU 交替访问导致页面来回移动。
- 工作集超过本地 HBM，出现反复换入换出。
- 按页迁移的数据量远大于实际需要的少量字节。

处理方向是观察缺页与迁移、明确热数据位置、合理使用适用平台的预取/建议接口，并比较显式分块传输方案。

**统一虚拟地址、统一内存 API、缓存一致性、同等访问性能是四件不同的事。**

### 12.5 与内核研究的衔接

推荐按下列顺序深入：

```text
NUMA 与内存策略
  → 页迁移与内存分层
  → ZONE_DEVICE / 设备内存类型
  → MMU notifier 与设备页表协同
  → HMM 和 GPU 驱动/运行时
```

本文讨论机制，不绑定某一个 Linux 版本的函数签名。研究 OLK-6.6 或其他目标内核时，应切换到该版本源码和文档核对接口，避免直接套用滚动更新的上游文档。

## 13. 多卡系统：HBM 再快也绕不开互联

### 13.1 本地带宽不等于远端带宽

访问另一块 GPU 的 HBM，需要经过 GPU 间互联或 PCIe；访问远端节点还可能经过 NIC 和网络。

```text
本地 HBM → 片上/封装内路径
远端 GPU HBM → GPU 间互联或 PCIe
远端主机/节点内存 → 主机互联、NIC、网络及相应软件路径
```

比较时固定：单向还是双向、单链路还是聚合、链路理论值还是应用有效值。厂商标称互联带宽可能采用双向聚合口径，不能直接与 HBM 带宽相除后下结论。

### 13.2 常见并行方案的 HBM 权衡

| 方案 | 对单卡容量的作用 | 需要关注的代价 |
|---|---|---|
| 数据并行 | 每卡通常保留一份模型，普通 DP 不降低模型副本大小 | 梯度同步与批量规模 |
| 张量并行 | 分片权重，部分状态/激活布局也改变 | 层内通信、同步、KV 复制或分片策略 |
| 流水线并行 | 按层分散权重与部分状态 | 气泡、阶段不均衡、跨阶段激活传输 |
| ZeRO/FSDP | 按阶段/策略分片优化器、梯度或参数 | all-gather、reduce-scatter 与临时峰值 |
| CPU/存储 offload | 降低本地 HBM 常驻需求 | 传输、预取、容量与时延权衡 |

容量不足时，模型从“无法运行”到“能够运行”可能带来巨大价值；但一旦可运行，继续加卡并不一定线性加速。

## 14. 深入硬件：封装、热、可靠性与成本

### 14.1 封装为什么是系统瓶颈？

增加 HBM 堆栈数量，不只是“多放几颗内存”：

- 需要更多计算芯片边缘 PHY 与布线资源。
- 中介层面积与制造复杂度可能增加。
- 封装基板、供电网络、机械应力与良率需要协同设计。
- 计算芯片、HBM 与封装产能均可能影响交付成本。

所以系统带宽不是只由 DRAM 工艺决定，而是 **DRAM + PHY/控制器 + 封装 + 散热 + 软件** 的共同结果。

### 14.2 高堆叠的热问题

堆叠 DRAM 与高功耗计算芯片邻接，温度会影响刷新、可靠性和可持续运行状态。不同平台也可能通过频率或功耗管理应对热约束。

研究指标应同时包括：峰值带宽、长时间可持续带宽、温度、功耗，以及性能随时间的变化。短时间跑到的峰值不能替代持续负载评估。

### 14.3 ECC 与错误处理

区分不同保护层级：

- DRAM 芯片内部的错误校正。
- 内存接口或系统级数据保护。
- 控制器/驱动报告的可纠正、不可纠正错误。
- 页面隔离、修复或退役等平台恢复机制。

不能把 on-die ECC 当成所有路径都受到端到端保护，也不能套用统一的“打开 ECC 固定损失 X% 带宽/容量”。具体开销和可观察性由产品实现决定。

### 14.4 测试与良率

一个堆栈包含多片 DRAM 和大量层间连接，因此需要关注已知良品 die、堆叠后测试、连接冗余与修复。

可用“多个环节良率相乘”理解整体良率压力，但真实生产包含筛选、冗余修复、返工和工艺相关性，不能简单用某个单 die 良率的幂次预测商业出货成本。

### 14.5 HBM4 之后应关注什么？

1. 更宽接口与更高每引脚速率如何平衡。
2. 更高堆叠、更高 die 密度与热约束如何协同。
3. 逻辑基底、定制接口与计算芯片的协同设计。
4. 更细间距互联、键合和封装路线。
5. 总带宽增长能否匹配算力增长。
6. 软件能否减少 IO，而不是只消耗更多带宽。

PIM（Processing-in-Memory，存内处理）是相关研究方向，但 HBM 并不天然等于 PIM；HBM4 也不意味着所有产品都把通用计算搬进 DRAM。

## 15. 学习路线与能力验收

### 15.1 六周路线

| 周次 | 重点 | 必须产出 |
|---|---|---|
| 第 1 周 | 存储层次、单位、容量/带宽/延迟 | 手算 5 组带宽，画出 CPU/GPU/HBM 数据路径 |
| 第 2 周 | TSV、封装、channel/bank、DRAM 时序 | 对照一款器件资料标注逻辑与物理结构 |
| 第 3 周 | Roofline、并行度、合并访问、缓存 | 为向量加法和 GEMM 建立流量模型 |
| 第 4 周 | 带宽基准与 profiler | 提交工作集/步长/并行度扫描图和解释 |
| 第 5 周 | LLM 权重、KV、prefill/decode、多卡 | 完成一个模型的容量预算与性能假设 |
| 第 6 周 | Linux/HMM 或硬件封装专题 | 写一份可复现的瓶颈分析报告 |

### 15.2 两条精通方向

**系统与软件方向**：CUDA/HIP/Triton → 算子融合与 IO-aware 算法 → profiler → LLM 调度与多卡通信 → NUMA/HMM/页面迁移。

**硬件与体系结构方向**：DRAM 命令与时序 → 控制器调度与地址映射 → PHY/SI/PI → TSV/封装/热 → 可靠性与成本建模。

精通 HBM 不要求一个人同时成为所有方向的专家，但应能解释另一侧的关键约束。

### 15.3 自测题与答案要点

1. **1024 bit、8 Gb/s/pin 的理论带宽是多少？** 1024 GB/s，即 1.024 TB/s；不再额外乘 2。
2. **容量从 24 GB 增至 36 GB，带宽一定提高 50% 吗？** 不一定，需看接口与速率。
3. **为什么指针追逐难以用满 HBM？** 地址依赖使独立在途请求不足。
4. **有效带宽超过标称 HBM 带宽意味着什么？** 先查缓存复用、流量口径、计时与单位。
5. **为什么低 occupancy 的 kernel 可能更快？** 更好的寄存器/共享内存复用可能减少访存与指令。
6. **FlashAttention 是否把稠密注意力计算量变成线性？** 没有；主要通过分块减少 HBM IO 和中间存储。
7. **为什么长上下文可能让 decode 变慢？** KV 读取、容量及相应注意力工作增长。
8. **numactl 是否能控制任意 GPU HBM？** 不能；取决于内存是否以 CPU NUMA 节点等形式暴露。
9. **多卡总带宽能否简单相加预测性能？** 只有理想均衡、本地并行且通信不成为瓶颈等条件下才有意义。
10. **如何证明一个算子受 HBM 带宽限制？** 流量模型、计数器、可持续带宽对照与受控实验共同支持，不能只看 GPU utilization。

### 15.4 一份合格的分析报告应该包含什么？

```text
问题：哪个业务指标不满足要求？
环境：硬件、软件、数据规模和运行条件。
模型：计算量、逻辑流量、HBM 流量假设及容量预算。
证据：时间线、热点、计数器、基准结果。
判断：瓶颈所在层级及排除其他解释的依据。
改动：只改变哪些关键因素，为什么预计有效？
结果：正确性、端到端收益、吞吐/延迟与资源变化。
限制：适用的模型、规模、硬件与反例。
```

## 最后一页：把 HBM 知识压缩成一个分析框架

每遇到一个 HBM 相关问题，按顺序问：

1. **装得下吗？** 权重、KV、激活和临时空间分别是多少？
2. **数据在哪里？** 本地 HBM、缓存、CPU DDR 还是远端设备？
3. **到底搬了多少？** 区分逻辑字节、缓存流量和 HBM 实际流量。
4. **搬运是否高效？** 合并访问、事务浪费、通道分布与并行度如何？
5. **现在卡在哪里？** 容量、带宽、延迟、算力、通信还是调度？
6. **如何验证？** 用可复现计时、计数器和受控实验形成证据链。

**HBM 的价值不只是“每秒能搬多少 TB”，更在于让系统以合理的容量、能耗与成本，把真正需要的数据及时送到计算单元。**
