# 方案对比：正常线程逻辑退出，延迟销毁 task

## 1. 输入和确认边界

用户确认 ARM64、多线程、一次性检查点、检查点后支持线程创建和销毁、允许协作建立安全点；随后提出检查点有效时可暂不真正销毁 task 并要求继续。

本阶段接受“用户态逻辑退出，内核保留任务”的方向，比较两种保留范围策略。两者都必须让 pthread_join 返回、允许线程库回收及复用 TLS/栈，不能只是让退出调用永远等待。

本文是待用户选择的候选方案对比。源码论证说明没有发现直接矛盾；不等于已经实现、编译或证明竞态安全。共享的停驻、地址空间切换等必须在⑤详细设计和⑥测试设计中闭环。

## 2. 共同机制

### 2.1 三种线程身份

```text
ORIGINAL：检查点中存在的任务
NEW：检查点建立后新增的任务
HELD：已经向线程库发布退出，但尚未执行完整 do_exit 的任务
```

ORIGINAL/NEW 是检查点成员身份，HELD 是运行状态，两者正交，不能用数字 TID 范围判断。

线程组事务的候选状态为：

```text
IDLE → COLLECTING → ARMED → RESTORING → CONSUMED
                       └→ DISARMING → IDLE
任意适用阶段 → TERMINATING
```

名称只是方案说明，不是最终 ABI 或代码定义。

### 2.2 建立检查点

1. 全部当前线程协作到达内核安全点，并禁止 clone/exit 改变本次采集成员集合。
2. 在每个线程自身上下文保存用户寄存器、TLS、FP/SIMD、信号及内核用户地址登记等必要状态。
3. 在全组停驻后建立独立 COW mm 快照，不能仅持有当前 mm 引用。
4. 设置 ORIGINAL 成员身份并发布 ARMED，随后允许创建和退出线程。

安全点应在用户态线程库/业务锁之外，不支持把任意内核等待队列或 PI 锁状态作为可回放快照。确切支持/拒绝集合必须在⑤确定，不能到实现时才假设所有 libc 调用都无状态。

### 2.3 逻辑退出入口

优先在 `kernel/exit.c:994` 的原始 exit 系统调用进入 do_exit **之前**增加显式分流，而不是无差别拦截所有 do_exit 调用。

依据：普通 pthread 工作线程与初始线程的收尾最终都能到达 raw exit；但 do_exit 还被不可恢复的致命错误等路径调用，不应把这些路径都变成可复活线程。exit_group、SIGKILL、已经建立的 SIGNAL_GROUP_EXIT 必须绕过保留，进入真正退出。

进入保留态的约束顺序：

1. 与 checkpoint 恢复/释放、clone/exit 成员变化序列化，发布“逻辑退出处理中”的中间态。
2. 在当前旧 mm 中完成所支持的 robust futex 退出清理；禁止未完成的用户内存访问和异步工作越过退出通知。
3. 撤销可能在停驻期间继续引用已回收用户地址的 rseq 等登记，保存回滚所需检查点记录。
4. 使用实际 clear_child_tid 注册地址发布内核退出通知并唤醒 futex；通知地址须从任务的有效登记中获取并撤销此运行世代的重复清理责任，避免最终清理再次写入已复用地址。
5. 进入 HELD；只等待恢复、检查点释放或真正终止，不返回已退出的用户栈，不运行用户信号 handler。

上面是必要的顺序约束，不能直接把 exit_mm_release 当作无副作用的“join 通知函数”：它包含 futex、架构及 mm_release 行为，需在⑤拆分并核对。

“清理先于通知”仅约束该路径由内核发布的通知，不能保证早于所有 libc 用户态通知。目标 glibc 的初始线程在 `libc_start_call_main.h:70-80` 已先写 joinstate 并唤醒等待者，再进入 raw exit。`sysdeps/nptl/dl-tls_init_tp.c:76-79` 同时确认初始线程 clear_child_tid 指向 joinstate、stack_mode 为 USER，且登记了 robust list 和 rseq。⑤必须单独证明初始线程 TLS/栈及登记在提前通知后的安全生命周期；不能把工作线程依赖内核最后清零的证明直接套在 leader 上。若需要 libc 配套变更，必须明确提出并经用户选择，不能隐藏在内核 hook 后。

`futex_exit_release()` 结束时状态为 DEAD，恢复时需要专门协调其状态回到可用；不能重初始化可能仍被其他路径引用的锁，或无锁清理 PI 状态后直接写 OK。首版的 PI futex 支持边界应明确，不能把任意 PI 所有权恢复等同于用户锁字回滚。

### 2.4 为什么可以保持 TID

HELD 不走 release_task/detach_pid，仍有原任务关联 PID，号码仍占用在各 namespace 的 IDR 中。这是保留任务关联，而非仅保留对象引用。因此无需在恢复时用 clone3 set_tid 抢回旧号码，也不会把历史线程身份指向已获得同号码的其他任务。

同时不执行正常 do_exit 的 quick_threads/live/PF_EXITING 更新，不在回滚时撤销这些不可逆动作。原生任务计数仍表示保留的内核任务，另外记录业务活动成员数；真正退出时让原生流程减计数一次。

### 2.5 回滚

```text
任意活动线程的默认 SIGABRT
  → 在 core/exit 前原子竞争恢复事务
  → 选择 ORIGINAL 成员承担协调（可以是已保留的 leader）
  → 停驻当前全部任务，序列化成员变化
  → NEW 任务在旧 mm 中完成退出和资源清理
  → ORIGINAL 任务分别切换到检查点 mm
  → 恢复用户上下文及内核登记
  → 全组提交后释放用户态执行
```

若触发者为 NEW，它负责发起事务但不必一直当协调者；必须转交给 ORIGINAL，再退出自身。不能依赖它在恢复之后仍然存在。

状态阶段必须区分：只有正常 ARMED 运行期间的最后逻辑活动线程退出，才按正常归零规则进入整组终止。**RESTORING 内部清理 NEW 不触发该归零规则**；即使所有 ORIGINAL 原先都处于 HELD，已完成接管的 ORIGINAL 仍负责恢复事务。交接必须有确认，失败则整组失败终止；外部 SIGKILL 或已开始的组退出依旧优先。

leader 如果通过 pthread_exit 逻辑退出，仍是原任务和原 TGID 的持有者，因此可直接从其保留态恢复，省去已完整退出 leader 的身份交换重建问题。main 返回/exit()/exit_group 是整组终止，不当作 leader 逻辑退出。

### 2.6 返回用户态

保留线程的内核等待点应位于可正常收尾的系统调用路径。恢复 user pt_regs 后，从当前内核栈正常返回，不恢复旧的内核调用栈。

ARM64 `kernel/syscall.c:57` 会把系统调用 C 返回值写入 x0，因此恢复路径必须保证返回值与恢复的 checkpoint 结果相同，不能恢复寄存器后又被当前 exit 调用返回值覆盖。

`arch/arm64/kernel/signal.c:978-1047` 在 get_signal 前保存旧系统调用重启信息，末尾还可能恢复 saved_sigmask。SIGABRT 恢复不仅改 pt_regs，还需要显式恢复结果分支，跳过旧调用的重启和旧 mask 恢复。restore_sigframe 的 forget_syscall 与 restart_block 处理可参考，但不是完整的组恢复实现。

## 3. 方案 A：仅 ORIGINAL 线程延迟销毁（推荐）

### 规则

- ORIGINAL 正常线程退出：发布退出通知后进入 HELD。
- NEW 正常线程退出：执行普通退出，不保留其 task。
- NEW 尚存活时发生回滚：以内部每线程退出协议结束，等待其旧 mm 用户地址清理完成后，才能提交快照。
- ORIGINAL 无论仍在运行还是 HELD，都已有原内核任务，不需要重建。

### 源码契约论证

- ORIGINAL 的 exit 分流在 do_exit 前，不触发 PF_EXITING/live/quick_threads 变化，保留 PID 和内核栈。
- NEW 的正常 do_exit 仍有 ORIGINAL 任务保留在线程组中，不会因为单个 NEW 退出误判整个物理线程组已经消失。
- leader 必然是初始快照成员，单独 pthread_exit 可以走保留路径；不需要让 NEW 接替 TGID。
- 每个 ORIGINAL 至多被保留一次，保留任务数量由检查点原线程数界定，而不是业务累计创建线程数。

### 优点

保留资源可控，NEW 的正常退出路径改动较少，动态创建/销毁大量临时线程不会无限积累 task。无需新增 PID 分配器号码预留机制。

### 代价

退出路径需要区分 ORIGINAL 与 NEW；活动计数、成员发布、恢复时 NEW 退场都必须统一协调。正常退出和保留退出两条路径须覆盖交叉竞态。

## 4. 方案 B：ARMED 期间所有正常退出线程均延迟销毁

### 规则

- ORIGINAL 和 NEW 的正常线程退出都发布退出通知并进入 HELD。
- 回滚时恢复 ORIGINAL，结束所有 NEW（包括已 HELD 的 NEW）。
- 消费/释放检查点后，不再截留退出，所有不需要的保留任务走原生最终清理。

### 源码契约论证

所有保留任务都在 do_exit 前分流，使用与 A 相同的通知、登记撤销和最终退出协议；无需对已死亡 task 执行重建。NEW 没有检查点现场，不能恢复，只能最终释放。内核任务的原生计数直到真实退出才改变。

### 优点

ARMED 期间的普通线程退出可以使用统一的保留动作，便于追踪、观察各次逻辑退出；不会在运行阶段释放任何加入过检查点管理组的 task。

### 代价

每次创建/退出临时线程都会积累 task、内核栈、PID 和其他保留资源。必须设置最大保留任务数，在 clone 发布前按限额拒绝新建，且消费/丢弃时清理大量 NEW。它只简化退出分类，不消除状态机、信号或恢复复杂度。

## 5. 两种方案的共享必要补充

### 5.1 信号、组停止和最终退出

- 不用 PF_EXITING 表达 HELD；增加专用检查点成员状态，并适配 wants_signal/retarget_shared_pending，避免把进程定向的普通信号分配给 HELD。
- 指向逻辑退出 TID 的普通线程定向信号应有明确结果；建议 ESRCH，不能因 PID 仍关联任务就让已 join 的线程重新执行用户 handler。此筛选**不适用于 SIGKILL、SIGSTOP、SIGCONT**：即使通过 tgkill 等接口定向发送到 HELD 的 TID，也必须保留它们的线程组终止或组控制效果，不能只有 kill(tgid, ...) 有效。
- SIGSTOP/SIGCONT 不能被忽略：组停止协议应把 HELD 视为已静止、无需新参与者，不让 group_stop_count 等待保留任务；从 CONT 返回也不能唤醒其用户现场。
- 当前信号代码的 `task_set_jobctl_pending()`、`do_signal_stop()`、retarget 逻辑需要一起检查；任务在已有组停止过程中转为 HELD 的情况也必须完成相应计数协调。
- 普通 exit_group、其他默认致命信号、SIGKILL、最后一个逻辑活动线程退出：解除保留，唤醒全部 HELD 完成真正退出。默认 SIGABRT 有有效快照时才竞争恢复；与组终止竞争时终止优先。
- libc 的 nthreads 计数会随用户态线程退出变化，内核原生 live 仍包含 HELD，不能互相替代。另设组级逻辑活动计数并在 clone 发布、逻辑退出/真实退出之间保证只登记一次。

### 5.2 一次性与释放

- 正常恢复提交后检查点被消费，原有 HELD 恢复为活动线程；释放快照记录时不能提前释放仍作为活动地址空间使用的 mm。
- 主动放弃检查点时，HELD 使用已经保存的退出码继续真正退出；不得重复触碰旧 clear_child_tid/rseq/robust 地址。
- 无有效检查点时所有任务走原生行为，第二次 abort 不回滚。
- 正常整组退出不恢复所有旧业务线程，直接放弃检查点、完成最终清理。

### 5.3 明确可观察差异

保留的是实际内核任务而非隐藏镜像，`/proc/<tgid>/task`、原生线程计数、资源限额及统计可能继续包含逻辑退出线程。不能声称与完全销毁线程在所有内核接口上等价。

本 demo 承诺 pthread 退出/join/detach、动态业务线程生命周期及回滚身份一致性；不承诺伪装所有 procfs/调试/统计接口。该可观察边界须随用户选定方案明确接受。

### 5.4 仍需详细设计证明的契约

1. mm 切换：membarrier、mm CID、LRU、mm_users/active_mm 引用及 ARM64 TLB/ASID 的每线程切换顺序。
2. 所有支持内核等待必须已退场，不能只停止 CPU 或发 IPI 后就换 mm；不能停驻的任务失败终止。
3. rseq、clear_child_tid、robust list、pending task_work 的注销/清理先于通知，恢复登记先于重新进入用户态。
4. PI futex、异步 I/O、共享可写映射、ptrace、exec/unshare、cgroup freezer/迁移及 ARM64 扩展状态等不支持操作的准确识别与拒绝/失效策略，不能只在文档里口头排除而让内核继续错误恢复。
5. OLD/NEW/HELD 的计数、状态发布、信号及 clone/exit 的锁序，不能持自旋锁等待线程或分配可睡眠资源。
6. 恢复过程中失败的全组终止闭环，以及快照、保留资源在所有路径释放一次。

上述是实现前的门槛；本阶段没有把未定义 helper 名称当作现成内核 API。

## 6. 对比与推荐

| 维度 | A：只保留 ORIGINAL | B：保留所有正常退出线程 |
|---|---|---|
| 支持动态创建、退出和 join | 是，按专用逻辑退出契约实现 | 是，按相同契约实现 |
| 原检查点 TID | 原任务关联保持 | 原任务关联保持 |
| leader 逻辑退出恢复 | 保留原 leader | 保留原 leader |
| NEW 正常退出 | 原生最终释放 | 延迟最终释放 |
| 延迟保留任务数 | 至多原检查点线程数 | 随累计线程创建增长，需额外上限 |
| 恢复时 NEW 清理量 | 当前仍存活 NEW | 所有累计未释放 NEW |
| 运行阶段退出分类 | 分 ORIGINAL/NEW | 统一保留，但恢复仍需分类 |
| PID 分配器改造 | 不需要 | 不需要 |
| 共同难点 | mm/上下文、组协议、信号、退出通知 | 相同，未因全量保留而消失 |

推荐 **A**：任务保留已经解决原线程身份问题，没有必要为快照中不存在的历史临时线程长期保留内核资源。B 可作为小规模实验的备选，但不是通用性更强或已被证明代码更少。

“完整销毁再用原 TID 重建”保留为远期方向，不计作本次已经论证可复用现有 API 的第三种可行方案。

## 7. 验收与后续

沿用 AC-01～16，并增加：

- join/detach 在回滚前完成，栈/TLS 被新线程复用后仍能恢复。
- 原线程逻辑退出后 TID 未被新任务复用，回滚恢复同一个 task/TID。
- /proc 允许显示 HELD；最终退出后全部保留任务和检查点资源释放。
- leader pthread_exit 后由工作线程、新建线程分别触发 abort。
- SIGSTOP/CONT、SIGKILL、exit_group、最后逻辑线程退出不因 HELD 挂住。
- 循环创建大量 NEW 验证 A 不积累已经退出的 NEW task；B 则验证上限拒绝与批量清理。
- 恢复后的第二次 SIGABRT 正常终止，退出通知不重复写入已回收地址。

Momus 审核为条件通过，三个修订条件已补入。用户已选择 A，进入⑤详细设计，锁定接口、文件改动、锁序、架构状态及失败处理，再进入测试设计和实现。B 保留为历史备选，不再作为当前实现范围。
