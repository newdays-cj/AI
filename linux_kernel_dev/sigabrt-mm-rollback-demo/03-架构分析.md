# ARM64 SIGABRT 线程组回滚：架构分析基线

## 1. 状态与依据

代码基线与需求见 `02-现有方案与上游调研.md`。本文件是与阶段②并行开展的初步架构分析，供后续方案对比使用，不是已经批准的详细设计。

开发时曾使用gen_kernel_kb生成kernel/基线overview。该工具索引在目录整理时作为可再生成
且已过时的中间文件删除；以下统计是当时基线记录，源码结论以直接核对和当前提交为准。

该工具扫描 549 个源码/头文件；自动统计中的 Kconfig 数量为零并不表示功能没有 Kconfig 依赖，本分析另外读取 init/Kconfig 和实际源码。工具输出为索引基线，以下判断以直接核对的代码为准。

## 2. 现有调用链

### 2.1 创建线程

```text
clone/clone3
  → kernel_clone(args)                   kernel/fork.c:3022
    → copy_process(NULL, ..., args)      kernel/fork.c:2371
      → copy_files/fs/sighand/signal
      → copy_mm                         kernel/fork.c:1832
      → copy_thread                     arch/arm64/kernel/process.c:384
      → alloc_pid(..., set_tid, ...)     kernel/pid.c:178
      → tasklist_lock + sighand.siglock
      → 发布线程、关联 PID 与线程组
    → wake_up_new_task                   kernel/fork.c:3094
```

`copy_process()` 返回的新任务尚未被 kernel_clone 唤醒，但已经可见于任务/PID 关系中，不能将其视为完全私有、无外部观察者的对象。恢复初始化必须保持门控，并处理任务发布后失败。

该 API 按 current 的状态复制，CLONE_THREAD 继承 current 所在线程组，CLONE_VM 共享 current->mm。恢复线程不能简单复制触发 abort 的线程的 TLS、寄存器和注册地址；须使用检查点中对应原线程的记录。

### 2.2 退出线程

```text
线程 exit
  → do_exit(code)                        kernel/exit.c:815
    → synchronize_group_exit
    → exit_signals / signal.live--
    → exit_mm
      → exit_mm_release
        → futex_exit_release
        → mm_release / clear_child_tid
    → exit_files/fs/namespaces/thread
    → exit_notify → release_task
    → do_task_dead
```

生命周期包含多项不可直接逆转的副作用。若允许完整退出，则恢复需要新建线程内核执行框架，而不是恢复退出时内核栈。用户后续允许保留任务，因此可以在 exit 系统调用进入 do_exit 前分流，从而不执行这些不可逆步骤；这仍需专用的逻辑退出和恢复协议。

leader 退出与最后一个线程退出不同：`exit_notify()` 为 leader 保留必要的组关联，最后线程退出还会触发组死亡及父进程通知。不能把前者等同于一个普通 detached 工作线程的重建；后续方案必须独立处理。

### 2.3 SIGABRT 默认终止

```text
get_signal                               kernel/signal.c:2684
  → 在 sighand.siglock 下取出信号
  → 处理 SIG_IGN / 自定义 handler
  → 默认动作
  → fatal                                :2880
    → 释放 siglock
    → PF_SIGNALED                        :2888
    → do_coredump                        :2902
    → do_group_exit                      :2916
```

候选接入点必须在不可逆 core/exit 前，且区分正常默认 SIGABRT 与已有 SIGNAL_GROUP_EXIT/SIGKILL。不能拿着 sighand.siglock 进行 mm 复制、等待线程或分配可能休眠的资源。

### 2.4 exec 换 mm

`fs/exec.c:980` 的 `exec_mmap()` 维护 exec_update_lock、mmap 锁、task_lock、中断状态、active_mm/mm、membarrier、mm CID、LRU 和旧 mm 引用。

但调用方先 `de_thread()`（`:1045`），用 zap_other_threads 终止其他线程。该前提和本需求不相同；不直接导出 exec_mmap 作为通用全线程切换 API。

## 3. 状态归属与快照内容

| 状态 | 现有归属/接口 | 需求差距 |
|---|---|---|
| VMA、页表、历史页 | mm_struct；dup_mm/dup_mmap | 快照独立性、fork 特殊映射语义、生命周期和资源记账 |
| 线程组身份和任务集合 | task_struct/signal_struct/PID namespace | 动态新增/退出、TID 预留/重建及 leader 状态 |
| 用户寄存器 | task_pt_regs | 保存检查点返回语义；恢复时取消旧 syscall restart |
| TLS | task_user_tls、TPIDR_EL0；tls_preserve_current_state | 当前 CPU 的 TLS 值可能尚未同步至内存，须在所属线程上下文处理 |
| FP/SIMD | thread.uw.fpsimd_state；fpsimd_preserve_current_state | 需要保存实时状态并失效 CPU 缓存，不仅 memcpy 字段 |
| 扩展架构状态 | SVE/SME/TPIDR2/FPMR/PAC/MTE 等 | 本仓库有后续 backport，支持集合需逐项核定 |
| 信号 | 每线程 blocked/pending、组 sighand/shared_pending | 定义触发消费、恢复屏蔽及处置、并发信号和强制终止优先级 |
| 用户地址注册 | clear_child_tid、robust_list、rseq 等 | 指针有效性随 mm 回滚恢复，内核登记必须同步重建 |
| 同步等待 | futex 等等待队列及 PI 状态 | 旧等待必须安全退场，不能仅回滚用户锁字 |
| 文件/socket 等外部对象 | files_struct/open file description 等 | 当前范围不回滚外部操作；其一致性限制必须在接口文档说明 |

## 4. 内存快照语义

`dup_mmap()` 对旧 mm 取 mmap 写锁，对新 mm 使用嵌套写锁，复制 Maple Tree/VMA 并建立页表关系。它会跳过 VM_DONTCOPY，对 VM_WIPEONFORK 作特殊处理，清除 VM_LOCKED_MASK。

可复用 fork/COW 原理，但必须先定义支持的映射集合。只对 mmget 或 mmgrab 计数不能保留历史数据。多线程在创建过程中仍写入内存会破坏跨线程一致性，因此应在全部线程停驻后建立快照并完成执行状态采集。

pthread 线程退出后可以 munmap 栈或复用 TLS/线程控制块；独立 mm 快照需保留原映射和私有页，恢复时才能重建旧用户现场。文件映射和共享页不自动具备外部内容快照语义。

## 5. 必须定义的同步与生命周期

以下是设计必须满足的约束，不是已经选定的锁实现：

1. 线程组中只能有一个创建/恢复事务；并发 SIGABRT 不能重复消费快照。
2. 建立检查点要与 clone/exit 的成员发布/移除序列化，单纯遍历一次线程链表不够。
3. 回滚期间必须让旧内核操作停止访问旧用户状态，且不能把旧 syscall 延续写入新 mm。
4. 先前退出线程的重建资源要有失败回收；新增线程清理必须和旧 mm 释放正确排序。
5. 所有恢复线程就绪前不允许任意一个线程回到用户态，形成组级提交屏障。
6. PID 预留若采用，应在所有可见 namespace 层级正确记账和释放，不影响 namespace 最后任务退出的唤醒语义。
7. SIGKILL、组退出、OOM、分配失败不能留下半切换线程组或永久不能释放的检查点。
8. 不直接修改远程正在运行线程的 mm 或 FP/TLS 状态；须明确其已停驻且不会被其他路径再次执行。

已有锁域：tasklist_lock 管理任务/线程关系；sighand.siglock 管理信号；pidmap_lock 管理号码 IDR；mmap_lock 管理地址空间；task_lock 与架构本地切换管理 current 的 mm/active_mm 等。新增协议需要锁序分析，不能在自旋锁或 RCU 读临界区等待全组。

## 6. ARM64 恢复参考

- `copy_thread():384-480` 设置 ret_from_fork 和新内核栈框架，同时处理 TLS、架构扩展状态，是重建线程入口的参考。
- `tls_preserve_current_state():483` 直接读 TPIDR_EL0；恢复不能只改 task 字段后假设当前 CPU 寄存器自动更新。
- `fpsimd_preserve_current_state():1698` 保存当前实时 FP 状态，`fpsimd_flush_task_state():1811` 使 CPU 中旧副本失效，`fpsimd_restore_current_state():1764` 在返回用户态前按标志加载。
- `signal_common.h:172-224` 的 restore_sigframe 展示寄存器、屏蔽字、用户寄存器校验及多种扩展状态恢复；`:345-374` 还设置 do_no_restart_syscall。
- 本需求没有理由恢复过去的内核调用栈；存活线程从当前受控内核路径收尾，重建线程使用新内核栈，最终都返回检查点用户现场。

## 7. 缺口策略建议

| 缺口 | 初步方向 | 需要在方案阶段证明 |
|---|---|---|
| 历史 mm | 扩展 fork 内部复制能力，以受限 VMA 集合作快照 | COW/页表/特殊映射和完整释放 |
| 线程消亡后的数字身份 | 新增显式号码预留与受控重建，或其他可保持 pthread 身份一致的机制 | 号码不被其他任务复用、namespace 及权限一致性 |
| 重建退出线程 | 复用受控任务创建路径并恢复每线程记录 | 不继承错误现场、正确恢复注册地址、资源限额和失败退出 |
| 移除新增线程 | 每线程内核退出协议，清理隔离于恢复 mm | 不触发无意的整组 SIGKILL、不污染历史内存 |
| 组级停驻与提交 | 专门的状态机和安全停驻/恢复入口 | clone/exit/get_signal/返回用户态的竞态闭环 |
| ABI | 独立 Kconfig 下显式检查点接口及结果返回约定 | 可测、可拒绝、不改变未启用任务行为 |

用户后续允许保留 task。仅停驻但让 join 一直等待仍不满足语义；完成线程库退出通知并保持内核任务的专用保留态，可作为候选。恢复同名新进程仍不满足同进程要求。

## 8. 影响与后续

预期涉及 kernel/fork.c、exit.c、pid.c、signal.c、任务/信号结构定义和 ARM64 上下文代码；mm 切换还需核对调度器 mm CID、LRU、membarrier 等。当前仓库有 AGENTS.md 和 Documentation/iommu/ 未跟踪工作，应保留。

保留态方向可避免修改 PID 号码分配机制，但必须修改正常线程退出分流及信号/组停止逻辑。保留线程不设置 PF_EXITING，不调用 exit_signals，不减少原生 live/quick_threads/nr_threads，也不解除 PID 关联；另外维护业务活动成员数量以识别“最后一个逻辑线程退出”。真正退出时才由原退出流程统一完成原生记账一次。该方向的契约与尚待证明部分见④。

没有发现需求逻辑上已被证明不可能，因此不触发“需求不可实现”的回退；也尚无完整原型证明可行。阶段④应至少比较两种真正满足动态线程语义的候选实现，明确 leader、TID 及线程库一致性策略后才能进入详细设计。

当前未修改内核源码，未开展构建或 QEMU 验证。本地 `~/tools/qemu_arm64_defconfig`、buildroot/output/images/rootfs.ext4 等存在；工具链实际运行及镜像库版本匹配留待构建准备实查。阶段②已补充 glibc 2.43 本地源码初查，注意 joinstate 与 tid 在该版本中是两个不同字段。

阶段④补充核查了 `pthread_detach.c`、`nptl_free_tcb.c`、`libc_start_call_main.h` 和 `sysdeps/nptl/dl-tls_init_tp.c`。初始线程在用户态提前发布 joinstate，且以 USER 模式栈登记 clear_child_tid/robust/rseq；该路径与普通工作线程依赖内核通知不同，是⑤必须独立证明的边界。
