## 2. 结论

本次在已检查的当前内核路径、主线 PID 实现和 CRIU 资料中，**未找到可直接满足全部需求的现成方案**。当前分类保持 Feature，不走“已有方案完全满足”的提前终止路径。

可以复用底层能力，但仍需新增线程组级恢复协议。必须同时解决：

1. 独立的历史内存快照；
2. 全组安全停驻及新旧地址空间切换；
3. 已退出线程的重建及 TID 身份一致性；
4. 新增线程的移除和退出清理顺序；
5. ARM64 每线程寄存器、TLS、FP/SIMD 以及内核登记用户地址恢复；
6. SIGABRT 并发触发、SIGKILL 优先和一次性资源生命周期。

其中，支持正常 pthread 线程退出/join/detach 是实质性新增工作，不能靠保留 mm 引用或简单保存 task_struct 完成。

## 4. 动态线程恢复的关键证据

### 4.1 get_pid 不是 TID 预留

`detach_pid()` 最终在没有任务关联时调用 `free_pid()`。`free_pid()` 在 `pidmap_lock` 下从各层 namespace 的 IDR 移除号码，之后才通过 RCU 放引用。

因此，检查点即使额外持有 `struct pid` 引用，也只能延缓对象释放，不能阻止其他任务获得同一号码。`get_task_struct()` 同样不撤销任务退出及其资源清理。

旧 TID 往往同时出现在 pthread 结构、锁 owner、线程定向接口等处，clear_child_tid 又关联对应线程库对象。恢复内存但给重建线程分配不同 TID，不能视作透明恢复。后续设计必须选择并论证号码保留/重建策略，不能在故障时抢占其他存活任务的号码。

### 4.2 正常线程退出有不可逆的内核清理

`kernel/exit.c:815-930` 的 `do_exit()` 会执行 `exit_mm()`、文件/fs/namespace 引用释放、`exit_thread()`、cgroup 退出、`exit_notify()` 等，并最终进入 `do_task_dead()`。

`kernel/fork.c:1737-1779` 还包括 clear_child_tid 清零和 futex 唤醒，`kernel/futex/core.c:1058-1163` 包括 robust/PI futex 清理。非 leader 线程在无 ptrace 的普通路径自动回收（`exit_notify():733-771`）。

若完整执行正常退出，需按受控重建路径恢复，不能清掉 PF_EXITING 后把旧 task 再次唤醒。用户后续提出可延迟真正销毁 task，因此允许论证专门的“逻辑退出并完成 join 通知、内核任务保留”路径。仅停驻而不发布退出通知仍然不满足需求。

### 4.3 新增线程应在旧地址空间完成清理

移除检查点后新增线程时，其退出清理可能访问 TLS、robust list、clear_child_tid。若先把这些任务切到恢复 mm，再走原退出清理，可能清零或修改快照中的其他数据。

需要先在旧 mm 安全完成清理，或提供明确隔离这些用户地址访问的受控清理路径。使用进程级 SIGKILL 杀新增线程会触发整个线程组终止，不能当作单线程移除接口。

## 6. 下一阶段需要解决的问题

- 是否新增 PID 号码预留及受控重建支持，如何与 PID namespace 退出、资源限额和失败清理兼容。
- 同 TGID 内创建替代线程、存活线程换 mm，以及新线程退出之间的全组协议。
- leader 已退出但组未退出时的身份处理；整个进程退出仍不属于自动复活范围。
- 回滚前后线程库内存、用户栈、TLS、clear_child_tid、robust list、rseq 的一致性。
- 当前 ARM64 下游包含较新的扩展状态：FP/SIMD 之外的 SVE/SME、PAC、MTE 等应逐项恢复或明确拒绝，不能仅复制 pt_regs 宣称支持。

当前是“存在底层基础，尚需设计及原型证明”，不是已验证所有约束均可满足。研究及方案应保留用户要求的动态线程生命周期，不退化为固定线程 demo。

## 7. 用户新增保留态方向后的补充

用户在调研阶段后提出检查点有效时不真正销毁 task。进入④比较原检查点成员保留与全部退出任务保留，详见 `04-方案对比.md`；原来基于“线程必须完全销毁”的重建难点不再是唯一实现路径。

新增源码依据：

- `kernel/exit.c:994-997`：原始 exit 系统调用在进入 do_exit 前可提供独立的正常线程退出分流点；`exit_group:1038-1042` 则应保持真正整组退出。
- `kernel/exit.c:822-840`：do_exit 早期已经更改 quick_threads、PF_EXITING、live，保留路径不能先执行这部分再随意逆转。
- `kernel/futex/core.c:1058-1163`：退出清理会清 robust_list，结束时 futex_state 为 DEAD；复用清理原语不代表回滚时可以无锁重置状态。
- `include/linux/sched.h:2499-2561`：rseq 通知依赖 task 中登记，rseq_execve 展示清除注册地址等字段的方法；需要完整处理通知和迁移状态，不能保留指向已复用 TLS 的登记。
- `kernel/signal.c:988-1079,2433-2527`：信号路由和组停止仍会遍历保留任务，必须显式适配而非仅依赖睡眠状态。
- glibc `nptl/pthread_detach.c:23-53`、`nptl/nptl_free_tcb.c:23-43`：detach 与 joinstate 竞争并释放 TCB；保留 task 不能阻止用户态正常回收。
- glibc `sysdeps/nptl/libc_start_call_main.h:61-83`：初始线程 pthread_exit 的收尾与工作线程不同，会自行发布 joinstate 退出通知；不能硬编码所有线程使用相同注册地址或清理动作。
