# 需求开发工作流

## 概述

本工作流定义了从需求提出到 QEMU 验证完成的完整开发流程。面向 OLK-6.6 内核开发场景。

## 审核机制

每个中止点（需用户确认的阶段）在提交用户确认前，须先经 **Momus 代理审核**。Momus 从以下维度评估产出物质量：

- **清晰性**：产出物的表述是否准确、无歧义
- **可验证性**：验收标准是否有明确的判定方法，能否被客观检验
- **完整性**：是否覆盖了该阶段应产出的所有内容，有无遗漏关键信息
- **一致性**：产出物内部及与前序阶段之间有无矛盾或脱节

审核流程：

1. 中止点触发时，将本阶段产出物提交 Momus 审核（使用 `task(subagent_type="momus", prompt=...)`）
2. Momus 输出审核意见：**通过** / **条件通过（附改进建议）** / **不通过（附必须修改项）**
3. 审核意见与产出物一并提交用户确认
4. 用户基于审核意见做决策：
   - **通过**：确认后进入下一阶段
   - **条件通过**：接受改进建议并继续，或要求先修复再确认
   - **不通过**：回到当前阶段或前一阶段修复后重新提交审核

> 回路判定点（②早期终止、③→①需求回退、⑦→⑤设计回退）同样须经 Momus 验证触发条件是否成立，避免误判导致不必要的回退。

**Momus 调用原则**：仅在中止点（用户确认点）和回路判定点调用 Momus。代码自审（⑥ 内）使用 checklist 自检，不调 Momus；补丁格式验证（⑧ 内）由 `scripts/checkpatch.pl` + `git am` 自动化完成，不调 Momus。

## 工作目录约定

每个需求在 `~/workspace/<project-name>/` 下创建独立项目目录，所有分析和设计产物均归档于该目录。

### 构建配置基线

所有编译验证使用 `~/tools/qemu_arm64_defconfig` 为基础配置。该文件是完整的内核 `.config`（8054 行），不是 Kconfig fragment。

使用方式：

```sh
cp ~/tools/qemu_arm64_defconfig .config && make olddefconfig
scripts/config --enable CONFIG_<new-feature>   # 启用新增选项
make -j$(nproc) Image
```

此基线适用于 ⑥ 编译验证和 ⑦ QEMU 验证，下文不再重复说明。

## 需求分级

### 分级判定

在 ① 阶段末尾，根据需求性质判定执行路径。分级判定结果写入 `01-需求描述.md`，经 Momus 审核后与需求描述一并提交用户确认。

| 级别 | 定义 | 判定条件 | 执行路径 |
|---|---|---|---|
| **Feature** | 新特性开发 | 无现成方案，需从零设计实现 | ① → ② → ③ → ④ → ⑤ → ⑥ → ⑦ → ⑧ |
| **Backport** | 上游已有实现，需合入 | 上游主线或社区已有对应 commit/patch series | ① → ②（验证上游方案存在）→ ⑥ → ⑦ → ⑧ |
| **Bugfix** | 缺陷修复 | 已有代码行为不符合预期，但根因和修复范围明确 | ① → ⑥ → ⑦ → ⑧ |
| **Trivial** | 微小改动 | 单文件、无逻辑变更（config 调整、typo、注释修正等）| ① → ⑥ → ⑧ |

> 分级原则：能走短路径的不走长路径。当不确定分级时，按更严格的级别处理（即选择路径更长的级别）。分级判定须经 Momus 审核。

### 已存在方案的早期终止（Feature 路径的 ② 阶段）

若 ② 调研发现已有现成方案可**完全满足**需求（无需任何新增开发或代码修改），须经 **Momus 验证**（确认"完全满足"判定是否成立）后，提交用户确认是否终止开发流程，直接进入 ⑧ 产物归档（产出轻量验证报告 + 归档结论）。

## 流程步骤

### ① 需求归档与分级

- **输入**: 用户提出的初始需求描述
- **过程**:
  1. 接收需求，识别模糊点和缺失信息
  2. 与用户确认：需求背景（为什么做）、原始诉求（解决什么问题）、约束条件
  3. 双方对需求理解达成一致
  4. **需求分级**：按分级判定标准确定级别（Feature / Backport / Bugfix / Trivial）
- **产出**: `~/workspace/<project-name>/01-需求描述.md`
- **内容**: 需求背景、原始诉求、功能目标、约束条件、验收标准、**需求分级及判定理由**
- **中止点**: 需求描述与分级需用户确认后方可进入下一阶段（须经 Momus 审核）

---

### ② 现有方案与上游调研

> **适用范围**: Feature 路径、Backport 路径。Bugfix 和 Trivial 路径跳过。
>
> **与 ③ 并行**: ② 与 ③ 可并行启动——两者检索和分析的是同一批内核代码，只是角度不同（调研 vs 架构分析）。② 调研方向确定后，即可同时启动 ③ 的代码分析。

- **输入**: 需求描述
- **原则**: 在深入架构分析之前，先确认需求是否已有现成解决方案，避免重复造轮。
- **调研维度**:
  1. **内核现有功能评估**：当前内核是否已有功能（config 选项、已有模块、已有接口）可直接或组合满足需求？若存在，列出并评估差距
  2. **社区最新版本调研**：若现有功能不满足，检查 Linux 主线最新版本（及本仓库已 backport 的提交）是否已有相关功能实现。**每个找到的方案须附链接**（upstream commit URL、lkml thread、patchwork 链接等）
  3. **社区邮件列表调研**：检索 LKML / lore.kernel.org 中是否有相关 RFC、patch set、讨论，了解社区对该类需求的设计方向。**每条引用须附链接**（lore.kernel.org 永久链接）
- **方法**:
  - 使用 `explore` 代理检索本仓库中相关的 config 选项、已有模块、接口
  - 使用 `librarian` 代理检索上游内核源码、社区邮件列表、LKML 讨论，**要求 librarian 返回每条发现的来源 URL**
- **产出**: `~/workspace/<project-name>/02-现有方案与上游调研.md`
- **内容**:
  - 内核现有功能评估（列表对比：已有机制 vs 需求的匹配度及不满足原因）
  - 社区最新版本调研结论（上游是否有相关实现，若有则分析差距；**附来源链接**：upstream commit / patchwork / lore 等）
  - 社区邮件列表调研结论（相关 RFC / 讨论 / 设计方向；**附 lore.kernel.org 永久链接**）
  - 替代方案总结（定位矩阵：已有方案与需求的定位对比，**每个方案附对应来源链接**）
- **中止点**: 调研结论需用户确认后方可继续（须经 Momus 审核）
  - Feature 路径 → 进入 ③（若并行启动则直接进入 ④）
  - Backport 路径 → 跳过 ③④⑤，直接进入 ⑥

> **早期终止路径**（Feature 路径专属）：若调研发现已有现成方案可完全满足需求，须经 **Momus 验证**后，提交用户确认是否终止开发流程，直接进入 ⑧（产出轻量验证报告 + 归档结论）。

---

### ③ 架构分析

> **适用范围**: Feature 路径。可与 ② 并行启动。

- **输入**: 需求描述 + 相关内核代码（② 调研结论用于交叉验证，但不阻塞 ③ 启动）
- **原则**: 深度思考，不浮于表面。分析必须支撑后续方案对比的可行性判断。
- **分析维度**:
  - **静态架构**: 涉及的功能模块现有设计、关键数据结构（含字段语义）、API 全集（函数签名 + 调用契约）
  - **动态行为**: 调用链（从触发点到结果）、时序/并发语义（锁、RCU、preempt）、错误路径
  - **配置与构建**: Kconfig 依赖、Makefile 编译条件、feature 宏开关
  - **外部接口**: 用户态接口（debugfs/sysfs/procfs）、内核态 consumer（哪些子系统依赖本模块）
  - **生命周期**: 初始化路径、运行时行为、热插拔/卸载路径
  - **变更影响评估**: 本次改动会影响哪些现有功能模块、与哪些并行开发任务有潜在冲突、合入时的依赖排序考量
- **方法**:
  - 使用 `gen_kernel_kb` 生成模块知识库，作为分析基线
  - 交叉验证：代码实现 vs 文档描述 vs 提交历史中的设计意图
  - 必要时咨询 Oracle（高复杂度架构决策、多子系统交互）
- **产出**: `~/workspace/<project-name>/03-架构分析.md`
- **内容**:
  - 各维度的分析结论
  - 差距分析——现有架构与需求的匹配度及缺口
  - **缺口解决策略建议**——对每个缺口给出初步解决方向（扩展 / 新增 / 重构 / 绕过），仅供参考，不替代 ④ 的正式方案对比
  - 变更影响评估结论
- **中止点**: 无（架构分析结果供 ④ 参考）

> **回路**: 若架构分析揭示需求本身有问题（目标不可实现或设计目标矛盾），须经 **Momus 验证**（确认需求问题判定是否成立）后，再提交用户决策是否回到 ① 重新定义或调整需求。

### ④ 方案对比

- **输入**: 架构分析（含缺口解决策略建议）
- **产出**: `~/workspace/<project-name>/04-方案对比.md`
- **内容**:
  - 至少 2 个可行方案
  - 每个方案的实现思路
  - 优缺点对比表
  - 推荐方案及理由
- **中止点**: 等待用户确认方案（须经 Momus 审核）

### ⑤ 详细设计与测试设计

- **输入**: ④ 方案对比 + 用户选择
- **过程**:
  1. 用户从候选方案中选择或提出修改意见
  2. 对确认的方案进行细化：将粗略对比中的方案轮廓展开为可指导详细设计的方案骨架，明确边界、排除项、关键设计决策点
  3. 基于确认的方案展开详细设计：新增/修改的文件、函数、数据结构、接口定义、数据流图、实现顺序与依赖
  4. **测试设计**（同步进行，不再分拆）：
     - 测试策略：测试类型（KUnit / QEMU 功能验证 / 用户态测试）、测试框架、覆盖维度（功能 / 并发 / 边界 / 错误路径）
     - 测试用例列表（含预期结果、测试数据、触发方式），编号体现层级：
       - 按"特性 → 函数 → 场景/分支"三级编号，如 `TC-01`（特性级）、`TC-01.02`（函数级）、`TC-01.02.03`（场景/分支级）
     - KUnit 测试用例设计（如适用）
     - QEMU 功能验证场景设计
     - 测试前置条件
     - **覆盖率矩阵**（独立交付件 `覆盖率.md`，设计阶段产出骨架）：
       - 以设计中的每个函数为单位，逐分支列出覆盖路径和对应的测试用例
       - 覆盖率目标：**100%**（每函数每分支），例外路径（不可测试的硬件依赖、概率性条件等）须注明合理理由
       - 覆盖矩阵格式：`函数 → 分支/关键路径 → 覆盖 TC（层级编号）→ 设计状态`；实测状态（✅ 🔴 ⚪）由 ⑦ 阶段填写
  5. 风险点
- **产出**:
  - `~/workspace/<project-name>/05-实现方案.md`
  - `~/workspace/<project-name>/覆盖率.md`（设计阶段：覆盖矩阵 + TC 列表；⑦ 阶段补充实测结果）
- **中止点**: 方案确认与详细设计（含测试设计）需用户确认后方可进入 ⑥；若用户对方案不满意则回到 ④ 调整（须经 Momus 审核）

> **回路**: 若测试设计发现存在不可测路径（无法在 QEMU 中触发、设计上无法验证），须经 **Momus 验证**（确认不可测路径判定是否成立、回退范围是否合理）后，再提交用户决策是否调整设计，使路径可被覆盖。

### ⑥ 代码实现与自审

- **输入**: ⑤ 实现方案（含测试设计）
- **原则**: 代码实现与 KUnit 测试同步编写，测试即代码的一部分。
- **产出**: 代码修改（多个 git commit，按逻辑单元拆分）+ 测试代码 + 自审结论
- **编码原则**:
  - **精简至上**: 用最少的代码解决问题，不引入不必要的抽象层或过度设计
  - **并发安全**: 充分分析并发场景，优先使用 RCU、lockless、atomic 等无锁方案；确需锁保护时，锁粒度尽可能细、持有时间尽可能短
  - **防御性编程**: 所有外部输入和跨模块调用必须有参数校验，避免空指针、越界、整数溢出
  - **错误处理**: 每个可能失败的路径有明确的错误处理和资源释放
  - **独立 Kconfig 控制**: 新特性需有独立的 `CONFIG_xxx` 选项，确保依赖关系合理
  - **必要注释**: 关键逻辑、非直观设计决策、锁语义需注释说明
- **Commit 规范**:
  - 格式：
    ```
    subsystem: short description (不超过 75 字符)

    详细说明（改了什么、为什么改、怎么改）。每行不超过 75 字符。

    Signed-off-by: Name <email>
    ```
  - 每个逻辑单元一个独立 commit，不混入无关改动
- **测试实现**（与代码同步编写）:
  - 编写可执行的测试程序（KUnit 模块、QEMU 验证脚本、用户态测试工具等）
  - 所有测试源码和脚本归档至 `~/workspace/<project-name>/tests/`
  - 确保测试程序可独立编译/执行，附简要使用说明
  - **自动化运行脚本**: 包含 `run_tests.sh`（或类似脚本），可一键执行所有测试用例并收集结果
  - 推荐包含 `run_qemu.sh` 脚本，封装 QEMU 启动 + 测试执行 + 结果收集的完整流程
- **增量验证**（强制）:
  - **逐 commit 编译验证**：每个 commit 完成后，立即执行 `make -j$(nproc)` 编译确认零 error
  - **逐 commit 样式检查**：每个 commit 完成后，立即执行 `scripts/checkpatch.pl --strict` 确认零新增 warning/error
  - 不通过则当场修复，通过后再继续下一个 commit
- **质量门禁**（全部 commit 完成后）:
  - 遵循内核编码规范（`Documentation/process/coding-style.rst`）
  - 最终代码通过 `scripts/checkpatch.pl --strict` 检查，零新增 warning/error
  - 不影响现有功能（不破坏已有行为）
  - 编译通过：以 `~/tools/qemu_arm64_defconfig` 为基础配置，追加新增 Kconfig 选项后，`make -j$(nproc) Image` 零 error
  - 如涉及新增 Kconfig 选项，需同步修改对应 Kconfig 文件；如涉及用户可见行为变更，需更新 `Documentation/` 对应文档

#### ⑥.1 代码自审（checklist 自检，不调 Momus）

全部代码实现和测试完成后，执行以下三项自审：

1. **功能完整性审查**: 逐 commit review diff，对照 ⑤ 实现方案核对完整性——所有设计的改动是否已实现、是否有遗漏逻辑
2. **代码质量审查**: 确认无死代码、无调试残留（printk 调试语句、TODO 占位符）、无冗余注释；所有新增代码符合 `scripts/checkpatch.pl --strict` 标准
3. **并发安全审查**: 确认关键路径的并发安全分析已落地——锁粒度是否合理、RCU/atomic 使用是否正确、是否有竞态窗口

- **产出**: `~/workspace/<project-name>/06-自审结论.md`（记录三项审查结果及整改情况）
- **中止点**: 三项审查全部通过后方可进入 ⑦；任一项不通过则回到 ⑥ 修复
- **审核方式**: Checklist 自检即可，不调 Momus。仅在自审无法确定是否通过时，咨询 Oracle。

#### ⑥.2 补丁格式验证（自动化，不调 Momus）

自审通过后，对生成的补丁执行自动化验证（此步骤从旧版 ⑩ 前移到 ⑥，作为质量门禁的一部分）：

- `scripts/checkpatch.pl --strict <patch-file>` 对每个 `.patch` 文件，零新增 warning/error
- `git am --check *.patch` 验证补丁可干净应用
- 不通过则回到 ⑥ 修复，通过后进入 ⑦

### ⑦ QEMU 验证

> **适用范围**: Feature、Backport、Bugfix 路径。Trivial 路径跳过。

- **输入**: ⑥ 产出的代码 + 测试
- **环境**: `qemu-system-aarch64`（ARM64 virt）
- **产出**: 测试报告 + 覆盖率实测结果（填入 `覆盖率.md`）+ gcov 原始数据
- **步骤**:

  1. **构建带 gcov 插桩的内核**:
     - 以 `~/tools/qemu_arm64_defconfig` 为基础配置，启用 gcov：
       ```sh
       cp ~/tools/qemu_arm64_defconfig .config && make olddefconfig
       scripts/config --enable CONFIG_GCOV_KERNEL
       scripts/config --enable CONFIG_GCOV_PROFILE_ALL
       make olddefconfig
       ```
     - 追加特性新增的 Kconfig 选项（如 ⑥ 中启用过的 `CONFIG_xxx`）
     - 执行 `make -j$(nproc) Image`

  2. **QEMU 环境准备**: 确保 rootfs 已挂载 debugfs：
     ```sh
     mount -t debugfs none /sys/kernel/debug
     ```

  3. 启动 QEMU 并加载新内核

  4. 执行测试用例（优先使用 `tests/run_qemu.sh` 自动化脚本）

  5. 记录测试结果，标记通过/失败

  6. **收集 gcov 覆盖率数据**:
     - 测试执行完毕后，从 `/sys/kernel/debug/gcov/` 提取 gcov 原始数据：
       ```sh
       # 在 QEMU 内执行（或通过 run_qemu.sh 自动调用）
       find /sys/kernel/debug/gcov/ -name '*.gcda' -exec cp --parents {} /tmp/gcov_data/ \;
       find /sys/kernel/debug/gcov/ -name '*.gcno' -exec cp --parents {} /tmp/gcov_data/ \;
       ```
     - 将 gcov 数据从 QEMU 传出（通过 virtio-9p 共享目录或 scp），保存至 `~/workspace/<project-name>/tests/gcov/`
     - 对目标源文件生成覆盖率报告：
       ```sh
       # 在宿主机执行（需 gcov 工具链，路径映射需与内核编译环境一致）
       cd ~/workspace/<project-name>/tests/gcov/
       lcov --capture --directory . --output-file coverage.info
       genhtml coverage.info --output-directory coverage_html
       ```
     - gcov 数据归档至 `~/workspace/<project-name>/tests/gcov/`；生成的 HTML 报告归档至 `~/workspace/<project-name>/tests/gcov/coverage_html/`

  7. **覆盖率实测**：基于 gcov 生成的覆盖率数据，对照 ⑤ 中产出的覆盖矩阵（`覆盖率.md`），逐项核对每个分支是否被实际执行覆盖，在矩阵中填写实测状态（✅ 🔴 ⚪）；未覆盖项须补充用例或提供合理例外理由

- **自动化指导**:
  - QEMU 启动命令参考：
    ```sh
    qemu-system-aarch64 \
        -machine virt,gic-version=3 \
        -cpu max \
        -smp 4 \
        -m 2G \
        -kernel arch/arm64/boot/Image \
        -drive file=~/tools/buildroot/output/images/rootfs.ext4,format=raw,if=none,id=hd0 \
        -device virtio-blk-device,drive=hd0 \
        -append "console=ttyAMA0 root=/dev/vda rw" \
        -nographic
    ```
  - 测试结果收集：从 QEMU 串口输出中过滤 dmesg 关键信息、解析测试程序的标准输出、自动汇总通过/失败计数；QEMU 原始串口日志保存至 `~/workspace/<project-name>/tests/qemu_output.log`，不放入 `patches/`
  - gcov 数据收集：推荐在 `tests/run_qemu.sh` 中集成 gcov 数据提取逻辑（挂载 debugfs → 执行测试 → 收集 gcov 数据 → 传输至宿主机），实现覆盖率数据的一键采集

- **失败回退**: 测试失败 → 定位根因 → 回到 ⑥ 修复 → 重新编译验证，直至全部通过
  - 覆盖率未达 100% → 补充用例 → 回到 ⑥ 补充实现 → 重新验证

- **中止点**: QEMU 验证通过 + 覆盖率达标后，须经 Momus 审核（测试报告 + gcov 覆盖率报告 + `覆盖率.md` 的结果可信度），再提交用户确认

### ⑧ 产物归档

- **输入**: ⑥ 产出的 git commits（已通过质量门禁）+ ⑦ 的测试报告（已验证通过）
- **产出**:
  - `~/workspace/<project-name>/patches/` 下的格式化补丁（仅补丁文件；测试报告、覆盖率等非补丁产物保留在项目根目录）
  - `~/workspace/<project-name>/00-交付清单.md`
  - `~/workspace/<project-name>/覆盖率.md`（最终版本，含设计与实测完整对照）
  - `~/workspace/<project-name>/测试报告.md`（从 ⑦ 产出归档，保留在项目根目录）
- **步骤**:

  **A. 交付清单**:
  1. 编写 `~/workspace/<project-name>/00-交付清单.md`，建立需求→交付的完整追溯链
  2. 内容须包含：
     - 需求编号/名称（对应 ① 的需求描述）+ 需求级别
     - 补丁系列概述（解决什么问题、补丁数量、各 patch 职责分工）
     - 测试覆盖说明（测试类型、覆盖维度、通过率）
     - 已知限制与未覆盖场景
     - 与上游的关系（backport / 原创 / 修改自某提交）

  **B. 测试报告归档**:
  1. ⑦ 的测试报告保存为 `~/workspace/<project-name>/测试报告.md`（项目根目录，不与补丁混放）
  2. 测试报告须包含：测试环境（QEMU 版本、内核配置）、用例执行结果（通过/失败明细）、未通过项的处理说明

  **C. 补丁归档**:
  1. **生成补丁文件**:
     - 单 commit: `git format-patch -1 <commit-hash> -o ~/workspace/<project-name>/patches/`
     - 多 commit 系列: `git format-patch --cover-letter <base>..<HEAD> -o ~/workspace/<project-name>/patches/`
     - `--cover-letter` 会生成 `0000-cover-letter.patch` 模板，需编辑填写系列概述
  2. **补丁命名**: 由 `git format-patch` 自动生成，格式为 `NNNN-subject.patch`，无需手动改名
  3. **编辑封面信**（多 commit 系列时）: 填写 `0000-cover-letter.patch`，说明本系列的：
     - 整体目的（解决什么问题）
     - 与上游的关系（backport / 原创 / 修改自某提交）
     - 各 patch 的职责分工
     - 测试情况摘要
- **中止点**: 产物归档完成后，须经 Momus 审核（交付清单 + 补丁 + 测试报告完整且可干净应用），再提交用户确认

## 特殊路径

### Backport 路径

```
①（需求归档 + 分级判定：Backport）→ ②（验证上游方案存在 + 评估合入难度）→ ⑥（cherry-pick + 适配 + 自审）→ ⑦（QEMU 验证）→ ⑧（归档）
```

- ② 阶段聚焦验证上游方案的适用性，无需完整的三个调研维度
- 跳过 ③④⑤（架构分析、方案对比、详细设计）
- ⑥ 阶段需注明 cherry-pick 来源（upstream commit hash）

### Bugfix 路径

```
①（需求归档 + 分级判定：Bugfix）→ ⑥（修复 + 自审）→ ⑦（QEMU 验证）→ ⑧（归档）
```

- 跳过 ②③④⑤
- ① 阶段需求描述需包含复现步骤和预期行为

### Trivial 路径

```
①（需求归档 + 分级判定：Trivial）→ ⑥（修改 + 自审）→ ⑧（归档）
```

- 跳过 ②③④⑤⑦
- ⑦（QEMU 验证）跳过——微小改动无运行时影响（如 config 调整、注释修正）

### 用户中途终止

若用户在任何阶段决定终止开发：

1. 已完成的阶段产出物（`*.md` 文档）归档至 `~/workspace/<project-name>/`
2. 在项目根目录创建 `ABANDONED` 标记文件，说明终止原因和终止阶段
3. 不进入 ⑧（产物归档），除非用户明确要求保留补丁
