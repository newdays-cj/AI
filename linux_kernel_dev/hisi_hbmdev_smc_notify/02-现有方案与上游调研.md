## 1. 内核现有功能评估

### 1.1 仓库现有 HiSilicon SMC FID 全量盘点

### 1.3 drivers/soc/hisilicon/ 通信机制现状

`drivers/soc/hisilicon/` 全目录 grep `smc|SMC|smccc|SMCCC` **零匹配**。该目录下驱动与固件通信机制：
- **PCC mailbox**：`kunpeng_hccs.c`（`acpi/pcc.h` + `mbox_client`）
- **ACPI 方法**：`hisi_hbmdev.c`（`_ON`/`_STA`）
- **直接 MMIO**：`hisi-reboot.c`（`writel`）

目标文件 `hisi_hbmdev.c` 当前**无任何 SMC 基础设施**，需新增 `#include <linux/arm-smccc.h>` 和 SMC 调用逻辑。

## 2. 社区规范调研

### 2.1 SMCCC FID 编码规则

**规范来源**：ARM DEN 0028C（"SMC Calling Convention"），内核头文件 `include/linux/arm-smccc.h` 明确引用；`drivers/firmware/smccc/soc_id.c` 引用 "Section 7.4"。
- 规范 URL：`https://developer.arm.com/documentation/den0028/latest`

**FID 位布局**（`include/linux/arm-smccc.h:19-44`）：

```
 31  30  29          24  23              16  15               0
┌────┬────┬─────────────┬─────────────────┬──────────────────┐
│Type│Conv│  Owner ID   │  (sub-range)    │  Function Number  │
│    │    │   (6 bits)  │  (owner-defined) │    (16 bits)     │
└────┴────┴─────────────┴─────────────────┴──────────────────┘
```

| Bit | 字段 | 值 |
|---|---|---|
| 31 | Call Type | 0=STD（可抢占）, 1=FAST（原子） |
| 30 | Calling Convention | 0=SMC_32, 1=SMC_64 |
| 29-24 | Owner ID | 0=ARCH, 1=CPU, **2=SiP**, **3=OEM**, 4=STANDARD, 5=STD_HYP, 6=VENDOR_HYP |
| 23-0 | Function Number | 由 owner 自行分配 |

构造宏：`ARM_SMCCC_CALL_VAL(type, calling_convention, owner, func_num)`

### 2.2 SiP sub-range 分配机制

**关键事实**：SMCCC 规范**不**在 SiP/OEM owner 空间内按厂商分配子范围。owner=2 (SiP) 和 owner=3 (OEM) 的整个 16 位 function number 空间（0x0000-0xFFFF）**完全由厂商自行管理**。ARM 仅集中管理 owner=0 (ARCH) 和 owner=4 (STANDARD)。

厂商身份通过运行时 `SMCCC_ARCH_SOC_ID` 调用（owner=0, func=0x02）返回 JEP-106 制造商码识别，与 FID 分配无关。

**实际影响**：HiSilicon 自行分配 function number。仓库内已用 function number：0x0109（TRNG）、0x0504/0x0505（STL）、0x90/0x91（PV SGI/SGI）。新 FID 需与 HiSilicon HIP11 固件团队确认不冲突。

## 3. Linux 5.10 SMCCC Helper API

### 3.1 三个 Helper 层级

| Helper | 实现 | 适用场景 | 模块可用 |
|---|---|---|---|
| `arm_smccc_smc()` | 外联汇编 `arch/arm64/kernel/smccc-call.S`，`EXPORT_SYMBOL(__arm_smccc_smc)` | SMCCC v1.0 直 SMC，固定 conduit | ✅ |
| `arm_smccc_1_1_smc()` | 内联汇编宏 | SMCCC v1.1+ 直 SMC，SVE hint | ✅ |
| `arm_smccc_1_1_invoke()` | 宏，内部调 `arm_smccc_1_1_get_conduit()` 自动选 SMC/HVC | 通用可移植代码，自动 conduit | ✅（但 `get_conduit` 未导出，`invoke` 宏内联所以仍可用） |

### 3.2 返回值契约

`struct arm_smccc_res` 含 `a0`-`a3` 四个 `unsigned long` 字段。标准返回码（`include/linux/arm-smccc.h`）：

| 宏 | 值 | 含义 |
|---|---|---|
| `SMCCC_RET_SUCCESS` | 0 | 成功 |
| `SMCCC_RET_NOT_SUPPORTED` | -1 | 不支持 |
| `SMCCC_RET_NOT_REQUIRED` | -2 | 不需要 |
| `SMCCC_RET_INVALID_PARAMETER` | -3 | 参数无效 |

**判断模式**（参考 `drivers/firmware/smccc/soc_id.c`、`arch/arm64/include/asm/archrandom.h`）：
```c
struct arm_smccc_res res;
arm_smccc_1_1_invoke(FID, ..., &res);
if ((int)res.a0 < 0)  // < 0 即错误（SMCCC_RET_* 均为负）
    /* 错误处理 */;
```

### 3.3 调用上下文

- FAST call 原子完成，可在任何上下文（进程/原子/IRQ）调用
- 无 preempt disable、无锁要求
- `arm_smccc_1_1_get_conduit()` 在 `arm_smccc_version_init()` core init 阶段完成探测，`module_init` 时已就绪

## 4. 替代方案总结与定位矩阵

| 方案 | Owner | FID 前缀 | 调用约定 | Helper | 与仓库现有 HiSilicon SMC 一致性 | 适用性评估 |
|---|---|---|---|---|---|---|
| A | 3 (OEM) | `0xC3xxxxxx` | FAST/SMC_64 | `arm_smccc_smc` | ✅ 与 TRNG/STL 一致（owner/调用约定）但 SMC_64 适配 u64 handle | **推荐**：传 u64 ACPI handle，SMC_64 必要；与现有 HiSilicon owner=3 一致 |
| B | 6 (VENDOR_HYP) | `0xC6xxxxxx` | FAST/SMC_64 | `arm_smccc_1_1_invoke` | ✅ 与 IPIV 一致 | 可选：但 VENDOR_HYP 语义偏向虚拟化，HBM 电源管理不属于此范畴 |
| C | 5 (STD_HYP) | `0xC5xxxxxx` | FAST/SMC_64 | `arm_smccc_1_1_invoke` | ❌ 0xC5 已被 PV SCHED 部分占用 | **不推荐**：语义不符（STD_HYP 是 ARM 标准半虚拟化），且存在冲突 |
| D | 2 (SiP) | `0xC2xxxxxx` | FAST/SMC_64 | `arm_smccc_smc` | ❌ 仓库内无 HiSilicon SiP 先例 | 可选：SiP 语义最贴切（Silicon Provider），但需与固件确认 |

### 关键决策点（需用户确认）

用户原始假设"0xC5000000-0xC50000FF range (fast call, bit 31=1, owner=4/SiP, HiSilicon sub-range)"存在解码偏差：
1. 0xC5 解码为 owner=5 (STANDARD_HYP)，非 owner=4 也非 SiP(2)
2. owner=4 是 STANDARD（ARM 标准服务，如 PSCI），非 SiP
3. SiP 实际是 owner=2，0xC2 前缀
4. 0xC5 范围被 generic PV SCHED 占用 4 个 FID

**推荐方案 A**：`0xC300xxxx`（owner=3/OEM，FAST/SMC_64），与仓库现有 HiSilicon SMC owner 一致，SMC_64 适配 u64 ACPI handle 参数传递。具体 function number 选 `0x0006`（避开 0x0109/0x0504/0x0505/0x0090/0x0091），最终 FID 候选 `0xC3000006`。

**必须由用户确认**：
- (1) Owner 选择：OEM(3) / SiP(2) / VENDOR_HYP(6)？
- (2) function number：`0x0006` 是否与固件团队分配一致？
- (3) 调用约定：SMC_64（推荐，传 u64）vs SMC_32？
- (4) Helper：`arm_smccc_smc`（与现有 HiSilicon 一致）vs `arm_smccc_1_1_invoke`（更现代）？
