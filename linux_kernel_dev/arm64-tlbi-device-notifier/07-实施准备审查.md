## 3. 首轮软件审查发现与整改要求

| 严重度 | 发现 | 必要整改 |
|---|---|---|
| 高 | KUnit 自动清理资源按逆序销毁；先注册 fixture、后安装 stub 时，stub 先消失，假对象清理可能落入真实硬件路径 | 改为 suite `.exit` 在 generic cleanup 前执行明确有序清理；部分安装与异常退出同样安全；还需核实 `.exit` 执行任务上下文。 |
| 中 | 直接使用 `kunit_hooks.get_static_stub_address` 属内部契约，不能声称公开 API | 选择可验证的安装协议并明确依赖。主会话发现返回成功的替代建议存在分配失败漏洞，已交回 Oracle 复核，见下一节。 |
| 中 | T7–T9 guard 不匹配会执行真实 raw 指令 | 错上下文在 bridge 入口拒绝；raw helper 的不匹配落穿仅源码/构建审计。 |
| 中 | provider TU 的 inline stub 不覆盖其他 TU 的 young/contpte/reclaim/fullmm 实际调用者 | 明确 E_CALLER 审计及后续平台运行义务，不以 T2/T3/T6 直接测试冒充调用者集成覆盖。 |
| 低 | 替换整个 batch_add 不执行其内部 full/forced-sync 分支 | 捕获命令参数，内部原分支列 E_IO/回归。 |
| 低 | 同一 WARN_ON_ONCE 站点无法每向量重新告警 | 每非法组合断言 -EINVAL，专用启动最多一次精确告警，不重置全局 once 状态。 |

## 4. 安装成功判据的追加复核

首轮 Oracle 建议“公开 activation 返回即成功，失败均 fatal”。主会话回读 `lib/kunit/static_stub.c:113-120` 后发现：ctx 分配虽有断言，随后 `kunit_alloc_resource` 的返回值没有断言或检查。因此不能将正常返回作为完整注册成功的证明。

同一 Oracle 会话追加复核已确认该反证，撤回“activation 返回即成功”的建议。最终选择保留 `kunit_hooks.get_static_stub_address`，明确为本源码版本绑定的内部依赖，不称公开 API；迁移内核版本须重新核实。

安装协议：每次 activation 后先检查 hook 非空，再以准确 real-function 地址查询，要求结果等于目标 typed replacement；只有确认后才加入 installed ledger。全部确认前 `run_enabled=false`。缺失或不匹配即中止安装，不进入 raw/OF/MMIO/CMDQ；清理仅 deactivate 已核实项，不能对不存在的失败项调用会断言的 deactivate。

异常清理使用每用例 `struct kunit_suite.exit`，不是 `suite_exit`。`lib/kunit/test.c:476` 起的 cleanup kthread 先设置 `current->kunit_test=test`，因此 `.exit` 内的 in_task/current-test 守卫仍可匹配。顺序为停 run/worker、在已核实 stub 保护下销毁候选和假对象、停已核实 stub、注销真实计数订阅并同步、释放 fixture，最后框架 generic cleanup。

**E_KUNIT_OOM**：ctx 已分配但 resource 分配失败时，本版本 KUnit 会遗失其私有 ctx。精确地址核验可发现 stub 未安装并阻止危险执行，但测试调用者没有指针可释放该框架资源。此路径不做全局分配故障注入，不宣称框架资源账平衡，也不在本任务修改 KUnit 核心。特性自己的资源清理仍须正确。
