# 02 现有方案与上游调研：arm64 TLBI 设备通知

## 调研范围

本文档对 ① 需求描述中所述机制（基于 32 位 per-CPU MMIO 读清除寄存器、按 bit0 条件触发的新增 mmu_notifier 钩子）进行现有方案核实与上游调研。

调研边界如下。已核实：本树 OLK-6.6 的 arm64 TLBI 通知路径、mmu_notifier 回调族、arm-smmu-v3-sva 类比消费方，以及上游相关提交 `f7edb07`、`6bbd42e2df8f` 及其 stable 回灌。已参考但仅作类比：BTM（Broadcast TLB Maintenance，2020 年 SMMUv3 广播 TLB 维护）lore 镜像、Arm DVM 文档。注意：BTM 指 SMMUv3 的广播 TLB 维护特性，与内核 `arch_tlbbatch_*`（2023 年合入的 unmap 批量延迟 DSB 机制）是不同概念，不可混淆。未核实：全仓库范围穷举、未归档的社区补丁、尚未公开的厂商实现。

"未找到"结论受限于上述已检查来源，不声称该机制在全局范围内不存在。

## 1. 现有机制核实

### 1.1 arm64 TLBI 通知插入点

源文件 `arch/arm64/include/asm/tlbflush.h`，逐行核实：

**`flush_tlb_mm`（253-263 行）**：先 `dsb(ishst)`，发 `__tlbi(aside1is)` 与 `__tlbi_user(aside1is)`，再 `dsb(ish)` 完成屏障，最后调用 `mmu_notifier_arch_invalidate_secondary_tlbs(mm, 0, -1UL)`。现有回调在完成 DSB 之后触发，范围参数为全地址空间（`0` 到 `-1UL`）。

**`__flush_tlb_page_nosync`（265-276 行）**：先 `dsb(ishst)`，发 `__tlbi(vale1is)` 与 `__tlbi_user(vale1is)`，随后调用 `mmu_notifier_arch_invalidate_secondary_tlbs(mm, uaddr & PAGE_MASK, (uaddr & PAGE_MASK) + PAGE_SIZE)`。此回调在包装函数 `flush_tlb_page`（284-289 行）的完成 `dsb(ish)` 之前触发。

**`__flush_tlb_range_nosync`（418-443 行）**：先 `dsb(ishst)`，执行 `__flush_tlb_range_op(...)`，随后调用 `mmu_notifier_arch_invalidate_secondary_tlbs(mm, start, end)`。同样在包装函数 `__flush_tlb_range`（445-453 行）的完成 `dsb(ish)` 之前触发。

时序小结：`flush_tlb_mm` 的现有回调在完成 DSB 之后；nosync 页/范围变体的现有回调在完成 DSB 之前。这一点对需求 AC-3（MMIO 读取须在 TLBI 完成之后）有直接影响，详见第 3 节。

### 1.2 mmu_notifier 回调族与分发

源文件 `mm/mmu_notifier.c`，逐行核实：

**同步分发（588-604 行）**：`__mmu_notifier_arch_invalidate_secondary_tlbs` 在 `srcu_read_lock` 下遍历 `mm->notifier_subscriptions->list`，对每个订阅同步调用 `subscription->ops->arch_invalidate_secondary_tlbs(subscription, mm, start, end)`，调用结束后释放 SRCU 锁。属同步分发，回调返回即视为完成。

**注册互斥（620-628 行）**：`__mmu_notifier_register` 中以 `WARN_ON_ONCE` 检查，同一订阅不得同时注册 `arch_invalidate_secondary_tlbs` 与 `invalidate_range_start`/`invalidate_range_end`。二者互斥，属现有回调族的注册约束。

回调语义（`include/linux/mmu_notifier.h` 189-210 行）：`arch_invalidate_secondary_tlbs` 由架构代码在失效 TLB 时调用，用于管理与 CPU 共享页表的非 CPU TLB。调用时持有 ptl 自旋锁，不允许睡眠。

### 1.3 类比消费方：arm-smmu-v3 SVA

源文件 `drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3-sva.c`，132-162 行：

`arm_smmu_mm_arch_invalidate_secondary_tlbs` 是 `arch_invalidate_secondary_tlbs` 回调的一个实现。它根据范围大小选择 `arm_smmu_tlb_inv_asid`（整 ASID 失效）或 `arm_smmu_tlb_inv_range_asid`（范围失效），再调 `arm_smmu_atc_inv_domain` 做 ATC 失效。全程同步，回调返回即设备侧失效完成。

此为现有机制可承载的同步设备侧 TLB 失效消费方，与需求中"回调返回即视为设备侧失效完成"的语义一致。但它不读取任何 per-CPU MMIO 读清除寄存器，不按 bit0 分支，不涉及 DT 资源发现。

## 2. 上游相关提交

### 2.1 本树已含的修复：范围上报 bug

本树已包含修复提交 `cb229d60aac38fabab1ae46bbdc74c251d4829e3`（"Fix mmu notifiers for range-based invalidates"），核实信息如下。

- 来源：stable-v6.6.88 回灌，对应 stable commit `4f687721a981a657aef002ffb8aa7329e1950974`。
- 上游 commit：`f7edb07ad7c66eab3dce57384f33b9799d579133`。
- 作者：Piotr Jaroszynski `<pjaroszynski@nvidia.com>`，与 lore 链接作者一致。
- 内容：修复 `__flush_tlb_range_op` 宏修改入参导致 `__flush_tlb_range_nosync` 中 `mmu_notifier_arch_invalidate_secondary_tlbs(mm, start, end)` 收到 `start == end` 空范围的问题。空范围恰好走了全失效路径，不引发正确性问题，但造成次优性能。
- 引入 bug 的原始提交：`6bbd42e2df8f`（"mmu_notifiers: call invalidate_range() when invalidating TLBs"）。

此修复仅纠正现有回调收到的地址范围参数，不涉及 per-CPU MMIO 读清除寄存器、bit0 条件分支、DT 资源发现，也不新增任何 mmu_notifier 钩子。与本需求所述机制无重叠。

## 3. 现有机制 vs 需求 对比

| 维度 | 现有 `arch_invalidate_secondary_tlbs` | 需求所述新机制 |
|---|---|---|
| 触发方式 | TLBI 路径固定调用，无条件 | TLBI 完成后读 32 位 per-CPU MMIO 读清除寄存器，按 bit0 条件触发 |
| 触发时序 | `flush_tlb_mm` 在 DSB 后；nosync 变体在完成 DSB 前 | 须在 TLBI 完成之后读取 MMIO，时序要求严格 |
| 回调身份 | 现有 `arch_invalidate_secondary_tlbs` 钩子 | 新增独立 mmu_notifier 钩子，与现有钩子并存 |
| CPU 亲和性 | 回调在发起 TLBI 的 CPU 上下文执行，但无 per-CPU MMIO 读取 | 仅发起 CPU 读取自身 MMIO 寄存器 |
| 资源发现 | 无 MMIO 资源，无 DT | 须通过 DT 发现并映射新增 MMIO 资源 |
| 回调语义 | 持 ptl 自旋锁，不可睡眠，同步完成 | 同步完成设备侧失效，回调返回即完成 |
| 批量语义 | 回调以 `mm`+`start`+`end` 为粒度，与 TLBI 软件包装对应 | 读取检查点粒度待硬件契约确认（见 ① 第 4 节） |
| 现有回调链 | 本身即现有回调 | 须保留现有回调链不变，不得修改或删除 |
| 配置控制 | `CONFIG_MMU_NOTIFIER` 已存在（bool，选择 INTERVAL_TREE）；无针对本硬件特性的独立开关 | 须新增独立硬件特性 Kconfig，默认关闭 |

关键差异有三。

第一，触发条件不同。现有机制无条件调用回调，需求要求先读 per-CPU MMIO 读清除寄存器再按 bit0 分支。现有代码无此读取与分支逻辑。

第二，插入时序不同。nosync 变体中现有回调在完成 DSB 之前触发，而需求要求 MMIO 读取在 TLBI 完成之后。新机制的读取点不能直接复用 nosync 回调点，须在完成 DSB 之后插入。`flush_tlb_mm` 的现有回调点（DSB 之后）在时序上与需求一致，但该点已有现有回调，新机制须与之并存而非替换。

第三，资源模型不同。现有机制无 MMIO 资源、无 DT 发现、无 per-CPU 区域。需求要求完整 DT 资源发现与映射流程。

批处理说明：现有 `arch_tlbbatch_add_pending`/`arch_tlbbatch_flush` 批处理路径延迟 DSB 到批量结束。该路径是否假设单一 mm 上下文，本调研不作断言，留待 ③ 架构分析与 ⑤ 阶段硬件契约一并确认。

## 4. 有界结论

### 4.1 等价实现查找结果

在以下已检查来源中，未找到与需求所述机制等价的实现：

- 本树 `arch/arm64/include/asm/tlbflush.h` 的 TLBI 通知路径（253-288、418-453 行）
- 本树 `mm/mmu_notifier.c` 的回调分发与注册逻辑（588-628 行）
- 本树 `drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3-sva.c` 的类比消费方（132-162 行）
- 本树 `include/linux/mmu_notifier.h` 的回调族定义（189-210 行）
- 上游修复 commit `f7edb07` 及其原始 bug 引入 commit `6bbd42e2df8f`
- BTM lore 镜像系列（类比参考）
- Arm DVM 文档（硬件类比参考）

此"未找到"结论受限于上述来源。本调研未穷举全仓库所有子系统、未检索未归档的社区补丁、未覆盖尚未公开的厂商实现。需求所述 per-CPU 32 位 MMIO 读清除寄存器、bit0 条件分支、新增独立钩子、DT 资源发现的完整组合，在已检查来源中无等价物。

### 4.2 现有代码状态

现有代码无证据表明存在缺陷。`cb229d60aac3` 修复的是范围上报参数问题，已在树上，属已修复状态。需求明确声明"并非修复现有代码缺陷"，本调研核实与此一致。

### 4.3 分级确认

① 需求描述暂定 Feature 分级。本调研支持该分级：

- 现有 `arch_invalidate_secondary_tlbs` 机制与需求所述机制在触发条件、插入时序、资源模型上均不相同，不构成等价实现，无 Backport 对象。
- 需新增钩子路径、MMIO 读取逻辑、bit0 分支、DT 资源发现，属从零设计实现，符合 Feature 特征。
- 未发现上游主线或社区已存在等价实现，不满足回退为 Backport 的条件。

分级确认为 **Feature**。

## 5. 未决项移交

以下事项不在本调研裁决范围，移交后续阶段：

### 5.1 移交 ③ 架构分析

- 新机制读取点的精确插入位置：`flush_tlb_mm` 的 DSB 后点在时序上符合需求，但 nosync 变体须另行设计完成检查点。具体插入方案待 ③ 阶段。
- 批处理路径（`arch_tlbbatch_*`）是否假设单一 mm 上下文：本调研不断言，待 ③ 阶段核实。
- 新钩子与现有 `arch_invalidate_secondary_tlbs` 的并存方式：二者是否共享订阅链、是否需要独立的 ops 字段，待 ③ 阶段设计。

### 5.2 移交硬件规格（Oracle / 用户）

- DT compatible 字符串、寄存器布局、每 CPU MMIO 区域与发起 CPU 的资源关联方式。
- 读清除寄存器的时序语义：状态累积方式、清除粒度、多 bit 语义。
- TLBI 完成与状态寄存器置位之间的 ordering 保证：是否需显式屏障。
- MMIO 物理地址（① 第 2 节第 10 条标注 TBD）。

### 5.3 移交 Consumer 驱动确认

- 实际 consumer 驱动身份待定。
- QEMU 无对应设备模型，端到端硬件验证不可行，软件层 mock 验证方案待 ⑤ 阶段。
