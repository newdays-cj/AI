本文为工作流④的初步方案对比，供 Oracle 技术审核参考，**不是已批准的最终设计，不授权编码实现**。方案 A 和方案 B 均为条件性策略草案，不构成已可行的定稿替代方案。两方案能否成立，取决于硬件规格输入；在硬件契约确认前，任一方案均不可判定为可行。Oracle 可行性审核已完成（见§10.1 Oracle 裁定及 Oracle 裁定附录），裁定 STOP BEFORE IMPLEMENTATION，触发 ③→① 技术回路。

源码引用相对于 `/home/chenjun/Git/OLK-6.6/`。源码事实与 Oracle 后续意见分别标注。已完成可行性审查，未执行代码测试或构建，不声称硬件契约或实现已通过验证。

核心需求回顾（`01-需求描述.md:26-39`）：发起用户 TLBI 的 CPU 在 TLBI 完成后，读取自身 32 位 per-CPU MMIO 读清除状态寄存器，按 bit0 条件触发携带目标 mm 和地址范围的新增 mmu_notifier 钩子。回调须同步完成设备侧失效，不得睡眠。现有 `mmu_notifier_arch_invalidate_secondary_tlbs` 回调链行为保持不变。新增 Kconfig 默认关闭。每 CPU 独立 MMIO 区域为暂定批准，待硬件规格确认。

现有代码无缺陷证据。本需求是新增机制，不是修复（`01-需求描述.md:17-22`）。

## 2. 源码核实基础

以下为本次对比直接依赖的源码事实，均经逐行读取核实。

**TLBI 路径完成模板**（`arch/arm64/include/asm/tlbflush.h:175-181`）：`DSB ISHST` 确保 prior 页表更新完成，`TLBI` 失效，`DSB ISH` 确保失效完成，kernel 映射还需 `ISB`。

**`flush_tlb_mm`**（同文件 253-263 行）：`dsb(ishst)` 后发 `aside1is` 和 KPTI 配对的 `__tlbi_user(aside1is)`，然后 `dsb(ish)`，最后调 `mmu_notifier_arch_invalidate_secondary_tlbs(mm, 0, -1UL)`。现有回调在完成 DSB 之后。

**`__flush_tlb_page_nosync`**（265-276 行）：`dsb(ishst)` 后发 `vale1is` 及 KPTI 配对，随后调 `mmu_notifier_arch_invalidate_secondary_tlbs`。无最终 DSB。包装器 `flush_tlb_page`（284-289 行）在 nosync 之后追加 `dsb(ish)`。

**`__flush_tlb_range_nosync`**（418-443 行）：超限回退 `flush_tlb_mm(mm)` 并返回（429-432 行）；普通分支 `dsb(ishst)` 后执行 `__flush_tlb_range_op` 宏循环，随后调 `mmu_notifier_arch_invalidate_secondary_tlbs(mm, start, end)`。无最终 DSB。包装器 `__flush_tlb_range`（445-453 行）追加 `dsb(ish)`。

**`__tlbi` 宏**（32-46 行）：单条 `__tlbi` 调用内部可能因 `ARM64_WORKAROUND_REPEAT_TLBI` 插入 `dsb ish` 和重复 `tlbi` 指令。KPTI 的 `__tlbi_user`（52-55 行）在 `arm64_kernel_unmapped_at_el0()` 时追加用户 ASID 失效。范围宏 `__flush_tlb_range_op`（363-396 行）按 scale/num 拆分循环。因此一个软件包装调用对应多条原始 TLBI 指令，内部还可能含中间 DSB。

**批处理路径**（291-330、500-504 行）：`arch_tlbbatch_should_defer` 在 `ARM64_WORKAROUND_REPEAT_TLBI` 时返回 false，否则 true。`arch_tlbbatch_add_pending` 调 `__flush_tlb_range_nosync` 发出 TLBI 但延迟 DSB。`arch_tlbbatch_flush` 仅 `dsb(ish)`，不带 mm/range 参数。`arch_flush_tlb_batched_pending`（312-315 行）调 `flush_tlb_mm(mm)`，注释 306-311 行明确：远端 CPU 上的 DSB 不能像本 CPU 那样保证此前 TLBI 完成。

**reclaim 批处理**（`mm/rmap.c:610-742`）：`tlb_ubc` 挂在 `current->tlb_ubc`，每任务一份。`set_tlb_ubc_flush_pending`（648-687 行）调 `arch_tlbbatch_add_pending(&tlb_ubc->arch, mm, start, end)`，传入当前 VMA 的 mm。`try_to_unmap_flush`（617-627 行）调 `arch_tlbbatch_flush` 即仅 `dsb(ish)`。`flush_tlb_batched_pending`（716-731 行）比较 pending/flushed 代数，不匹配时调 `arch_flush_tlb_batched_pending(mm)` 即整 mm 失效。`should_defer_flush`（693-699 行）检查 `TTU_BATCH_FLUSH` 标志和 `arch_tlbbatch_should_defer`。

**young-bit 路径**：`__ptep_clear_flush_young`（`arch/arm64/include/asm/pgtable.h:974-991`）清 young 后若 young 为真，调 `flush_tlb_page_nosync`，注释 980-987 行说明可省略尾部 DSB，完成窗口由下次上下文切换保证。`contpte_ptep_clear_flush_young`（`arch/arm64/mm/contpte.c:511-530`）对连续 PTE 块调 `__flush_tlb_range_nosync`，注释 519-522 行引用同样理由省略 DSB。两条路径均在无最终 DSB 的情况下返回，现有回调 `mmu_notifier_arch_invalidate_secondary_tlbs` 在 nosync 函数内部、完成 DSB 之前调用。pgtable.h 141 行注释也指出 `__ptep_clear_flush_young` 省略 DSB。

**arm64 批处理结构**（`arch/arm64/include/asm/tlbbatch.h:5-10`）：`struct arch_tlbflush_unmap_batch` 当前为空，注释说明硬件 shootdown 无需 IPI cpumask。无 mm、range、发起 CPU 或读清状态记录。

## 3. 两方案概述

### 3.1 方案 A：功能激活时就地完成

当 Kconfig 开启且硬件已启用时，在 per-mm 用户 nosync 路径（`flush_tlb_mm`、`__flush_tlb_page_nosync`、`__flush_tlb_range_nosync`）中，于目标 mm 和地址范围仍在调用栈可知的时机，就地完成 TLBI 发出、DSB、MMIO 读取和 bit0 条件通知。

Kconfig 关闭时，所有路径保持现有行为，无额外 MMIO 读取或回调。

关键设计要点：

1. 若批处理延迟与就地完成冲突，功能激活时使 `arch_tlbbatch_should_defer` 返回 false，强制每次 unmap 同步完成。是否需要如此取决于硬件是否支持跨操作状态合并，待确认。
2. 包装器（`flush_tlb_page`、`__flush_tlb_range`）在 nosync 之后追加的 `dsb(ish)` 不得引发重复 MMIO 读取。`__flush_tlb_range_nosync` 的超限回退分支（429-432 行调 `flush_tlb_mm`）也须避免重复读取。
3. 从首条相关 TLBI 到 DSB 再到 MMIO 读取的区间内，须固定发起 CPU 不可迁移。CPU 固定与本地 IRQ 排他是**两个独立关注点，非二选一**；必须在发出首条 TLBI 前建立保护，并覆盖完整 issue/DSB/read 区间，不能只在 DSB 后关 IRQ。读取并保存状态后恢复调用者原有 IRQ/preempt 状态，再遍历回调；不额外扩大回调的禁 IRQ 区间。具体机制仍须结合配置和硬件嵌套契约设计，关 IRQ 不能排除 NMI/更高 EL 干扰。
4. 须防止 IRQ 重入在 TLBI 与 DSB 与读取之间消费同一 per-CPU 状态，以及防止回调自身触发 TLBI 导致嵌套状态消费。
5. 旧回调保持独立于 bit0、每逻辑失效一次及正确参数；激活路径是否允许将其 preDSB 时序加强为 postDSB 是未决兼容性问题，不能宣称精确时序已保留。配置关闭时保持现有路径。

### 3.2 方案 B：保留延迟并记录元数据

保留现有延迟完成模型（nosync 发出 TLBI 但延迟 DSB 到包装器或批末），在发出时记录每个目标的 mm、地址范围和发起 CPU，在延迟完成点执行 DSB 后读取对应发起 CPU 的 MMIO 并按 bit0 条件通知。

关键设计要点：

1. `arch_tlbflush_unmap_batch` 当前为空。仅加一个 mm 指针不充分，因为 reclaim 批处理可跨多个 mm（rmap 遍历多个 folio 的映射 VMA，每个 VMA 的 `vm_mm` 可能不同）。
2. 须在发出时保存多组 (mm, start, end, issuing_cpu) 记录，定义记录容量、溢出处理和合并策略。
3. mm 引用须在通知前保持有效。mm 可能在发出与延迟完成之间退出，须引用计数管理。
4. 发起 CPU 与完成 CPU 可能不同（rmap 路径含 `cond_resched`，任务可调度迁移）。需求要求仅发起 CPU 读取自身 MMIO，跨 CPU 读取不被允许。
5. young-bit 路径省略 DSB，完成延至下次上下文切换。延迟记录的元数据须存活到该时刻。
6. 内存分配受原子上下文约束。`set_tlb_ubc_flush_pending` 在 PTL 自旋锁下调用，不可睡眠分配。

## 4. 共同硬件前提

以下前提对方案 A 和 B 均适用。任一前提不满足，两方案均不可行。这些前提当前未经硬件规格确认，不构成已验证的保证。

1. **DT 兼容与 CPU 资源关联**：须有实际的 DT compatible 字符串、寄存器端序、偏移布局和 per-CPU MMIO 区域与逻辑 CPU 的资源关联方式。物理地址可在后续 DT 中给出，不是编译阻断因素。不因当前未知确切数值就推断协议缺失。
2. **TLBI 完成时状态可见性**：硬件须保证 TLBI 完成后状态位已对 MMIO 可见，或定义所需显式屏障。CPU 侧 `dsb(ish)` 完成语义不自动证明设备状态已就绪。
3. **KPTI/范围/workaround 原始操作的状态合并**：一个软件包装调用（如 `__flush_tlb_range_nosync`）内部含多条原始 TLBI 指令：主体 TLBI、KPTI 配对、范围循环拆分、repeat workaround 的内部 DSB 加重复。硬件须将这些原始操作的状态合并为一次可读取的检查点状态。方案 A 的检查点为每次包装调用，方案 B 的检查点为延迟完成点，后者合并跨度更大。
4. **读清除原子性与归属**：读清除寄存器读取即清除，不可重复读。须明确 IRQ、其他 CPU 或广播场景下的读取归属，防止误清或归属错配。
5. **全 CPU 硬件启用初始化**：所有 CPU 的 MMIO 区域须在首次受约束 TLBI 前完成映射和初始化。部分 CPU 映射失败时不得宣称全局已启用。
6. **回调原子性**：新增钩子回调须与现有 `arch_invalidate_secondary_tlbs` 一致，不可睡眠，同步完成设备失效。实际 consumer 驱动身份未知，不虚构 compatible 或占位订阅者。
7. **QEMU 不可端到端验证**：通用 QEMU 无对应设备模型，端到端硬件行为验证不可行。软件层 mock 验证可作为替代手段，但不证明硬件行为正确。

两方案均不得将本地 `dsb(ish)` 等同于远端设备完成保证。`dsb(ish)` 保证 inner shareable 域内 CPU 侧 TLB 失效完成，不保证设备侧 TLB 或 IOMMU TLB 已失效。bit0 状态读取是**决策点**——决定是否请求设备侧失效（bit0==1 请求，bit0==0 不请求），不是设备完成检查或设备已完成的证明。设备侧失效完成由回调协议建立：回调返回即视为设备侧失效同步完成（`01-需求描述.md:34-35`）。

## 5. 正确性复杂度对比

| 维度 | 方案 A | 方案 B |
|---|---|---|
| mm/range 归属 | 调用栈中 mm 和 range 直接可知，无需跨时间恢复 | 须在发出时记录，完成时恢复；多 mm 场景须逐一匹配 |
| CPU 亲和性 | 发起 CPU 就地完成读取，**在 CPU 已固定的前提下**满足"仅发起 CPU 读取自身 MMIO"；须显式 `preempt_disable` 保证，非天然成立 | 发起 CPU 与完成 CPU 可能不同；rmap 含 cond_resched 可迁移；须额外机制保证发起 CPU 读取 |
| IRQ/嵌套 | 须防止 TLBI 与 DSB 与读取之间 IRQ 重入消费 per-CPU 状态；区间较短 | 区间更长，须覆盖迁移、hotplug 和嵌套；任务数据与 per-CPU 状态须可关联 |
| 批处理并发补刷 | `flush_tlb_batched_pending` 调 `flush_tlb_mm`，A 在该路径就地完成，发起 CPU 可知 | 该路径可能在远端 CPU 执行，原批次发起 CPU 未知，无法满足 CPU 亲和性要求 |
| 回调语义保留 | 保留旧回调条件、次数和参数；激活路径时序变化须另行裁决 | 同样须证明旧回调契约，且新增延迟记录不改变旧路径义务 |
| 状态归属唯一性 | 每次包装调用一个检查点，mm/range 与读取一一对应 | 多条延迟记录累积到一个完成点，须硬件保证可用一份待完成集合解释此次读值 |

方案 A 的正确性复杂度集中在局部区间内的 CPU 固定、IRQ 防护和嵌套防护。方案 B 的正确性复杂度延伸到跨调度、跨 CPU 的元数据一致性，且 reclaim 批处理的并发补刷路径（`flush_tlb_batched_pending` 在远端 CPU 调 `flush_tlb_mm`）在当前代码结构下无法恢复原批次各发起 CPU 身份——这是**成本与缺失证明**，不构成对未来 B 的绝对不可能判定（未来硬件契约或设计创新可能提供解法），但当前无证据表明 B 可行。`arch_flush_tlb_batched_pending` 的注释（`tlbflush.h:306-311`）已明确远端 DSB 不保证此前 TLBI 完成，方案 B 在此路径上面临更深归属缺口。

`preempt_disable`（CPU 固定）与 `local_irq_save`（IRQ 屏蔽）是两个独立关注点，须在 issue/DSB/read 区间同时满足（见§3.1 第 3 点），非二选一。关抢占不等于禁 IRQ 重入；关 IRQ 的长同步回调对延迟影响须评估。回调遍历须在 IRQ/preempt 恢复后执行。

## 6. 性能对比

| 维度 | 方案 A | 方案 B |
|---|---|---|
| 批处理延迟优化 | 若禁用 `arch_tlbbatch_should_defer`，每次 unmap 同步完成 DSB，失去合批收益 | 保留延迟 DSB 的合批收益 |
| MMIO 读取频次 | 每次包装调用一次读取；频次较高 | 每次延迟完成点一次读取；频次较低，但须硬件支持跨操作状态合并 |
| 热路径开销 | 增加 DSB、MMIO 总线延迟和同步回调耗时 | 增加记录记账、mm 引用操作和完成路径耦合 |
| young-bit 优化 | 为覆盖用户范围，A 必须就地完成，牺牲原省略 DSB 优化，不得排除 | young-bit 延迟到上下文切换，记录元数据须存活更久，延迟窗口更大 |
| PTL 持有时间 | DSB 和 MMIO 读取延长 PTL 持有或禁抢占/禁 IRQ 区间 | 记录操作在 PTL 下进行，DSB 延迟到批末或上下文切换，PTL 持有时间影响较小 |

方案 A 在性能上的主要代价是失去 reclaim 批处理的 DSB 合并优化。`arch_tlbbatch_should_defer` 在 `ARM64_WORKAROUND_REPEAT_TLBI` 时已返回 false，说明该优化在某些硬件上已被放弃，方案 A 在功能激活时的行为与此一致。但功能激活时对所有平台禁用合批的影响须评估。

方案 B 保留合批收益，但记录多组 (mm, range, CPU) 的记账开销、mm 引用计数操作和完成路径的复杂耦合可能抵消部分收益。若硬件不支持跨操作状态合并，方案 B 的单次读取无法覆盖整个批次，可能退化为逐条读取，反而比 A 更慢。

## 7. mm 生命周期对比

| 维度 | 方案 A | 方案 B |
|---|---|---|
| mm 引用有效性 | 调用栈中 mm 经由 vma 或 mmu_gather 持有引用，就地完成时引用必然有效 | 记录的 mm 须在延迟完成前保持有效；mm 退出与延迟完成之间存在竞态 |
| 引用管理开销 | 无额外引用管理 | 须对每个记录的 mm 做 `mmgrab`/`mmdrop` 或等效引用管理，定义容量与溢出 |
| 多 mm 场景 | 不涉及跨时间多 mm 恢复 | rmap 遍历可跨多个 mm（KSM 或共享页映射），每条记录可能对应不同 mm |
| young-bit 延迟 | 须明确处理，见第 9 节 | young-bit 元数据须存活到上下文切换，延迟最长；mm 在此期间可能退出 |

方案 A 在 mm 生命周期上无明显缺口：调用栈保证 mm 有效，就地完成后无需持有引用。方案 B 的核心难点在于延迟期间 mm 可能被销毁。`mmu_notifier_unregister` 以 SRCU 等待回调结束（`mm/mmu_notifier.c:802-850`），但不自动排空延迟记录中的 mm 引用。须定义引用获取、释放、队列容量和溢出处理，且全部在不可睡眠的原子上下文中完成。

## 8. 可测试性对比

| 维度 | 方案 A | 方案 B |
|---|---|---|
| 就地路径验证 | 每条 TLBI 路径自包含，可逐路径验证 MMIO 读取在 DSB 之后、发起 CPU 一致、mm/range 正确 | 须验证延迟记录与实际发出 TLBI 的一一对应，跨调度/迁移后一致性 |
| 批处理路径验证 | 禁用合批后路径简化，可逐 unmap 验证 | 须验证多 mm 记录、代数推进、并发补刷和溢出处理 |
| mock 设备验证 | 可 mock MMIO 寄存器，验证 bit0 分支和回调参数 | 可 mock，但延迟完成和跨 CPU 归属验证更复杂 |
| 端到端硬件验证 | 通用 QEMU 不可行，两方案同等受限 | 同左 |

两方案的软件层 mock 验证均可进行，但端到端硬件行为验证在通用 QEMU 上不可行，须待硬件规格和平台到位。方案 A 的验证维度较少，每条路径可独立验证。方案 B 须额外验证延迟状态一致性和跨 CPU 归属正确性，验证复杂度显著更高。

## 9. 批处理路径与 young-bit 路径的显式覆盖

两方案均须覆盖以下路径，不得静默排除。

**reclaim 批处理路径**：

方案 A：功能激活时使 `arch_tlbbatch_should_defer` 返回 false，`should_defer_flush`（`rmap.c:693-699`）随之返回 false。此时 reclaim 路径**跳过** `set_tlb_ubc_flush_pending`/`arch_tlbbatch_add_pending`，改走同步 `flush_tlb_range`（或 `ptep_clear_flush`）分支（`rmap.c:1791-1794`、`2154-2168`）。`arch_tlbbatch_add_pending` **不被调用**，nosync TLBI 不经批处理路径发出。若无遗留 pending 批次，`try_to_unmap_flush` 在 `flush_required == false` 时直接返回，不调用架构批末 DSB（`rmap.c:617-626`）；首次激活前仍须定义遗留批次排空。`flush_tlb_batched_pending` 的并发补刷路径调 `flush_tlb_mm`，A 在该路径就地完成。

方案 B：保留 `arch_tlbbatch_should_defer` 返回 true。须在 `arch_tlbbatch_add_pending` 中记录每组 (mm, start, end, issuing_cpu)。`arch_tlbbatch_flush` 的 `dsb(ish)` 之后，须按记录的各发起 CPU 读取对应 MMIO。但 `arch_tlbbatch_flush` 无 mm/range/CPU 参数，`arch_tlbflush_unmap_batch` 为空，须扩展结构。reclaim 路径含 `cond_resched`（`rmap.c` rmap_walk 系列），任务可迁移，完成 CPU 可能不是发出 CPU。`flush_tlb_batched_pending` 的并发补刷在远端 CPU 调 `flush_tlb_mm`，原批次发起 CPU 不可恢复。

**young-bit 路径**：

`__ptep_clear_flush_young`（`pgtable.h:974-991`）调 `flush_tlb_page_nosync`，省略 DSB，完成由下次上下文切换保证。`contpte_ptep_clear_flush_young`（`contpte.c:511-530`）调 `__flush_tlb_range_nosync`，同样省略 DSB。两条路径均无最终 DSB 检查点。

方案 A：功能激活时**必须**在 young-bit 路径建立就地完成检查点。young-bit 路径属用户地址空间 TLBI，用户诉求覆盖全部用户地址空间失效，排除该路径等于改变用户范围，不在授权内。建立检查点会改变现有省略 DSB 的优化，`pgtable.h:980-987` 注释所述的容错窗口不再适用，须评估对页老化性能的影响。不得以"以后处理"为由静默跳过该路径的设备侧通知义务。

方案 B：young-bit 路径的 TLBI 在 nosync 函数中发出，现有回调已执行。延迟完成到下次上下文切换。方案 B 须在发出时记录元数据，且元数据须存活到上下文切换时的完成检查点。这一延迟窗口远长于 reclaim 批末，mm 引用和 per-CPU 状态归属的管理复杂度更高。上下文切换路径（`arch/arm64/kernel/process.c:542-548`）在可能迁移前完成本 CPU pending maintenance，但不提供本功能所需的原 CPU MMIO 读取或元数据归属。

**full-mm 回退路径**：

`__flush_tlb_range_nosync` 在超限时回退 `flush_tlb_mm(mm)`（429-432 行），`flush_tlb_mm` 自带 DSB 和现有回调。方案 A 须确保该回退路径不产生重复 MMIO 读取。方案 B 须确保该回退路径的元数据被正确记录或由 `flush_tlb_mm` 的就地完成覆盖。

**不得以全设备通知替代所需范围通知**：两方案的新增钩子均须携带与触发 TLBI 对应的目标 mm 和地址范围，不得在无法精确归属时退化为通知设备全量失效。

## 10. 暂定倾向与未决项

### 10.1 暂定倾向

初步倾向方案 A，理由如下：

1. mm 和 range 在调用栈中直接可知，无需跨时间恢复，归属更简单。
2. 发起 CPU 就地完成读取，在 CPU 已固定（`preempt_disable`）的前提下满足 CPU 亲和性要求。
3. mm 引用在调用栈中有效，无延迟期间的生命周期管理问题。
4. 验证维度较少，每条路径可独立验证。

此倾向以硬件支持 per-operation 状态合并为前提。方案 A 的检查点为每次包装调用，若硬件能将一次包装调用内的全部原始 TLBI 指令（KPTI 配对、范围循环、repeat workaround）的状态合并为一次可读取的检查点状态，则 A 的归属模型成立。若硬件仅支持更大粒度的合并（如跨操作累积到某个全局完成点），则 A 的每次包装调用读取可能无法获取有效状态，须重新评估。

方案 B 在硬件支持跨操作状态合并时有理论优势（减少读取频次），但其跨 CPU、跨调度的元数据一致性和 mm 生命周期管理的正确性复杂度显著高于 A。reclaim 并发补刷路径中发起 CPU 不可恢复的问题尤为关键——当前无证明 B 可行，但亦不排除未来硬件契约或设计创新提供解法的可能。

**Oracle 裁定**（session `ses_eb66e2c17ffeRIIArLrXY4nbjV`，高置信度）：两方案均未选定为已可行的最终方案。条件性方向 A 的安全约束（见 Oracle 裁定附录）与方向 B 的元数据保留约束均为待硬件契约确认的设计方向，非已批准方案。最终设计须经 ③→① 回路补齐硬件契约后定稿。

### 10.2 未决项

以下未决项须在硬件规格输入和 Oracle 审核后才能定论：

1. 硬件状态合并粒度：per-operation（每次包装调用）还是 per-batch（延迟完成点）还是 per-raw-instruction。
2. 读清除寄存器的状态累积和清除语义：多 bit 是否有效、清除粒度。
3. TLBI 完成与状态置位之间的 ordering 保证。
4. DT compatible、寄存器布局、per-CPU 资源关联方式。
5. 方案 A 的 IRQ/preempt 机制选择。
6. 方案 A 在 young-bit 路径建立就地完成检查点的实现与性能影响；不包含排除该用户 TLBI 路径的选项。
7. 方案 B 的 mm 引用管理、记录容量和溢出处理在原子上下文中的可行性。
8. 方案 B 在 reclaim 并发补刷路径中恢复发起 CPU 身份的可行性。
9. 实际 consumer 驱动身份及其设备侧同步完成能力。

任一方案在以上未决项确认前均不可判定为可行。需求可能须先获取硬件输入，才能证明任一方案可行。若硬件不支持 per-operation 状态合并，方案 A 的暂定倾向须重新评估。

## 11. Oracle 裁定附录

Oracle 可行性审核 session `ses_eb66e2c17ffeRIIArLrXY4nbjV` 已完成，高置信度。

### 11.1 裁定结论

**STOP BEFORE IMPLEMENTATION**。触发工作流 ③→① 技术回路：架构分析揭示需求所需硬件契约缺口，非需求不可实现。用户人工确认门禁维持自动预批准，但技术审核与测试仍强制执行。最终设计未批准。

### 11.2 条件性方向 A（安全约束，非已批准方案）

- 功能激活时，用户 nosync 操作就地同步完成，此时目标 mm/range 仍在调用栈可知。
- 功能激活时禁用 reclaim 延迟合批（`arch_tlbbatch_should_defer` 返回 false）。
- 仅在硬件确认粘性状态累积（sticky aggregate）覆盖 KPTI/range/repeat 全部原始操作时，才保证每个逻辑操作仅一次检查点读取。
- 在 issue/DSB/read 区间内 pin CPU 并屏蔽本地 IRQ；读取状态后恢复 IRQ/preempt，再遍历回调。
- 现有回调无条件调用一次（独立于 bit0），新回调仅在 bit0==1 时调用。
- 现有 page/range 回调的 preDSB 时序**可能**需要在功能激活时加强为 postDSB——这是未决兼容性边界，**不假装能保留精确时序，也不授权静默改变现有语义**。
- 回调不在 IRQ 屏蔽下持有（除非调用方进入时已如此）。

### 11.3 条件性方向 B

- 保留延迟模型，记录多组 (mm, range, issuing_CPU) 元数据，须满足生命周期与原子内存约束。
- 不假设单一 mm——reclaim 批处理可跨多个 mm。
- 当前无证明 B 可行，但不排除未来硬件契约或设计创新提供解法。

### 11.4 缺失的硬件契约（③→① 回路触发点）

以下契约缺口是 STOP 的根因，非物理地址未知（物理地址可在后续 DT 中给出，非唯一阻断因素）：

1. eligible/noneligible TLBI 事件源定义，及粘性状态累积范围——含广播/全局/reserved ASID 场景。
2. 状态可见性：同 CPU DSB 后是否可见，或须厂商规定的同步操作。
3. 寄存器 offset/端序/reset/读清除原子性，及 bit1+ 的所有权与语义。
4. 本地 IRQ 与 NMI/更高 EL 生产者的可达性与序列化。
5. CPU-资源 DT ABI：init/hotplug/quiescence 的文档化协议。
6. fail-closed consumer 协议：非睡眠同步失效及失败处理。

不虚构 compatible 字符串、stub notifier 或驱动骨架。
