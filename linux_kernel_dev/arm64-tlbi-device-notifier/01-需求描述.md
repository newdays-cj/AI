# 01 需求描述：arm64 TLBI 设备通知

## 需求编号

`arm64-tlbi-device-notifier`

## 阶段

Feature。用户已补充寄存器与 SMMU 消费方约束，本轮进入详细设计和测试设计。此前 Oracle STOP 和 Momus 文档交接批准是历史结论，不代表本轮设计已获批准；内核实现仍未开始。

---

## 1. 需求背景

arm64 在执行用户地址空间 TLB 失效（TLBI）时，需要把失效动作同步传递到挂载在同一地址空间上的设备，让设备侧的 TLB（或 IOMMU TLB）一并失效。

代码核实结论（`arch/arm64/include/asm/tlbflush.h`）：

- 内核已有 `mmu_notifier_arch_invalidate_secondary_tlbs` 通知路径：`flush_tlb_mm` 在 `dsb(ish)` 完成后调用该通知；`__flush_tlb_page_nosync` 与 `__flush_tlb_range_nosync` 在最终 `dsb(ish)` 之前调用该通知。
- 未发现本需求所述机制：基于 32 位 per-CPU MMIO 读清除寄存器、按 bit0 条件触发的新增 mmu_notifier 钩子。

本需求是在已有通知路径之外新增一条按 bit0 条件触发的设备侧同步失效路径，并非修复现有代码缺陷，也不声称现有代码存在过期映射残留问题。

## 2. 原始诉求

在 arm64 用户地址空间 TLBI 路径中新增 mmu_notifier 钩子，触发规则如下：

1. 仅覆盖 arm64 用户地址空间失效，内核地址空间失效不在范围内。
2. 仅由发起 TLBI 的 CPU 执行后续动作，不跨 CPU。
3. 发起 CPU 等待 TLBI 完成后，读取该 CPU 对应的 32 位小端 MMIO 寄存器。用户确认本次逻辑 TLBI 的 bit0 状态能够累积，发起 CPU 完成 `dsb(ish)` 后可直接读取，无需额外硬件同步；读取清除整个寄存器。
4. 根据寄存器 bit0 取值分支：
   - bit0 == 1：调用新的 mmu_notifier 钩子。
   - bit0 == 0：不调用新钩子。
5. 新 notifier 关联目标 mm（进程地址空间）和地址范围。
6. 钩子回调在设备侧同步完成设备 TLB 失效，回调返回即视为设备侧失效完成。
7. 用户最新确认：`bit0` 只反映 SMMU TLB，不反映设备 ATC。功能就绪时只对 SMMU TLB 软件刷新应用条件判断，ATC 仍按既有 ATS/master 等条件处理，不能随 `bit0 == 0` 一并跳过。关闭/不支持时保留旧路径，其他订阅者及 release/free 生命周期不变。此前“仅新槽复用整个 TLB+ATC 回调”的提案失效；当前选定职责拆分，避免重复 TLB 不等于禁止独立 ATC 回调。
8. 新增 DT 资源解析和映射；使用独立 DT 节点，其中 `reg` 数组列出各 CPU 寄存器。
9. 本轮先按每 CPU 独立的 32 位小端寄存器设计，读取整个寄存器并清除整个寄存器。
10. 板级物理地址待定，后续由 DT 提供；CPU 与 `reg` 的关联属性需要软件设计，不预设数组下标就是 Linux CPU 编号。
11. 用户已选择推荐的职责拆分方向：仅条件化软件 SMMU TLB，独立处理 ATC，主 TLB 完成早于 ATC，关闭/不支持时保留原合并路径。不再把 A/B 留给用户选择。软件落实方案见 05 §7–§8：同一订阅 new=TLB-only、old=ATC-only，单 SRCU 逐项 new→old，允许正交双槽并保留 range_start/end 排斥；这些是软件决策，不是用户逐项指定的 API，也不是硬件前提成立的证明。
12. 用户最新补充：本轮先按 bit1–bit31 为保留位、寄存器没有其他读取消费者处理。因此整寄存器读清不存在清除其他功能有效位的已知归属冲突；这是当前规格约定，不推导并发置位与读清的优先级，也不预设后续位用途不变。

## 3. 功能目标

| 编号 | 目标 | 备注 |
|---|---|---|
| F-1 | 仅 arm64 用户地址空间 TLBI 路径接入新通知机制 | 内核地址空间不在范围 |
| F-2 | 发起 CPU 在 TLBI 完成后读取 32 位 MMIO 读清除寄存器 | 读清除语义，多余读取会丢失状态 |
| F-3 | bit0 == 1 触发新 mmu_notifier 钩子，bit0 == 0 不触发 | bit0 为唯一判定位 |
| F-4 | 新钩子携带目标 mm 和地址范围 | 与触发 TLBI 的目标一致 |
| F-5 | 钩子回调在设备侧同步完成 TLB 失效 | 同步语义，回调返回即完成 |
| F-6 | 就绪时仅 SMMU TLB 软件刷新由 bit0 控制；ATC 保留独立处理义务 | 不全局屏蔽旧链，不重复 TLB，不漏 ATC |
| F-7 | 通过独立 DT 节点与 reg 数组发现各 CPU 寄存器 | CPU 关联属性与匹配标识待设计 |
| F-8 | 新增独立 Kconfig 控制，默认关闭（项目工作流约束） | 关闭时不引入额外 MMIO 读取/回调，保留现有 TLBI 通知语义 |
| F-9 | 本轮每 CPU 一个独立 32 位小端读清寄存器 | 整寄存器读清；板级地址待提供 |

## 4. 约束条件

- 架构：仅 arm64。
- 失效范围：仅用户地址空间 TLBI，不含内核地址空间。
- CPU 亲和性：仅发起 TLBI 的 CPU 读取自身 MMIO 寄存器，不跨 CPU 读取。
- 寄存器宽度和端序：32 位小端，bit0 为判定位。
- 读清除语义：整个寄存器读清。每个经设计确定的完成检查点只读取一次，不允许调试等额外破坏性读取。本次逻辑 TLBI 序列中的 bit0 可累积，不预设每条原始 TLBI 指令对应一次读取；这不自动证明并发读清与新置位的原子优先级。
- 软件包装：现有 TLBI 软件包装（如 `flush_tlb_mm`/`flush_tlb_page`/`flush_tlb_range` 等）内部可能包含多条原始 TLBI 指令，含 KPTI 配对的 `__tlbi_user` 以及 `ARM64_WORKAROUND_REPEAT_TLBI` 等工作绕过；用户未批准确切的原始指令计数，"一次读取"以设计确定的完成检查点为准，不以原始指令计数为准。
- 时序：MMIO 读取必须发生在发起 CPU 的完成 `dsb(ish)` 之后。用户已确认此时状态可读，无需额外硬件同步。
- 兼容性：SMMUv3 SVA 的软件 TLB 失效不重复走新旧路径；ATC 独立于 bit0 判断，需在相应主 TLB 失效完成后执行。旧链继续服务其他订阅者。回调拆分、跨链顺序及激活路径 pre/post-DSB 时序须在详细设计中明确，不得沿用整个回调被条件跳过的旧方案。
- 配置（项目工作流约束，非用户原始诉求引用）：新增 Kconfig 选项默认关闭；关闭时不引入额外 MMIO 读取/回调，并保留现有 TLBI 通知语义。本项为工作流 `需求开发.md` ⑦ 编码原则"独立 Kconfig 控制"的落实要求，不作为用户对硬件行为的原始陈述。
- 平台依赖：独立 DT 节点与每 CPU `reg` 项已确定。匹配标识、CPU 关联属性和验证规则属于本轮软件接口草案；具体板级地址后续提供。
- 硬件依赖：通用 QEMU 缺少对应设备模型，端到端硬件行为验证无法在通用 QEMU 中进行；软件层验证或 mock 设备测试仍可行。

## 5. 验收标准

### 5.1 已明确的验收项

| 编号 | 验收点 | 判定方法 |
|---|---|---|
| AC-1 | bit0 == 1 调用新钩子，bit0 == 0 不调用 | 分支覆盖 |
| AC-2 | 新钩子携带的 mm 和地址范围与触发 TLBI 的目标一致 | 参数核对 |
| AC-3 | MMIO 读取发生在 TLBI 完成之后 | 时序核对 |
| AC-4 | MMIO 读取由发起 TLBI 的同一 CPU 执行 | CPU 亲和性核对 |
| AC-5 | 每个经设计确定的完成检查点只读取一次状态寄存器，无额外破坏性读取 | 读取次数核对 |
| AC-6 | 就绪时 bit0=0 不发 SMMU 软件 TLBI，但仍处理必要 ATC；bit0=1 完成相应 TLB 后处理 ATC；旧平台和其他订阅者不被屏蔽 | 分别观察 TLB/ATC 次数、顺序、范围及生命周期 |
| AC-7 | 新 Kconfig 默认关闭，关闭时不引入额外 MMIO 读取/回调，并保留现有 TLBI 通知语义 | 配置核对 |

### 5.2 待定验收项（需硬件规格明确后再细化）

以下验收项依赖硬件规格输入，当前仅作为占位，不构成已批准的验收标准：

- 用户确认本次逻辑 TLBI 的累计状态可读；具体检查点、KPTI/范围拆分和重复 workaround 的一次读取覆盖规则须在详细设计落实。
- 初始化时序保证：MMIO 区域映射与首次 TLBI 之间的 ordering。
- CPU 热插拔场景：热插拔下的 MMIO 区域生命周期与 TLBI 路径正确性。

## 6. 待解决问题（未决项）

以下均为未确认项。在硬件规格或上游调研结果输入前，不得作为已批准的设计假设使用。这些条目不是已批准的猜测。

### 6.1 硬件规格未决

- 32 位、小端、整个寄存器读清、累计 bit0、DSB 后无需额外同步均已确认，不再列为待确认项。
- CPU 与 reg 的关联、4 字节资源从偏移 0 读取及匹配标识将作为软件接口草案提出，不冒充现成厂商 ABI；板级物理地址仍待提供。
- 已确认本轮 bit1–bit31 暂为保留位、没有其他读取消费者，不再将寄存器读取所有权列为阻塞。哪些非用户或嵌套 TLBI 会产生置位、NMI/更高 EL 的事件影响、状态覆盖哪些 SMMU，以及置位与读清的并发优先级仍是独立平台条件。
- CPU 热插拔/掉电后的可访问性、复位状态、首次启用前积存状态的处理需设计和平台约定；不能通过额外试读清零掩盖状态归属问题。

### 6.2 Consumer 驱动与集成边界

- 消费方为 ARM SMMUv3 SVA。现有合并函数不能直接作为 bit0 条件槽；05 已明确共享范围规范化、TLB-only、ATC-only、legacy 合并函数和对应 ops/注册规则，保留各自功能及生命周期。尚无代码实现或运行验证。
- 现有函数的 CMD_SYNC 等待、错误返回及超时策略需按源码核实；复用现有行为不等于保证硬件故障时也必然成功，不擅自新增 panic、重试或改变全驱动错误策略。
- 功能声明存在但资源解析/映射失败时如何禁止错误进入条件路径、以及多 SMMU 的适用范围，属于详细设计内容，不能把初始化失败当作 bit0 为 0。
- 通用 QEMU 缺少对应设备模型：无法在通用 QEMU 中进行端到端硬件行为验证；软件层验证或 mock 设备测试仍可行。

### 6.3 平台验证未决

- 无提供的硬件规格文档：真实硬件上的行为无法核对。
- 无提供的平台基线：无法在真实硬件上执行端到端验证。软件层验证或 mock 设备测试仍可作为替代手段，但端到端硬件行为验证需待硬件规格/平台到位。

## 7. 需求分级及判定理由

### 7.1 分级

**Feature**（新特性开发）

### 7.2 判定理由

- 内核已有 `mmu_notifier_arch_invalidate_secondary_tlbs` 通知路径，但未发现本需求所述基于 32 位 per-CPU MMIO 读清除寄存器、按 bit0 条件触发的新增 mmu_notifier 钩子机制（代码核实见第 1 节）。
- 需新增 mmu_notifier 钩子路径，涉及 arm64 TLBI 指令语义、MMIO 读清除时序、mmu_notifier 回调链三处子系统交互，属从零设计实现。
- 触发路径跨架构代码、设备驱动注册、DT 资源解析三个维度，不具备 Backport 或 Bugfix 的条件。

### 7.3 分级依据与范围

本分级经 ② 有界调研支持（已检索权威来源样本中未识别到等价方案，不构成全局不存在证明）。05、06 和矩阵已按选定拆分方向完成软件设计同步；旧 Oracle 结论不能代替运行或硬件验证。分级维持 Feature。
