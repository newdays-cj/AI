# 03 架构分析：arm64 TLBI 设备通知

## 1. 定位、证据与边界

本文为工作流③的源码架构分析，供④方案对比使用，**不是⑤可直接编码的详细设计，也不授权生产代码占位实现**。依据 `01-需求描述.md:26-67`：发起用户 TLBI 的 CPU 在完成后，单次读取自身 32 位 read-clear MMIO；bit0 为 1 才调用携带目标 mm/range 的新增回调；回调返回代表设备失效同步完成。每 CPU 独立区域仍为暂定；地址、绑定和状态时序未定。保留全部已有回调及配置关闭时行为。

除明确标注“建议/待定”外，下文事实来自当前工作树源码。源码引用相对于 `/home/chenjun/Git/OLK-6.6/`；需求、知识库引用相对于本文目录。本文成文于 Oracle 可行性审核返回之前；Oracle 后续裁定（STOP BEFORE IMPLEMENTATION，触发 ③→① 技术回路，详见 `00-进度与阻塞.md` 及 `04-方案对比.md` Oracle 裁定附录）与本文缺口分析方向一致。本文不作上游等价方案、测试通过或最终审核通过声明。

知识库基线为 `kb/OLK-6.6/arch/arm64/mm/overview.json:2-20,21-63,233-275,408-449`：扫描 24 个文件，列出 contpte API、初始化入口和并发统计。**它不是正确性证明**：扫描范围不含 `arch/arm64/include/asm/` 和通用 `mm/`；签名含省略号，`keyStructures` 为空，构建列表也不完整。实际 Makefile 的常驻目标及条件目标见 `arch/arm64/mm/Makefile:2-18`；下列关键结论均回到源码核对，不能由知识库的锁/屏障计数推出。

范围限定为有目标用户 mm 的 Stage-1 失效。全局/内核失效、ASID 分配器全刷、Stage-2 不接入新功能；不能因为底层宏共享就给所有 `__tlbi` 加钩子。证据：全刷 `tlbflush.h:237-251`、内核范围/页表 `:466-498`、共享 Stage-2 宏 `:398-399`（本段文件为 `arch/arm64/include/asm/tlbflush.h`）。缺少本新增机制**不意味着现有内核有 bug**，也不改变需求的暂定 Feature 属性（`01-需求描述.md:17-22,115-129`）。

## 2. 现有静态接口与数据归属

### 2.1 arm64 失效接口

以下签名均为现有接口，通常是头文件内联函数；不是拟新增 API。

| 接口 | 现有契约与证据 |
|---|---|
| `void flush_tlb_mm(struct mm_struct *mm)` | 发出 ASID 失效，最终 `dsb(ish)` 后通知已有 secondary-TLB 回调，范围为 `(0, -1UL)`；`arch/arm64/include/asm/tlbflush.h:253-263`。 |
| `void __flush_tlb_page_nosync(struct mm_struct *mm, unsigned long uaddr)` | 发出页失效，按页对齐通知已有回调，无最终 DSB；同文件 `:265-276`。 |
| `void flush_tlb_page_nosync(struct vm_area_struct *vma, unsigned long uaddr)` / `void flush_tlb_page(struct vm_area_struct *vma, unsigned long uaddr)` | 前者转交 `vma->vm_mm`，后者另加最终 DSB；同文件 `:278-289`。 |
| `void __flush_tlb_range_nosync(struct mm_struct *mm, unsigned long start, unsigned long end, unsigned long stride, bool last_level, int tlb_level)` | 按 stride 扩展边界；超限回退 `flush_tlb_mm`；普通分支在发出范围/逐页 TLBI 后通知已有回调，无最终 DSB；同文件 `:418-443`。 |
| `void __flush_tlb_range(struct vm_area_struct *vma, unsigned long start, unsigned long end, unsigned long stride, bool last_level, int tlb_level)` / `void flush_tlb_range(struct vm_area_struct *vma, unsigned long start, unsigned long end)` | 包装 nosync 并追加 DSB；公开范围接口使用 `PAGE_SIZE, false, 0`；同文件 `:445-464`。 |
| `void arch_tlbbatch_add_pending(struct arch_tlbflush_unmap_batch *batch, struct mm_struct *mm, unsigned long start, unsigned long end)` | 立即发出 nosync 范围失效，不保存参数；同文件 `:500-504`。 |
| `void arch_tlbbatch_flush(struct arch_tlbflush_unmap_batch *batch)` | 只有 `dsb(ish)`，没有 mm/range 参数；同文件 `:317-330`。 |
| `bool arch_tlbbatch_should_defer(struct mm_struct *mm)` / `void arch_flush_tlb_batched_pending(struct mm_struct *mm)` | repeat-TLBI workaround 可禁止批处理；并发补刷使用整 mm 失效，不以远端 DSB 代替；同文件 `:291-315`。 |

范围通常为 `[start,end)`；全 mm 使用已有哨兵 `(0, ULONG_MAX)`。新增回调是否沿用该全 mm 表达、范围代表请求值还是对齐/回退后的实际覆盖值，须在⑤明确，不能在范围回退后仍假定只失效原始小范围。

### 2.2 两种批处理不是同一种数据模型

| 数据结构 | 字段/归属 | 对本需求的含义 |
|---|---|---|
| `struct mmu_gather` | `mm`、`start/end`、`fullmm`、`freed_tables`、`cleared_*`；`include/asm-generic/tlb.h:302-339`。初始化固定 `tlb->mm = mm`；`mm/mmu_gather.c:376-399`。 | 一次 gather 关联一个 mm；范围与页表层级可追踪，但不是每次 gather 都真正执行用户 TLBI。 |
| `struct tlbflush_unmap_batch` | `arch`、`flush_required`、`writable`；`include/linux/mm_types_task.h:48-68`；挂在 `task_struct.tlb_ubc`，`include/linux/sched.h:1398`。 | **每任务不等于单 mm**，也不保证仅一个发起 CPU。 |
| `struct arch_tlbflush_unmap_batch` | arm64 当前为空，注释说明硬件 shootdown 无需 IPI cpumask；`arch/arm64/include/asm/tlbbatch.h:5-10`。 | 没有 mm、范围、发起 CPU、读清状态归属等记录。 |
| `mm->tlb_flush_batched` | pending/flushed 代数，由 atomic 操作推进；`mm/rmap.c:638-687,716-730`。 | 用来判断并发补刷，不是保存所有待通知 mm/range 的队列。 |

### 2.3 已有 notifier 的注册与调用契约

- 回调签名：`void (*arch_invalidate_secondary_tlbs)(struct mmu_notifier *subscription, struct mm_struct *mm, unsigned long start, unsigned long end)`；`include/linux/mmu_notifier.h:190-210`。`struct mmu_notifier` 有 `ops/mm/hlist/rcu/users`，见同文件 `:237-242`。
- 注册/撤销：`int mmu_notifier_register(struct mmu_notifier *subscription, struct mm_struct *mm)`、`int __mmu_notifier_register(struct mmu_notifier *subscription, struct mm_struct *mm)`、`void mmu_notifier_unregister(struct mmu_notifier *subscription, struct mm_struct *mm)`；声明见 `include/linux/mmu_notifier.h:300-305`。内部注册要求 mmap 写锁；现有 secondary 回调与 invalidate_range_start/end 同时注册会报错，`mm/mmu_notifier.c:606-628`。新增 ops 与既有 ops 的组合契约尚需单独定义，不能随意放宽旧检查。
- 包装器只在 `mm_has_notifiers(mm)` 时派发，`include/linux/mmu_notifier.h:486-491`；实现以 SRCU 保护链表，**在原调用栈逐一同步调用**，不是工作队列，`mm/mmu_notifier.c:588-604`。
- SRCU 可保护遍历/撤销竞态，不使调用点自动变成可睡眠上下文。现有回调明确可能在 PTL 自旋锁下调用，禁止睡眠，`include/linux/mmu_notifier.h:196-198`。新增回调若覆盖相同路径，也必须满足原子上下文约束；“驱动同步完成”不等于“允许睡眠等待”。
- 已有 consumer 示例是 SMMUv3 SVA：注册旧 ops，范围转大小后做 SMMU/ATC 失效，`drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3-sva.c:132-162,201-205`。这不是本需求新 consumer 的身份证据；实际注册新钩子的设备驱动仍未知。

## 3. 动态链与完成点缺口

### 3.1 普通失效与 mmu_gather

现有时序可概括为：

```text
flush_tlb_mm:       DSB ISHST -> ASID TLBI(+KPTI) -> DSB ISH -> 旧通知
page/range nosync:  DSB ISHST -> TLBI 序列          -> 旧通知 -> 返回
page/range sync:    nosync                        -> DSB ISH -> 返回
```

源码完成模板见 `arch/arm64/include/asm/tlbflush.h:175-181`，具体实现见§2.1。**不能将旧通知统一挪到 DSB 后来替代新增通知**：page/range 现有通知在末尾 DSB 之前，full-mm 在之后；需求要求保留这条链的行为。Oracle 裁定指出未决兼容性边界：功能激活时，现有 page/range 回调的 preDSB 时序**可能**需要加强为 postDSB（在完成 DSB 之后调用旧回调再走新机制），但当前**不假装能保留精确时序，也不授权静默改变现有语义**。该边界须在 ⑤ 阶段硬件契约输入后正式设计，不在本文裁决范围。

munmap 相关路径：`mm/mmap.c:2474-2481` 的 `tlb_gather_mmu -> unmap_vmas -> tlb_finish_mmu`；退出地址空间使用 fullmm，见 `:3456-3472`。通用 `tlb_flush_mmu()` 先 tlbonly 后释放，`mm/mmu_gather.c:370-374`；tlbonly 在有清除标志时调用架构 `tlb_flush`，`include/asm-generic/tlb.h:458-469`。

arm64 `tlb_flush(struct mmu_gather *tlb)` 根据页表释放选择 last-level、stride、TTL；fullmm 只有释放表时调用 `flush_tlb_mm`，否则直接返回，普通情况调用 `__flush_tlb_range`，见 `arch/arm64/include/asm/tlb.h:53-73`。所以应按实际发生的 eligible TLBI 建模，不能给没有发出 TLBI 的 fullmm 返回分支凭空制造一次读清检查。

原始指令序列不是一个软件调用对应一条指令：KPTI 的 `__tlbi_user`/`__tlbi_user_level` 追加用户 ASID 失效；repeat workaround 在指令间插入 DSB 并重复；范围宏还会拆分循环。见 `arch/arm64/include/asm/tlbflush.h:32-55,119-122,363-396`。内部 workaround DSB 不是整个序列的最终完成点；不得据此推定硬件状态已经覆盖最终一条 TLBI。读取粒度必须与硬件契约一致，不能在原始宏中逐指令破坏性读取。

### 3.2 reclaim 的每任务批处理：多 mm、多范围、可调度

```text
vmscan: TTU_BATCH_FLUSH -> try_to_unmap(folio)
  -> rmap_walk{_locked} -> 每个映射 VMA 的 try_to_unmap_one
  -> mm = vma->vm_mm -> 清 PTE（PTL 下）
  -> set_tlb_ubc_flush_pending -> arch_tlbbatch_add_pending
  -> __flush_tlb_range_nosync（旧通知已执行）
稍后 try_to_unmap_flush[_dirty] -> arch_tlbbatch_flush -> DSB ISH
```

证据：`mm/vmscan.c:1282-1307,1369,1485,1552`；`mm/rmap.c:1989-2002,1637-1641,1781-1794,648-659,617-635`。rmap 对匿名/文件 VMA 树迭代调用，且显式 `cond_resched()`，`mm/rmap.c:2625-2641,2689-2702`。单 folio 可以被多个进程映射，单任务 reclaim 又可遍历多个 folio；因此不能拿 `current->mm`、最后一个 mm 或一个无 mm 的并集范围代表整个批次。

批末 API 既没有 mm/range，arm64 batch 又为空；仅在 `arch_tlbbatch_flush()` 的 DSB 后读取无法恢复对应失效集合。现有 CPU TLB 完成依赖还包括上下文切换：`arch/arm64/kernel/process.c:542-548` 明确在可能迁移前完成本 CPU pending maintenance。这可以解释现有 CPU 维护的完成路径，**不提供本功能所需的原 CPU MMIO 读取或元数据归属**。

最终完成屏障必须针对发出相关 TLBI 的 CPU 分析；不能假设别的 CPU 执行一个 DSB 就等价。源码已明确远端 DSB 不保证此前 TLBI 完成，故并发补刷调用整 mm 失效，`arch/arm64/include/asm/tlbflush.h:306-315`。若批次跨调度/迁移，必须覆盖每个发起 CPU 上的完成与读清，而不是仅在任务最终 CPU 上读一次。

### 3.3 young-bit 路径独立于批末 flush

`int __ptep_clear_flush_young(struct vm_area_struct *vma, unsigned long address, pte_t *ptep)` 在清 young 后直接调用 `flush_tlb_page_nosync`；注释允许把最终 DSB 延至下次上下文切换，`arch/arm64/include/asm/pgtable.h:974-991`。

`int contpte_ptep_clear_flush_young(struct vm_area_struct *vma, unsigned long addr, pte_t *ptep)` 对连续 PTE 块采用同样策略，按 `CONT_PTE_SIZE` 对齐后调用范围 nosync，`arch/arm64/mm/contpte.c:511-530`。因此只修改 `flush_tlb_page/range` 同步包装器或 reclaim 批末都不完整：这两条路径没有在那里完成。现有对 CPU young-bit 老化容错的说明，不构成设备 read-clear 时序可延迟的硬件保证。

## 4. 并发、CPU 亲和与读清归属的开放不变量

以下为后续设计必须证明的条件，**不是已具备的保证**：

1. **CPU 固定区间**：从序列的首次相关 TLBI 到最终完成及本 CPU MMIO 读取，必须证明不会迁移；若保留延迟，则逐段保留原 CPU 责任。仅在 DSB 后调用 `smp_processor_id()` 不够，那里只能识别读取时 CPU，不能证明它是发起者。PTL 可能约束局部抢占，但并非全部包装器/批次生命周期的统一 CPU 固定协议。
2. **中断/嵌套归属**：禁止抢占不等于禁止本 CPU IRQ 重入。若另一上下文在 TLBI—DSB—读清之间发出相关 TLBI、消费同一状态或递归调用回调，就可能把 mm A 的 bit 归给 mm B，或提前清除 A 状态。必须明确实际入口的 IRQ/异常可达性、序列化范围、回调是否重入。不能未经证明直接宣称关抢占已解决，也不能默认任意关 IRQ 的长同步回调安全。
3. **状态与 mm/range 的一一归属**：一个 bit 不携带 mm。若累积多个目标的状态，需硬件保证可用一份待完成集合解释此次读值；在无法区分是哪条触发时，是否必须通知全部相关 mm/range、是否允许扩大范围，仍需定义。保留最后一个目标、读前清零、调试多读均不成立。
4. **完成与 MMIO 顺序**：CPU TLBI 的 DSB 完成语义不自动证明自定义设备状态已对 MMIO 可见；寄存器更新、总线顺序、映射属性、端序及读取 accessor/屏障须有硬件依据。不能假定 `readl` 或额外任意 DSB 自行补足缺失硬件契约。
5. **回调原子性与锁序**：保留 PTL 下可调用能力，不得睡眠、等待依赖同一 PTL 的完成者或无界轮询；驱动须说明设备完成的有界同步机制及失败处置。SRCU 不能解决设备锁、IRQ 和页表锁的死锁；新路径不得替换旧通知或改变其条件。
6. **延迟对象有效性**：若缓存 mm/range，必须在通知前持有有效 mm/订阅/设备引用，并定义 mm 退出、范围合并、队列容量与溢出处理；现有空 batch 与两个布尔值不提供这些保证。CPU 固定和对象引用是不同问题。

## 5. DT、初始化与资源生命周期

### 5.1 可参考的机制，不是本设备契约

- `struct device_node *of_get_cpu_node(int cpu, unsigned int *thread)` 按逻辑 CPU 查找匹配节点，返回带引用节点，结束需 `of_node_put()`，`drivers/of/cpu.c:101-129`。
- spin-table 用该接口读取 CPU 节点的 `cpu-release-addr`，保存每 CPU 地址并处理缺项；prepare 映射失败返回错误，使用后解除映射，`arch/arm64/kernel/smp_spin_table.c:43-104`。它映射的是启动协议要求的 Normal 内存，不应照搬 `ioremap_cache` 到本 MMIO。
- GICv3 先映射资源区域，并在失败时逐一回收，`drivers/irqchip/irq-gic-v3.c:2690-2755`；按 MPIDR affinity 与 `GICR_TYPER` 匹配后发布当前 CPU 的 redistributor 基址，`:1324-1368`。它依赖 GIC 已定义的寄存器/布局，不能推导新设备也有相同 affinity、stride 或寄存器发现能力。

两者只支持“逻辑 CPU 需解析到硬件资源、映射需有错误路径”的架构类比，**没有提供本需求 compatible、物理地址或 CPU—寄存器映射契约**。不能按 CPU 编号臆造地址步长，也不能把 CPU 节点顺序当作资源身份。

### 5.2 生命周期约束与缺口

| 阶段 | 必须解决的问题（方向，非最终方案） |
|---|---|
| 发现/映射 | DT binding 需规定 CPU 标识、资源归属、宽度/大小/对齐/端序；解析引用成对释放。初始化可失败，不得在持 PTL 的 TLBI 快路径中分配或临时映射。 |
| 首次启用 | 资源映射、CPU 关联及 consumer 就绪必须先于首次受该功能约束的 TLBI；不能仅选一个常规驱动 probe/initcall 就声称时序成立。未就绪时是禁止绑定设备、禁止启用功能还是拒绝平台，需确定；不能静默漏通知却允许设备使用映射。 |
| 部分失败 | 某些 CPU 映射失败时，不得发布“全局已启用”却留下可访问空指针/漏通知的 CPU。启用前回滚映射，或采用可证明的受限启用/绑定策略，选择待定；不能把失败当作 bit0 为 0。 |
| CPU hotplug | online 前须建立该 CPU 的可访问资源和状态归属；offline 前完成该 CPU pending TLBI/读清/通知，处理遗留位与再次 online。资源是否掉电、离线 CPU MMIO 是否仍可访问均待硬件说明，不能让另一 CPU 代读。 |
| 设备解绑/掉电 | 回调对象、MMIO 以及实际设备命令通路须在所有在途读/回调期间有效；不能让 devm 释放资源先于热路径退出。设备暂停/复位期间的完成语义仍需定义。 |
| 撤销/卸载 | 现有 `mmu_notifier_unregister` 与回调可并发，返回前以 SRCU 等待回调结束，`mm/mmu_notifier.c:802-850`。这不自动排空未来新增的延迟元数据或 MMIO 访问。未证明停用、排空、解绑及引用协议前，不支持可卸载映射提供者，禁止留下已释放函数指针/基址。 |

## 6. 缺口与候选补齐方向（留给④比较）

| 缺口 | 方向 A：功能激活时让相关 nosync 就地同步完成 | 方向 B：保留延迟并记录 mm/range/CPU 元数据 |
|---|---|---|
| 无末尾 DSB 的 page/range/young/contpte | 在仍持有目标参数的发起点建立完成、读清、通知；旧回调激活路径时序须单独解决，不能假定不变 | 记录各发起点，覆盖实际最终 DSB（含切换相关路径）和读清点，不能只补 reclaim 批末 |
| reclaim 批末丢失目标 | 不依赖空 batch 恢复 mm/range，功能开启时牺牲相关合批收益 | 保存多 mm、多范围及各发起 CPU，不能退化成单 mm 字段；需引用、合并、容量、溢出协议 |
| CPU/IRQ/read-clear 归属 | 区间较局部，但仍须证明 CPU 固定、IRQ 重入与回调锁序 | 区间更长，必须处理切换/迁移、嵌套和 hotplug；任务数据与 per-CPU 状态需可关联 |
| 性能/侵入性 | 增加 DSB、MMIO 和同步驱动耗时，削弱 reclaim/young 优化 | 保留潜在合批收益，但增加热路径记账、引用及完成路径耦合；硬件不支持状态合并时可能不可行 |

两方向均须保留配置关闭时现有 nosync、回调和指令语义；均不能跳过硬件状态可见性证明。A 不是已批准方案，B 也未证明可实现；本阶段不定新增钩子名、寄存器宏、状态结构或初始化级别。后续若不能满足归属不变量，应先收敛硬件/需求契约，而非写空回调、虚构地址或“以后补齐”的生产骨架。

## 7. 配置、构建、接口与影响

- **已有配置事实**：arm64 选择 `ARCH_WANT_BATCHED_UNMAP_TLB_FLUSH` 和 OF（`arch/arm64/Kconfig:113,262-263`）；`ARM64_CONTPTE` 控制 `contpte.o`（`arch/arm64/mm/Makefile:6`）；repeat workaround 的 defer 分支见 `arch/arm64/include/asm/tlbflush.h:291-304`。`MMU_NOTIFIER` 是 bool 并选择 INTERVAL_TREE，`mm/Kconfig:782-784`；core 目标在 `mm/Makefile:83`。
- **可能的变更位置，不是定名/落地清单**：`arch/arm64/Kconfig` 和 `arch/arm64/mm/Makefile` 可承载独立默认关闭的架构特性及支持目标；`include/linux/mmu_notifier.h`/`mm/mmu_notifier.c` 可承载新增 ops/派发语义；`tlbflush.h`、`pgtable.h`、`contpte.c` 及必要的批处理完成上下文是接入评估面。DT binding 可能位于 `Documentation/devicetree/bindings/`，具体归类待设备身份确定。不预定新 CONFIG、文件或函数名称；是否依赖或选择 MMU_NOTIFIER、是否限制内建须在④⑤定稿。
- **兼容性**：已有 `CONFIG_MMU_NOTIFIER` 关闭 stub 见 `include/linux/mmu_notifier.h:667-670`，新功能关闭也须无新增 MMIO/回调，并保持旧包装器语义；不能仅靠运行时空指针分支代替完整 config-off 契约。扩展公共 ops/批处理结构还需评估下游模块构建与 KABI 影响。
- **外部接口**：当前需求未确立 syscall/ioctl/sysfs/procfs/debugfs 等用户 ABI；DT 新 binding 一旦引入将成为需维护的平台 ABI，目前尚未定义。不能以调试读取 read-clear 状态增加观测接口。新 consumer 未知，无法给出真实设备侧同步完成能力结论。
- **热路径及依赖**：影响 munmap/退出、mprotect 等既有失效调用者、reclaim、页老化、连续 PTE、KPTI/errata 组合及已有 SMMU 等 notifier consumer；增加 DSB、MMIO 总线延迟、回调遍历/设备同步开销，可能延长 PTL/禁抢占/禁 IRQ 区间。B 额外牵涉调度切换和热插拔。上述文件的并行改动存在冲突面，尚无已知并行任务清单。集成依赖应先明确硬件/DT 与回调上下文契约，再联动资源生命周期、通知及 consumer；不能只合架构触发端就宣称设备功能可用。
